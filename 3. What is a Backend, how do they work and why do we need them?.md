## 03. What is a Backend, How Does It Work & Why Do We Need It?

### 1. What is a Backend?

At its simplest, a backend is a **computer/server that listens for requests** through an open network port.

Clients can communicate with it using protocols such as:

* HTTP
* WebSocket
* gRPC
* Other application protocols

The backend can:

* Receive data from clients
* Process data
* Return data
* Serve static content
* Persist and retrieve data
* Perform business logic

A simple mental model:

```text
Client
   │
   │ Request
   ▼
Backend Server
   │
   │ Process
   ▼
Response
   │
   ▼
Client
```

The important idea is that a backend isn't necessarily some special machine. **It is essentially a computer running software that accepts and processes requests.** 

---

# 2. How Does a Backend Work?

Consider a backend deployed on an AWS EC2 instance.

A request from a browser doesn't magically appear inside the Node.js application.

It travels through several layers.

```text
Browser
   ↓
DNS
   ↓
Public IP
   ↓
Firewall
   ↓
EC2 Instance
   ↓
Reverse Proxy
   ↓
Backend Application
   ↓
Response
```

This request journey is one of the most important things to understand.

---

# 3. Domain Name → DNS

Suppose the client requests:

```text
https://backend.example.com/users
```

The browser needs to know:

> **Which machine should I send this request to?**

That's where **DNS (Domain Name System)** comes in.

DNS maps domain names to network destinations.

A simplified example:

```text
backend.example.com
          ↓
        DNS
          ↓
    203.0.113.10
          ↓
      AWS EC2
```

Two common DNS records mentioned here:

### A Record

Maps a domain/subdomain to an IP address.

```text
backend.example.com
        ↓
203.0.113.10
```

### CNAME Record

Maps a domain/subdomain to another domain name.

```text
api.example.com
       ↓
backend.example.com
```

The important takeaway:

> **DNS helps translate a human-readable domain name into where the request should go.** 

---

# 4. DNS → AWS Server

In the example from the video, the DNS A record points to the **public IP address of an AWS EC2 instance**.

```text
backend.example.com
        ↓
       DNS
        ↓
Public IP
        ↓
AWS EC2 Instance
```

So the request can now reach the machine hosting the backend.



---

# 5. Firewall / Security Group 🔥

Before the request reaches the actual computer, it passes through a firewall.

In AWS, this is controlled through the instance's **Security Group**.

The security group determines which ports are accessible.

For example:

```text
Internet
   │
   ▼
Firewall
   │
   ├── Port 80  → HTTP
   │
   ├── Port 443 → HTTPS
   │
   └── Other allowed ports
```

If port `443` isn't allowed:

```text
HTTPS Request
      ↓
Firewall
      ↓
   BLOCKED ❌
```

The request never reaches the application.



### Important distinction

```text
DNS
→ Where should the request go?

Firewall
→ Is this traffic allowed to enter?
```

---

# 6. Reverse Proxy

Once the request reaches the EC2 instance, it doesn't necessarily go directly to the Node.js application.

The video uses **Nginx** as a reverse proxy.

### What is a reverse proxy?

A reverse proxy is a server that sits **in front of other servers**.

```text
Internet
    ↓
 Nginx
    ↓
Backend Server
```

Instead of exposing every application's configuration directly, Nginx can provide a centralized point for things such as:

* Routing
* Redirects
* SSL/TLS configuration
* Domain handling
* Proxying requests



---

# 7. HTTP → HTTPS

In the example, Nginx listens on port `80` and redirects HTTP traffic to HTTPS on port `443`.

```text
HTTP
Port 80
   ↓
Nginx
   ↓
HTTPS
Port 443
```

So:

```text
http://example.com
        ↓
    Redirect
        ↓
https://example.com
```

The video also mentions Certbot as part of automatically managing SSL certificates.



---

# 8. Nginx → Node.js

Nginx then forwards the request to the actual backend application.

In the example:

```text
Internet
   ↓
DNS
   ↓
AWS EC2
   ↓
Nginx
   ↓
localhost:3001
   ↓
Node.js Backend
```

The Node.js application is running locally on port `3001`.

Nginx essentially says:

> "Requests arriving for this domain should be forwarded to the application running on port 3001."



---

# 9. Why `localhost`?

Inside the EC2 machine, the Node.js server can simply be running on:

```text
localhost:3001
```

The outside world doesn't need to directly access this port.

Instead:

```text
Internet
   ↓
Nginx :443
   ↓
localhost:3001
   ↓
Node.js
```

This gives us a useful separation:

```text
Public-facing
     ↓
   Nginx
     ↓
Private application
```

# 11. What Happens in Development?

When developing locally, this entire network path is much simpler.

You might simply do:

```text
Browser
   ↓
localhost:3000
   ↓
Frontend
```

or:

```text
Browser
   ↓
localhost:3001
   ↓
Backend
```

There is no need for:

```text
DNS
AWS
Public IP
Firewall
Nginx
```

because everything is running on your own machine.

# 12. Why Do We Need Backends?

This is the central question.

Imagine Instagram.

You press:

```text
❤️ Like
```

What needs to happen?

```text
You click Like
      ↓
Frontend sends request
      ↓
Backend receives request
      ↓
Identify the user
      ↓
Identify the post
      ↓
Persist the Like
      ↓
Find the post owner
      ↓
Trigger notification
      ↓
Friend receives notification
```

The frontend alone isn't responsible for coordinating all of this.

The backend maintains and processes the underlying application data and state. 

---

# 13. The Core Responsibility of a Backend

If we reduce backend responsibility to one central idea:

# **DATA**

A backend deals heavily with:

```text
Receive Data
     ↓
Process Data
     ↓
Store Data
     ↓
Retrieve Data
     ↓
Modify Data
     ↓
Send Data
```

This includes application state such as:

* Users
* Posts
* Likes
* Followers
* Orders
* Payments
* Permissions
* Notifications
* Preferences

The backend acts as the centralized system that manages this state for many clients.



---

# 14. Why Not Put Everything in the Frontend?

This is an important interview question.

> **Why can't we simply connect the frontend directly to the database and perform all business logic there?**

There are several problems.

---

## Reason 1 — Security 🔐

Frontend code runs on the user's machine.

Anything sent to the browser can potentially be inspected.

You cannot trust the client with:

* Database credentials
* Secret API keys
* Internal business logic
* Privileged operations

The backend provides a controlled environment for sensitive operations.

---

# 15. Reason 2 — Browser Sandbox

JavaScript running in a browser is heavily restricted.

The browser operates in a **sandboxed environment**.

```text
Browser JavaScript
       │
       ├── DOM
       ├── Browser APIs
       ├── Cookies
       ├── Local Storage
       └── Limited external access
```

It cannot freely access:

* The operating system
* Arbitrary files
* Server environment variables
* Internal system resources

This isolation exists for security.

Imagine visiting a malicious website and its JavaScript being able to freely read your computer's files.

That would be disastrous.



---

# 16. Reason 3 — CORS

Browsers restrict JavaScript from freely calling other origins.

This is where **CORS (Cross-Origin Resource Sharing)** comes in.

For example:

```text
Frontend
https://frontend.example.com

        ↓

Backend
https://api.example.com
```

These are different origins.

The browser applies cross-origin security rules.

The backend can explicitly allow the frontend through appropriate HTTP headers.

### Important

CORS is primarily a **browser security mechanism**.

A server-to-server request isn't subject to the browser's CORS enforcement in the same way.

The video introduces this concept here and indicates it will be explored more deeply later. 

---

# 17. Reason 4 — Database Access

Backend environments can use database drivers directly.

For example:

```text
Node.js
   ↓
PostgreSQL Driver
   ↓
PostgreSQL
```

or:

```text
Backend
   ↓
MongoDB Driver
   ↓
MongoDB
```

These environments can handle things such as:

* Socket connections
* Binary data
* Persistent connections
* Connection pooling
* Efficient query execution

Browsers aren't designed to directly manage database connections in this way.



---

# 18. Connection Pooling

A backend can maintain a pool of database connections.

```text
Backend
   │
   ├──── Connection 1 ────┐
   ├──── Connection 2 ────┤
   ├──── Connection 3 ────┤
   ├──── Connection 4 ────┤
   └──── Connection 5 ────┘
                           ↓
                       Database
```

Instead of creating a new database connection for every request:

```text
Request
 ↓
Create connection
 ↓
Query
 ↓
Destroy connection
```

we can reuse existing connections.

```text
Request
 ↓
Get connection from pool
 ↓
Query
 ↓
Return connection to pool
```

This becomes especially important when thousands of requests arrive.

Without connection pooling, repeatedly creating and destroying connections could overwhelm the database.



---

# 19. Reason 5 — Computing Power 💻

Frontend code runs on the user's device.

That device could be:

```text
High-end PC
Laptop
Phone
Tablet
Low-powered device
```

Not every client has the same CPU or memory.

Heavy business logic running entirely on the client could cause:

```text
Heavy Computation
       ↓
Weak Device
       ↓
High CPU / Memory Usage
       ↓
Slow Application
```

A centralized backend can provide predictable and scalable computing resources.

```text
             Backend
           ┌─────────┐
           │ CPU     │
           │ Memory  │
           │ Storage │
           └────┬────┘
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
    Client   Client   Client
```

Resources can also be increased as load grows.

# 20. How Frontends Actually Work

The video also demonstrates why frontend and backend execution are fundamentally different.

Suppose we have a Next.js application.

The browser initially requests the page:

```text
Browser
   ↓
Frontend Server
   ↓
HTML
```

Then the browser requests additional resources:

```text
HTML
 ├── JavaScript
 ├── CSS
 ├── Images
 └── Fonts
```

The browser downloads these resources and executes the JavaScript **on the user's machine**.



---

# 21. Frontend vs Backend Execution

This distinction is extremely important.

### Backend

```text
Request
   ↓
Server
   ↓
Backend code executes
   ↓
Result
   ↓
Client
```

### Frontend

```text
Server
   ↓
Sends HTML / JS / CSS
   ↓
Browser
   ↓
JavaScript executes
   ↓
UI interaction
```

In other words:

> **Backend code is executed on the server.**

> **Frontend JavaScript is generally executed by the browser.**



---

# 22. Why Browser Restrictions Exist

The browser receives code from potentially unknown remote servers.

Therefore, that code cannot be allowed unrestricted access to the user's computer.

Without sandboxing:

```text
Visit Website
     ↓
Website JavaScript
     ↓
Read arbitrary files ❌
     ↓
Access sensitive information ❌
```

Instead, browsers isolate web applications.

```text
Browser
┌─────────────────────────┐
│       Sandbox           │
│                         │
│  Web Application        │
│       ↓                 │
│  Limited APIs           │
└─────────────────────────┘
```

This is a fundamental reason why sensitive backend operations belong on servers.



---

# 23. Backend vs Frontend

|                           | Frontend                 | Backend                          |
| ------------------------- | ------------------------ | -------------------------------- |
| Runs on                   | User's device            | Server                           |
| Runtime                   | Browser / client runtime | Server runtime                   |
| Main role                 | UI & interaction         | Data & business logic            |
| Database access           | Restricted / indirect    | Direct through drivers           |
| File system               | Sandboxed                | Server resources                 |
| Secrets                   | Cannot safely store them | Can manage secrets               |
| Computing                 | Depends on client        | Centralized resources            |
| Cross-origin restrictions | Browser enforced         | Not the same browser restriction |

# ⭐ Key Takeaways

1. **A backend is fundamentally a server that listens for and processes requests.**
2. A backend can communicate through HTTP, WebSockets, gRPC, and other protocols.
3. A typical Internet request may travel through **DNS → IP → firewall → reverse proxy → application**.
4. **DNS resolves domain names to network destinations.**
5. **Firewalls control which traffic can reach the server.**
6. **Nginx can act as a reverse proxy in front of the application.**
7. A backend manages application **data and state** for many clients.
8. Frontend code generally executes on the user's device, while backend code executes on the server.
9. Browser sandboxing prevents web applications from freely accessing the user's machine.
10. Backend applications can communicate directly with databases using appropriate drivers.
11. **Connection pooling** avoids repeatedly creating and destroying database connections.
12. Centralized backend infrastructure provides predictable computing resources and allows systems to scale.
13. Backend and frontend aren't simply two parts of the same codebase—they operate in **different environments with different capabilities and constraints**.

---

# 🔥 One-Line Summary

**A backend is the server-side system that receives requests, processes data and business logic, interacts with other systems, maintains application state, and returns results to clients.**
