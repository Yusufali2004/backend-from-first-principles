# 18. Logging, Monitoring & Observability 🔭

> **A production system that you cannot see is a system you cannot reliably operate.**
>
> Your backend can be running, but that doesn't mean it's healthy.
>
> Requests might be getting slower, error rates might be increasing, a database might be running out of connections, or one service might be failing intermittently.
>
> **Logging, monitoring, and observability are the tools that let us understand what is happening inside a running system.**
>
> This chapter is about learning to answer three questions:
>
> **What happened? → Logs**
> **Is something wrong? → Monitoring**
> **Why is it happening? → Observability**

The source video is the chapter you've linked as **"18. Logging, Monitoring and Observability."** ([YouTube][1])

---

# 1. Why Do We Need Observability?

Imagine your API suddenly becomes slow.

Users report:

```text
"Website is taking 10 seconds to load."
```

You look at the server:

```text
Server: Running ✅
CPU: 40%
Memory: 50%
```

Everything looks normal.

So what happened?

Maybe:

```text
Database queries became slow
        ↓
API requests wait longer
        ↓
Response latency increases
```

Without proper observability, you're guessing.

With observability:

```text
Metrics
  ↓
Latency increased

Logs
  ↓
Database timeout errors

Traces
  ↓
90% of request time spent in PostgreSQL
```

Now you have an explanation.

---

# 2. The Three Pillars

The classic model is:

```text
             OBSERVABILITY
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
     Logs       Metrics     Traces
       │          │          │
    Events      Numbers    Requests
       │          │          │
       └──────────┼──────────┘
                  ↓
            System Understanding
```

These aren't interchangeable.

Each answers a different question.

---

# 3. Logs

Logs are records of events that happened inside your system.

Example:

```text
2026-09-01 21:20:31
INFO
User authenticated
userId=123
```

Another:

```text
2026-09-01 21:20:32
ERROR
Database connection failed
```

Logs are generally best for answering:

> **"What happened?"**

---

# 4. Metrics

Metrics are numerical measurements collected over time.

Examples:

```text
CPU usage
Memory usage
Request count
Error count
Request latency
Database connections
Queue depth
```

For example:

```text
Requests/sec = 2,500
Error rate   = 1.2%
p95 latency  = 420ms
CPU          = 72%
```

Metrics are excellent for:

> **"Is the system healthy?"**

and:

> **"Is something changing?"**

---

# 5. Traces

A trace follows a request through multiple components.

For example:

```text
Client
  ↓
API Gateway
  ↓
User Service
  ↓
Order Service
  ↓
PostgreSQL
```

A trace can show:

```text
Total request: 1.2s

API Gateway      20ms
User Service     80ms
Order Service    100ms
PostgreSQL       950ms
```

Now you immediately know:

> PostgreSQL is responsible for most of the latency.

Traces are especially valuable in distributed systems.

---

# 6. Logs vs Metrics vs Traces

| Signal      | Best question                          |
| ----------- | -------------------------------------- |
| **Logs**    | What happened?                         |
| **Metrics** | How is the system behaving?            |
| **Traces**  | Where did this request spend its time? |

Think:

```text
Logs
"What happened?"

Metrics
"Is something wrong?"

Traces
"Where exactly did it happen?"
```

---

# 7. Logging

Logging is more than:

```javascript
console.log("hello");
```

Production logging needs structure, context, appropriate levels, storage, retention, and security controls.

A useful log should help someone understand:

```text
What happened?
When?
Where?
For which request?
What operation?
What went wrong?
```

---

# 8. Log Levels

Common log levels include:

```text
TRACE
DEBUG
INFO
WARN
ERROR
FATAL
```

Not every system uses all of them.

A common hierarchy is:

```text
DEBUG
  ↓
INFO
  ↓
WARN
  ↓
ERROR
  ↓
FATAL
```

---

# 9. DEBUG

Used for detailed information useful during development or troubleshooting.

Example:

```text
DEBUG
Executing SQL query
query=SELECT ...
```

You generally don't want enormous amounts of debug logging enabled permanently in production.

---

# 10. INFO

Normal operational events.

Example:

```text
INFO
Server started
port=3000
```

or:

```text
INFO
User registered
userId=123
```

These logs describe normal application behavior.

---

# 11. WARN

Something unusual happened, but the system can continue.

Example:

```text
WARN
Redis unavailable
Using database fallback
```

The request might still succeed.

---

# 12. ERROR

Something failed.

Example:

```text
ERROR
Failed to process payment
orderId=123
provider=Stripe
```

An error usually deserves investigation, though not every error necessarily means the entire system is unhealthy.

---

# 13. FATAL

A severe problem that prevents the application from continuing safely.

For example:

```text
FATAL
Required configuration missing
DATABASE_URL
```

The application may terminate.

---

# 14. Structured Logging ⭐

Bad:

```text
User Yusuf logged in from Bangalore
```

Better:

```json
{
  "level": "info",
  "event": "user_login",
  "userId": "123",
  "ip": "10.0.0.1"
}
```

This is:

> **Structured logging**

Instead of putting everything into an unstructured string, you store meaningful fields.

---

# 15. Why Structured Logs Matter

Suppose you have:

```text
10 million logs
```

and want:

```text
all payment failures
for service=payment
during the last hour
```

With structured logs, you can query fields:

```text
service = "payment"
level = "error"
event = "payment_failed"
```

Instead of trying to search arbitrary text.

---

# 16. Contextual Logging

A log should contain useful context.

Instead of:

```text
ERROR Payment failed
```

prefer something like:

```text
ERROR
event=payment_failed
requestId=req_abc123
orderId=order_456
userId=user_789
provider=payment_service
errorCode=TIMEOUT
```

Now the engineer has something to investigate.

---

# 17. Request IDs ⭐

Suppose a request goes through:

```text
Client
 ↓
API Gateway
 ↓
Order Service
 ↓
Payment Service
 ↓
Database
```

Give the request a unique identifier:

```text
requestId=req_abc123
```

Then every service logs it.

```text
API Gateway
req_abc123

Order Service
req_abc123

Payment Service
req_abc123
```

You can now search for:

```text
req_abc123
```

and reconstruct the request's journey.

---

# 18. Correlation IDs

In distributed systems, you may have several related operations.

For example:

```text
Checkout Request
      ↓
Order Created
      ↓
Payment Requested
      ↓
Email Sent
```

A correlation ID can connect related events.

Conceptually:

```text
Correlation ID
      │
 ┌────┼────┬────┐
 ↓    ↓    ↓    ↓
Order Payment Email DB
```

This becomes extremely useful when debugging asynchronous systems.

---

# 19. Don't Log Secrets 🚨

Never blindly log:

```text
Passwords
API keys
Access tokens
JWTs
Private keys
Database passwords
Credit-card information
```

Bad:

```javascript
logger.info({
  user,
  headers,
  config
});
```

because those objects might contain sensitive information.

Instead:

```text
Log only what you actually need.
```

---

# 20. Sensitive Data Redaction

Sometimes a field is useful but shouldn't be logged completely.

For example:

```text
Authorization: Bearer eyJ...
```

should not be stored as-is.

You might log:

```text
authPresent=true
```

instead.

Or redact:

```text
email=j***@gmail.com
```

depending on the requirements.

---

# 21. Logging Isn't Free

Logging consumes:

```text
CPU
Memory
Disk
Network bandwidth
Storage
```

Imagine every request generates:

```text
50 KB logs
```

and you receive:

```text
100,000 requests/sec
```

That's enormous log volume.

Therefore:

> **Log useful information, not everything.**

---

# 22. Log Sampling

For extremely high-volume systems, you may sample logs.

For example:

```text
100,000 requests
       ↓
Log 1,000 representative requests
```

But important events should generally still be captured.

For example:

```text
Authentication failure
Payment failure
Security event
Database failure
```

shouldn't simply disappear because of sampling.

---

# 23. Centralized Logging

Suppose you have:

```text
Server A
Server B
Server C
Server D
```

Each produces logs.

If logs remain only on each machine:

```text
Server A → logs
Server B → logs
Server C → logs
Server D → logs
```

debugging becomes painful.

Instead:

```text
Server A ─┐
Server B ─┤
Server C ─┼──→ Central Log System
Server D ─┘
```

Now engineers have one place to search.

---

# 24. Log Aggregation

A common architecture:

```text
Application
    ↓
Log Agent / Collector
    ↓
Log Pipeline
    ↓
Central Storage
    ↓
Search / Visualization
```

Examples of technologies in this ecosystem include:

```text
ELK / Elastic Stack
OpenSearch
Loki
Fluent Bit
Fluentd
```

The specific tool isn't the important part.

The architecture is.

---

# 25. Log Rotation

Logs can grow indefinitely.

Suppose:

```text
application.log
```

continues growing:

```text
1 GB
5 GB
20 GB
100 GB
```

Eventually you'll have problems.

Log rotation creates manageable log files:

```text
app-2026-09-01.log
app-2026-08-31.log
app-2026-08-30.log
```

and old logs can be compressed or deleted according to retention policies.

---

# 26. Log Retention

You need to decide:

> **How long should logs be stored?**

For example:

```text
Debug logs → 3 days
Application logs → 30 days
Security logs → 1 year
```

The exact retention depends on:

```text
Cost
Compliance
Security
Debugging requirements
Business requirements
```

# 27. Monitoring

Monitoring is about continuously collecting measurements and checking whether the system is behaving within acceptable limits.

For example:

```text
CPU > 90%
```

could trigger an alert.

Or:

```text
Error rate > 5%
```

could trigger an alert.

---

# 28. What Should We Monitor?

Think across several layers.

```text
Monitoring
│
├── Infrastructure
├── Application
├── Database
├── Network
├── Dependencies
└── Business
```

---

# 29. Infrastructure Monitoring

Examples:

```text
CPU
Memory
Disk
Network
Load
Container health
Instance count
```

Example:

```text
CPU = 95%
```

could indicate resource exhaustion.

But remember:

> High CPU doesn't automatically mean the application is broken.

Metrics need context.

---

# 30. Application Monitoring

Monitor things such as:

```text
Request rate
Error rate
Latency
HTTP status codes
Active requests
Queue depth
Throughput
```

For example:

```text
Requests/sec = 5,000
5xx = 3%
p95 = 900ms
```

These tell you much more about application health.

---

# 31. Database Monitoring

Important database metrics include:

```text
Connection count
Connection pool usage
Query latency
Slow queries
Lock contention
CPU
Memory
Disk usage
Replication lag
Cache hit ratio
```

A backend might look healthy while the database is becoming the bottleneck.

---

# 32. Dependency Monitoring

Your application may depend on:

```text
Payment API
Email provider
Object storage
Authentication provider
Search service
Redis
```

Monitor:

```text
Availability
Latency
Error rate
Timeouts
Rate limits
```

For example:

```text
Payment API
Latency → 200ms → 250ms → 1s → 5s
```

That trend can warn you before complete failure.

---

# 33. Business Metrics

Monitoring isn't only infrastructure.

You can monitor business-level signals.

For an e-commerce system:

```text
Orders/minute
Checkout success rate
Payment success rate
Cart abandonment
Revenue
```

Imagine:

```text
Server health → ✅
CPU → 40%
Memory → 50%
```

but:

```text
Payment success rate → 40% ❌
```

Your infrastructure looks healthy while the business is effectively broken.

---

# 34. The Four Golden Signals

A very useful framework for service monitoring is the **Four Golden Signals**:

```text
Latency
Traffic
Errors
Saturation
```

---

# 35. Latency

> How long does it take to serve requests?

Example:

```text
p50 = 100ms
p95 = 300ms
p99 = 900ms
```

Monitor both normal latency and tail latency.

---

# 36. Traffic

> How much demand is the system receiving?

Examples:

```text
Requests/sec
Messages/sec
Orders/minute
Bytes/sec
```

Traffic helps you understand load.

---

# 37. Errors

> How many requests are failing?

Examples:

```text
HTTP 500
HTTP 503
Timeouts
Database failures
Dependency failures
```

For example:

```text
Error rate:
0.2% → 0.4% → 1% → 5%
```

could indicate a serious problem.

---

# 38. Saturation

> How close are your resources to their limits?

Examples:

```text
CPU utilization
Memory usage
Disk utilization
DB connection pool
Thread pool
Queue capacity
```

A service at:

```text
95% connection pool utilization
```

may be close to failure even if requests are currently succeeding.

---

# 39. Monitoring Dashboard

A useful backend dashboard might show:

```text
┌──────────────────────────────────────┐
│ API HEALTH                           │
├──────────────────────────────────────┤
│ Requests/sec          4,250          │
│ Error Rate              0.4%         │
│ p95 Latency             280ms        │
│ p99 Latency             720ms        │
│ CPU                      65%         │
│ Memory                   58%         │
│ DB Connections           72%         │
│ Queue Depth              120         │
└──────────────────────────────────────┘
```

The goal isn't to create pretty dashboards.

The goal is:

> **Make important system behavior visible.**

---

# 40. Alerts

Monitoring becomes useful operationally when abnormal conditions generate alerts.

For example:

```text
IF error_rate > 5%
FOR 5 minutes
THEN alert
```

Or:

```text
IF p99_latency > 2 seconds
FOR 10 minutes
THEN alert
```

---

# 41. Alert Fatigue 🚨

A dangerous monitoring system produces:

```text
100 alerts/day
```

Engineers eventually stop paying attention.

This is:

> **Alert fatigue**

Bad:

```text
CPU = 81%
→ ALERT

CPU = 82%
→ ALERT

CPU = 83%
→ ALERT
```

Better:

```text
CPU > 90%
for 10 minutes
→ ALERT
```

Only alert when someone needs to take action.

---

# 42. Symptoms vs Causes

Suppose:

```text
Database becomes slow
```

causes:

```text
API latency increases
```

which causes:

```text
Requests timeout
```

You might receive three alerts:

```text
API latency high
Request timeout high
Database latency high
```

The underlying cause might be:

```text
Database problem
```

Good alert design tries to help engineers identify the root cause rather than flooding them with symptoms.

---

# 43. Observability

Monitoring tells you:

```text
Something is wrong.
```

Observability helps you investigate:

```text
Why is it wrong?
```

A useful mental model:

```text
Monitoring
→ Known problems

Observability
→ Investigating unknown problems
```

---

# 44. High Observability

Suppose you receive:

```text
Error rate increased to 10%.
```

That's monitoring.

Now you can ask:

```text
Which endpoint?
Which service?
Which instance?
Which database query?
Which dependency?
Which users?
Which deployment?
```

and answer those questions from telemetry.

That's observability.

---

# 45. Distributed Tracing ⭐

Consider:

```text
Request
 ↓
API Gateway
 ↓
User Service
 ↓
Order Service
 ↓
Payment Service
 ↓
PostgreSQL
```

A distributed trace can represent the request as spans:

```text
Trace
│
├── API Gateway       20ms
│
├── User Service      50ms
│
├── Order Service     100ms
│    │
│    └── PostgreSQL   80ms
│
└── Payment Service   800ms
```

Immediately:

```text
Payment Service
```

looks suspicious.

---

# 46. Span

A **span** represents one operation within a trace.

For example:

```text
Trace: checkout_request

Span 1:
API Gateway

Span 2:
Create Order

Span 3:
Database Query

Span 4:
Payment API
```

Together:

```text
Spans
 ↓
Trace
```

---

# 47. Trace Context

A trace needs identifiers that can travel between services.

Conceptually:

```text
traceId
spanId
parentSpanId
```

So:

```text
Service A
trace=123
span=A
      ↓
Service B
trace=123
span=B
      ↓
Service C
trace=123
span=C
```

Now the tracing system can reconstruct the entire request.

---

# 48. OpenTelemetry

A major modern standard/ecosystem for collecting telemetry is:

> **OpenTelemetry**

It provides APIs, SDKs, and instrumentation for telemetry such as:

```text
Traces
Metrics
Logs
```

The important architectural idea:

```text
Application
    ↓
OpenTelemetry
    ↓
Telemetry backend
```

You can instrument your application without tightly coupling all observability logic to one vendor.

# 50. Monitoring vs Observability

This is a common interview question.

### Monitoring

You define:

```text
What should I watch?
```

and detect known failure conditions.

Example:

```text
Error rate > 5%
```

### Observability

You design the system so that:

```text
I can investigate what's happening internally
using the outputs the system produces.
```

The distinction is subtle but important.

---

# 51. Logs + Metrics + Traces Together

Imagine:

```text
Metric:
p99 latency increased
```

↓

```text
Trace:
Payment Service takes 4 seconds
```

↓

```text
Log:
Payment provider returned timeout
```

Now:

```text
Metric → tells you WHAT
Trace  → tells you WHERE
Log    → tells you DETAILS
```

This is why the three signals complement each other.

  ↓

# 53. Deployment Correlation

Suppose your application suddenly becomes unhealthy:

```text
12:00 → normal
12:05 → latency spikes
```

Check deployments:

```text
12:04 → version 2.8 deployed
```

That correlation is extremely useful.

This is why observability systems should make it easy to associate telemetry with:

```text
Version
Deployment
Instance
Environment
Service
Region
```

# 54. SLI

A **Service Level Indicator (SLI)** is a measurement of an aspect of service behavior.

Examples:

```text
Request success rate
Request latency
Availability
```

For example:

```text
Successful requests / Total requests
```

might be an availability-related SLI.

---

# 55. SLO

A **Service Level Objective (SLO)** defines a target for an SLI.

Example:

```text
99.9% of requests should succeed
```

or:

```text
95% of requests should complete within 300ms
```

The SLO is the target.

---

# 56. SLA

An **SLA (Service Level Agreement)** is generally a formal agreement with users/customers about service expectations and potentially consequences if those expectations aren't met.

Think:

```text
SLI
→ What we measure

SLO
→ What target we want

SLA
→ What we formally promise
```

---

# 57. Error Budget ⭐

Suppose your SLO is:

```text
99.9% availability
```

Then you're allowed roughly:

```text
0.1%
```

of unavailability.

That allowed failure is your:

> **Error budget**

It gives engineering teams a way to balance:

```text
Reliability
vs
Feature velocity
```

If you're constantly burning the error budget, you may need to prioritize reliability work.

---

# 58. Observability and Cost

Observability can become expensive.

You may generate:

```text
Millions of logs
Billions of metrics
Huge trace volumes
```

So you need to consider:

```text
Sampling
Retention
Aggregation
Filtering
Cardinality
Storage
```

---

# 59. High Cardinality

Suppose you create a metric label:

```text
user_id
```

and have:

```text
10 million users
```

Now you potentially have millions of unique time series.

This can become expensive and difficult to operate.

Be careful with labels such as:

```text
user_id
request_id
session_id
```

in high-volume metrics.

Use them more appropriately in logs or traces where possible.

---

# 60. Logging vs Metrics: A Practical Example

Suppose you want to know how many payment failures occurred.

### Metric

```text
payment_failures_total = 1,245
```

Excellent for:

```text
Dashboards
Alerts
Trends
```

### Log

```json
{
  "event": "payment_failed",
  "orderId": "123",
  "provider": "X",
  "reason": "timeout"
}
```

Excellent for:

```text
Debugging individual failures
```

You often need both.

---

# 61. Monitoring vs Logging: Don't Confuse Them

You shouldn't create an alert by manually searching logs every time.

Instead:

```text
Logs
→ Detailed events

Metrics
→ Aggregated measurements

Alerts
→ Automated detection
```

For example:

```text
payment_failed logs
        ↓
payment_failure metric
        ↓
Alert if > threshold
```

# 🧠 Interview Mental Models

### What is logging?

> Recording application and system events so that they can be inspected later.

---

### What is monitoring?

> Continuously collecting measurements and checking them against expected behavior or thresholds to detect problems.

---

### What is observability?

> The ability to understand a system's internal behavior and diagnose problems from the telemetry it produces.

---

### What are the three pillars?

```text
Logs
Metrics
Traces
```

---

### What is structured logging?

> Logging events as structured fields rather than only unstructured text, making logs easier to search, aggregate, and analyze.

---

### Why use request IDs?

> To correlate logs and operations belonging to the same request across different components and services.

---

### What are the Four Golden Signals?

```text
Latency
Traffic
Errors
Saturation
```

---

### What is a trace?

> A representation of a request's journey through one or more services, composed of individual spans.

---

### What is a span?

> A single timed operation within a distributed trace.

---

### What is alert fatigue?

> A condition where excessive or low-value alerts cause engineers to become desensitized to alerts, increasing the risk of missing important incidents.

---

### What is the difference between SLI, SLO, and SLA?

```text
SLI
→ Measurement

SLO
→ Target

SLA
→ Formal commitment
```

# ⚠️ Interview Traps

### ❌ "Observability means adding lots of logs."

No.

```text
Observability
≠
Lots of logs
```

You need meaningful telemetry:

```text
Logs
Metrics
Traces
```

---

### ❌ "Monitoring and observability are exactly the same."

Not quite.

```text
Monitoring
→ Detect known problems

Observability
→ Investigate system behavior and unknown problems
```

---

### ❌ "Log everything."

No.

Too much logging creates:

```text
Cost
Noise
Performance overhead
Storage problems
Security risks
```

Log information that helps operate and debug the system.

---

### ❌ "CPU is high, so the application is broken."

Not necessarily.

CPU may be high because:

```text
Traffic increased
```

and the system might be scaling correctly.

Always correlate multiple signals.

---

### ❌ "Just alert whenever an error occurs."

This can create alert fatigue.

Instead:

```text
Error
 ↓
Aggregate
 ↓
Define meaningful threshold
 ↓
Alert when action is required
```

---

### ❌ "Put user_id in every metric."

Careful.

High-cardinality labels can make metrics expensive and difficult to manage.

User-specific details are often better suited to logs/traces.

# 🔥 Core Takeaways

* **Logging records events.**
* **Monitoring measures system health.**
* **Observability helps you understand why the system behaves the way it does.**
* The three major observability signals are **logs, metrics, and traces**.
* Structured logs are easier to search and analyze than arbitrary text.
* Logs should contain useful context such as request IDs, operation names, service names, and error information.
* **Never blindly log passwords, tokens, API keys, or other sensitive data.**
* Centralized logging becomes essential once you have multiple instances or services.
* Log rotation and retention prevent logs from consuming unlimited resources.
* Metrics are particularly useful for dashboards, trends, and automated alerts.
* The **Four Golden Signals** are latency, traffic, errors, and saturation.
* Business metrics matter too; infrastructure can look healthy while the business is failing.
* Alerts should be actionable and carefully designed to avoid alert fatigue.
* A **trace** represents a request's journey through a distributed system.
* A **span** represents one operation inside that trace.
* Request IDs and correlation IDs help connect events across services.
* **OpenTelemetry** provides a vendor-neutral approach to collecting telemetry.
* High-cardinality metrics can become expensive and operationally difficult.
* SLI = measurement, SLO = target, SLA = formal commitment.
* An **error budget** represents the amount of unreliability permitted by an SLO.
* Good observability connects everything:

```text
Metrics
   ↓
Detect

Traces
   ↓
Locate

Logs
   ↓
Understand
```

> ### The interview-level mental model
>
> Don't say:
>
> **"I'll add logs and monitor the server."**
>
> Say:
>
> **"I'd build observability around structured logs, metrics, and distributed traces. I'd track the Four Golden Signals—latency, traffic, errors, and saturation—along with important database, dependency, and business metrics. Logs would include correlation and request IDs without exposing sensitive information. I'd define actionable alerts around SLOs, use traces to locate latency or failure across service boundaries, and use logs to investigate the detailed cause. For a distributed system, I'd use consistent telemetry collection and correlation so that an incident can move from alert → metric → trace → log → root cause."**
>
> **That's the production-engineering mindset you want for backend and system-design interviews.**
