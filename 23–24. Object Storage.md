# 23–24. Object Storage — Everything You Need to Know 📦

> Object storage is the storage model behind a huge part of modern cloud applications. It is designed for **large amounts of unstructured data** such as images, videos, documents, backups, datasets, logs, and user uploads.

# 1. Why Do We Need Object Storage?

A typical backend application needs to store more than database records.

For example, imagine a social media application:

```text
User
 ├── name
 ├── email
 └── profile_picture.jpg
```

The user information is structured data.

The image is not something you normally want to store directly inside a relational database.

Similarly:

```text
Images
Videos
PDFs
Audio
Documents
Backups
Logs
Datasets
Machine learning files
```

can become extremely large.

This is where **object storage** becomes useful.

---

# 2. What Is Object Storage? ⭐

Object storage stores data as **objects**.

An object generally consists of:

```text
Object
 ├── Data
 ├── Metadata
 └── Unique Identifier
```

For example:

```text
Object ID:
users/123/profile.jpg

Data:
<binary image data>

Metadata:
Content-Type: image/jpeg
Size: 2.4 MB
Created: ...
```

The important idea:

> **The file and the information describing that file are stored together as an object.**

Object storage is designed particularly for massive amounts of unstructured data. ([SegmentFault][2])

---

# 3. Object Storage vs File Storage vs Block Storage ⭐⭐⭐

This is an important interview question.

There are three major storage models:

```text
             STORAGE
                │
       ┌────────┼────────┐
       ↓        ↓        ↓
     File     Block    Object
```

---

## File Storage

Files are organized using a hierarchy:

```text
/users
   /123
      /profile.jpg
      /resume.pdf
```

You access the file using its path.

Mental model:

```text
File system
→ directories
→ files
→ paths
```

---

## Block Storage

Data is divided into blocks.

```text
Disk
 ├── Block 1
 ├── Block 2
 ├── Block 3
 ├── Block 4
 └── ...
```

Applications or operating systems interact with these blocks.

Block storage is commonly associated with high-performance disk-like workloads.

---

## Object Storage

Objects live in a largely flat namespace:

```text
Object A
Object B
Object C
Object D
```

Each object has an identifier/key.

```text
bucket/
   users/123/profile.jpg
   users/456/profile.jpg
   posts/789/image.png
```

The `/` in these keys often **looks like folders**, but object storage doesn't necessarily have a traditional directory hierarchy underneath.

---

# 4. The Core Difference

| Storage    | Mental Model        | Common Use                         |
| ---------- | ------------------- | ---------------------------------- |
| **File**   | Files + directories | Shared filesystems                 |
| **Block**  | Raw blocks/disks    | Databases, VM disks                |
| **Object** | Objects + metadata  | Images, videos, backups, documents |

Remember:

```text
File
→ "Where is the file in the directory?"

Block
→ "Which blocks contain my data?"

Object
→ "Give me the object identified by this key."
```

# 5. Why Object Storage Became Important

Modern applications generate enormous amounts of unstructured data:

```text

 ↓
Images + videos

Streaming
 ↓
Video + audio

Cloud applications
 ↓
Documents + backups
```

Traditional filesystem-based storage becomes increasingly difficult to manage at enormous scale.

Object storage is designed around:


# 6. Bucket

Object storage commonly organizes objects into **buckets**.

Think:

```text
Storage Account
      │
      ├── Bucket A
      │      ├── image1.jpg
      │      ├── image2.jpg
      │      └── video.mp4
      │
      └── Bucket B
             ├── backup.zip
             └── data.csv
```

A bucket is essentially a logical container for objects.

---

# 7. Object Key

Every object needs a way to identify it.

This is commonly called the **object key**.

Example:

```text
users/123/profile.jpg
```

Another:

```text
products/456/images/main.png
```

The key uniquely identifies the object within its bucket.

---

# 8. "Folders" in Object Storage

Suppose you see:

```text
users/
  123/
    profile.jpg
```

It looks like:

```text
users
 └── 123
      └── profile.jpg
```

But conceptually this can simply be:

```text
Key = users/123/profile.jpg
```

The `/` is part of the key.

This is an important distinction between traditional filesystems and object storage.

---

# 9. Object Metadata

An object isn't just raw data.

It can have metadata such as:

```text
Content-Type
Content-Length
Creation time
Modification information
Custom metadata
Cache directives
Encryption information
```

For example:

```text
profile.jpg

Metadata:
Content-Type: image/jpeg
Size: 1.8 MB
Cache-Control: ...
```

Metadata helps storage systems and applications understand how the object should be handled.

---

# 10. Object Storage Is Usually API-Based

One of the biggest differences from traditional filesystems is the access model.

Applications commonly communicate with object storage using APIs over HTTP.

Conceptually:

```text
Backend
   │
   │ HTTP
   ↓
Object Storage
```

Common operations resemble:

```text
PUT
GET
DELETE
HEAD
```

For example:

```text
PUT /bucket/users/123/profile.jpg
```

uploads an object.

```text
GET /bucket/users/123/profile.jpg
```

retrieves it.

```text
DELETE /bucket/users/123/profile.jpg
```

deletes it.

Object storage APIs commonly use HTTP/REST-style interfaces. ([SegmentFault][2])

# 11. Object Storage vs Database

A very common interview question:

> **Why not simply store files in PostgreSQL?**

You can store binary data in a database, but object storage is often a better fit for large files.

Consider:

```text
PostgreSQL
→ users
→ orders
→ payments
→ products

Object Storage
→ images
→ videos
→ PDFs
→ backups
```

The database stores **application state and structured relationships**.

Object storage stores **large binary objects**.

---

# 12. Why Not Store Everything in the Database?

Large binary files can cause problems such as:

```text
Database size increases
Backup size increases
Database I/O increases
Replication becomes heavier
Queries can become more expensive
Database resources are consumed by file storage
```

Instead:

```text
Database
 └── image_url / object_key

Object Storage
 └── actual image
```

This is a very common architecture.

---

# 15. Direct-to-Object-Storage Upload ⭐⭐⭐

Instead of:

```text
User
 ↓
Backend
 ↓
Object Storage
```

the backend can authorize the upload and let the client upload directly:

```text
                Backend
                  │
            Generate upload
              permission
                  │
                  ↓
Client ─────────────────→ Object Storage
```

This prevents your backend server from becoming a bottleneck for large files.

---

# 16. Presigned URLs

A common mechanism is a **presigned URL**.

The backend generates a temporary URL that allows a specific operation.

Conceptually:

```text
Client
  │
  │ "I want to upload image.jpg"
  ↓
Backend
  │
  │ Generate temporary upload URL
  ↓
Client
  │
  │ PUT image.jpg
  ↓
Object Storage
```

The client doesn't necessarily need your long-term storage credentials.

---

# 17. Why Presigned URLs Are Useful

They can provide:

```text
Temporary access
Limited permissions
Expiration
Direct upload/download
Reduced backend bandwidth
```

Example:

```text
Upload URL
valid for
10 minutes
```

After expiration:

```text
URL ❌
```

This is much safer than exposing permanent storage credentials to clients.

---

# 18. Upload Flow

A production-style upload might look like:

```text
1. User selects file
       ↓
2. Client asks backend for upload permission
       ↓
3. Backend authenticates user
       ↓
4. Backend validates intended file operation
       ↓
5. Backend generates temporary upload URL
       ↓
6. Client uploads directly to object storage
       ↓
7. Object storage confirms upload
       ↓
8. Backend stores object key/metadata
```


# 22. Security Model

A backend should never blindly trust:

```text
"Give me this object."
```

It should establish:

```text
Who is the user?
 ↓
Are they authenticated?
 ↓
Are they authorized?
 ↓
Do they own this resource?
 ↓
Can they access this object?
```

For example:

```text
User A
 ↓
GET /documents/B's-invoice.pdf
 ↓
Authorization ❌
```

The existence of an object key doesn't mean the user should be able to access it.

# 24. Don't Expose Storage Credentials

A dangerous design:

```text
Frontend
 ↓

 ↓
Object Storage
```

If those credentials leak:

```text

 ↓

 ↓
Read/write/delete
```

Instead:

```text

 ↓
Backend
 ↓
Temporary restricted permission
 ↓
Object Storage
```

or another appropriately scoped credential mechanism.

# 25. Large File Uploads

Large files create another problem.

Suppose:

```text
10 GB video
```

You don't want the system to depend on one enormous request.

Instead, large objects can be uploaded in **multiple parts/chunks**.

Conceptually:

```text
10 GB file
 │
 ├── Part 1
 ├── Part 2
 ├── Part 3
 ├── ...
 └── Part N
```

Then the storage service assembles them into the final object.

---

# 26. Multipart Upload ⭐

A typical multipart flow:

```text
1. Start upload
       ↓
2. Upload part 1
       ↓
3. Upload part 2
       ↓
4. Upload part 3
       ↓
5. ...
       ↓
6. Complete upload
```

Advantages:

```text
Large file support
Parallel uploads
Retry individual failed parts
Resume interrupted uploads
Better reliability
```

---

# 27. Why Multipart Upload Is Better

Imagine uploading:

```text
5 GB
```

and the connection fails at:

```text
4.9 GB
```

With a single upload:

```text
Restart 😭
```

With multipart:

```text
Part 1 ✓
Part 2 ✓
Part 3 ✓
Part 4 ✓
Part 5 ❌

Retry only Part 5
```

Much more efficient.

# 30. Durability vs Availability ⭐

These terms are often confused.

### Durability

> **Will my data still exist?**

### Availability

> **Can I access it right now?**

Example:

```text
Data exists safely
but temporary service outage
```

The data may be durable but temporarily unavailable.

A storage system needs to consider both.

# 31. Replication

Object storage systems typically distribute/replicate data across infrastructure to protect against failures.

Conceptually:

```text
                Object
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
    Storage A  Storage B  Storage C
```

If one storage component fails:

```text
A ❌
B ✓
C ✓
```

the system can potentially continue operating and/or recover the lost copy.

The exact mechanism varies by storage provider/system.

---

# 32. Why Replication Matters

Hardware fails.

```text
Disk ❌
Server ❌
Rack ❌
Network ❌
Data center component ❌
```

A production storage system must assume failures will happen.

Therefore:

> **Don't design storage around the assumption that hardware never fails.**

---

# 33. Erasure Coding

Another technique used in distributed storage is **erasure coding**.

Instead of simply making full copies:

```text
Original
 ↓
Copy A
Copy B
Copy C
```

data can be encoded into multiple pieces with redundancy.

Conceptually:

```text
Data
 ↓
Encoding
 ↓
D1 D2 D3 D4 P1 P2
```

If some pieces are lost, the original data can potentially be reconstructed.

The tradeoff is more computation and complexity.

---

# 34. Replication vs Erasure Coding

|                  | Replication       | Erasure Coding              |
| ---------------- | ----------------- | --------------------------- |
| Simplicity       | Higher            | Lower                       |
| Storage overhead | Higher            | Often lower                 |
| Recovery         | Straightforward   | Computationally heavier     |
| Common use       | Hot/critical data | Large-scale durable storage |

The exact tradeoffs depend on the implementation.

```text
      ↓         ↓         ↓
```

### Hot


# 45. Object Storage Is Not a Filesystem

This distinction is important.

Object storage generally does **not** behave like:

```text
open()
write()
seek()
rename()
```

against a traditional local filesystem.

Instead, it is typically accessed through object APIs.

Mental model:

```text
Filesystem
→ manipulate files

Object Storage
→ manipulate objects
```

---

# 46. Object Storage Is Not a Database

Similarly:

```text
Object Storage
≠
PostgreSQL
```

Object storage is excellent for:

```text
Large blobs
Files
Media
Backups
Archives
Datasets
```

It is not designed to replace relational querying.

Don't expect:

```text
SELECT users WHERE age > 25
```

from basic object storage.

# 49. Don't Trust User-Supplied Filenames

Suppose a user uploads:

```text

```

or:

```text

```

You shouldn't blindly use user-controlled filenames as storage identifiers.

Better:

```text

+

```

```text

```

# 67. RPO and RTO

Two useful disaster-recovery concepts:

### RPO — Recovery Point Objective

> How much data can we afford to lose?

Example:

```text
RPO = 1 hour
```

Means the system should be designed so that losing up to roughly an hour of recent data is within the defined recovery tolerance.

### RTO — Recovery Time Objective

> How quickly must the system recover?

Example:

```text
RTO = 30 minutes
```

means the service should be recoverable within that target.

# 🧠 Interview Mental Models

### What is object storage?

> A storage model where data is stored as independent objects containing the data itself, metadata, and a unique identifier, typically accessed through APIs.

### Object vs file storage?

```text
File
→ hierarchical filesystem

Object
→ object + metadata + key
```

### Object vs block storage?

```text
Block
→ raw storage blocks

Object
→ complete objects accessed through an API
```

### Why use object storage instead of PostgreSQL for images?

> Object storage is designed to handle large amounts of binary/unstructured data at scale, while the database can focus on structured application state and relationships.

### What should the database store?

```text
Object key
Owner
Filename
Content type
Size
Business metadata
Permissions
```

### What should object storage store?

```text
Actual file/blob
```

### Why use presigned URLs?

> To give a client temporary, scoped permission to upload or download an object without exposing long-lived storage credentials and without forcing large file transfers through the backend.

### Why multipart upload?

> To upload large files in parts, allowing retries, resumption, and potentially parallel uploads without restarting the entire file.

### Why object storage helps horizontal scaling?

> Because uploaded files don't have to live on individual application servers. Multiple stateless application instances can access shared object storage.

# 🔥 Core Takeaways

* **Object storage stores data as objects rather than traditional files or raw blocks.**
* An object consists conceptually of **data + metadata + unique identifier/key**.
* Object storage is particularly suited for **large-scale unstructured data**.
* Images, videos, PDFs, backups, archives and datasets are common use cases.
* A **bucket** is a logical container for objects.
* An object key identifies an object within its storage namespace.
* Paths such as `users/123/profile.jpg` are commonly object keys rather than traditional directories.
* Object storage is accessed primarily through APIs rather than filesystem operations.
* **File storage, block storage and object storage solve different problems.**
* Databases should generally store application metadata and object references rather than unnecessarily storing huge binary files.
* A common architecture is:

  ```text
  PostgreSQL → metadata
  Object Storage → actual file
  ```
* **Presigned URLs** allow temporary, scoped access to objects.
* Direct client-to-object-storage uploads prevent large file transfers from overwhelming backend servers.
* Multipart uploads split large files into independently uploaded parts.
* Multipart uploads allow failed parts to be retried without restarting the entire upload.
* Streaming avoids loading huge files completely into memory.
* Object storage can help application servers remain **stateless**, making horizontal scaling easier.
* Private objects require proper authentication and authorization.
* Never expose long-lived storage credentials to untrusted clients.
* Don't blindly trust client-supplied filenames, MIME types, or file sizes.
* Object storage can integrate with queues and background workers for asynchronous file processing.
* CDN + object storage is a common architecture for globally serving frequently accessed static content.
* Versioning can protect against accidental overwrites/deletions.
* Lifecycle policies can move old objects into cheaper storage tiers or delete them automatically.
* **Durability** asks whether data survives; **availability** asks whether it can be accessed now.
* Distributed storage can use replication and/or erasure coding to tolerate failures.
* Large-file systems benefit from range requests and resumable uploads.
* Object storage is not a replacement for PostgreSQL or a general-purpose filesystem.
* The core architectural pattern to remember is:

```text
        APPLICATION STATE
              ↓
          PostgreSQL
              │
              │ object key
              ↓
        OBJECT STORAGE
              │
              ↓
          CDN / Client
```

> ### The interview-level answer
>
> **"For large unstructured data like images, videos and documents, I'd use object storage rather than putting the binary data directly into the relational database. The database would store the object's key, owner, metadata and application-level permissions, while the actual file would live in object storage. For scalable uploads, I'd authenticate and authorize the request in the backend, generate a short-lived presigned upload URL, and let the client upload directly to object storage. For large files I'd use multipart/resumable uploads, and for downloads I'd use streaming or range requests where appropriate. Object events could trigger background workers for processing such as thumbnails or virus scanning. For delivery, a CDN can sit in front of the object store. This keeps the application servers stateless and avoids making them a bottleneck for large file transfers."**

That's the **core object-storage architecture** you should be able to explain in a backend interview.
