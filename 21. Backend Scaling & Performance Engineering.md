# 21. Backend Scaling & Performance Engineering 📈

> **Scaling is not simply "adding more servers." Performance engineering is about understanding where time and resources are being spent, identifying bottlenecks, and designing the system so it can handle increasing load without degrading unpredictably.**
>
> This chapter is split into **Part 1** and **Part 2**, so I'm keeping them together as one study chapter while separating the concepts where useful.
>
> **Part 1:** Backend Scaling and Performance Engineering
> **Part 2:** Backend Scaling and Performance Engineering

---

# 1. What Does Performance Mean?

At a basic level, performance is about:

```text
How quickly
+
How efficiently
+
How reliably
the system handles work.
```

For a backend, this could mean:

```text
Request
   ↓
API
   ↓
Business Logic
   ↓
Database
   ↓
Response
```

How quickly can the entire operation complete?

But speed isn't the only concern.

We also care about:

```text
Throughput
Resource utilization
Scalability
Reliability
Cost
```

---

# 2. Latency vs Throughput ⭐

Two fundamental performance concepts.

### Latency

> How long does one operation take?

Example:

```text
GET /users
→ 120 ms
```

### Throughput

> How much work can the system handle per unit of time?

Example:

```text
5,000 requests / second
```

Think:

```text
Latency
→ Time per request

Throughput
→ Requests per second
```

A system can have:

```text
Low latency
+
Low throughput
```

or:

```text
High throughput
+
High latency
```

They are related, but not the same.

---

# 3. Response Time

A user's perceived response time may contain multiple pieces:

```text
Client
 ↓
Network
 ↓
Load Balancer
 ↓
Application
 ↓
Database
 ↓
Application
 ↓
Network
 ↓
Client
```

So:

```text
Total response time
=
network
+
queueing
+
processing
+
database
+
external services
+ ...
```

Optimizing only application code may not solve the actual bottleneck.

---

# 4. P50, P95 and P99 Latency ⭐

Average latency can be misleading.

Suppose:

```text
99 requests → 100 ms
1 request   → 10 seconds
```

Average latency may not look terrible.

But one user had a terrible experience.

Percentiles help.

### P50

50% of requests are faster than this value.

### P95

95% are faster.

5% are slower.

### P99

99% are faster.

1% are slower.

Example:

```text
p50 = 100ms
p95 = 300ms
p99 = 900ms
```

The tail matters enormously in production systems.

---

# 5. Why Tail Latency Matters

Imagine one API request calls:

```text
Service A
 ↓
Service B
 ↓
Service C
 ↓
Service D
```

If every dependency has a small probability of being slow, the overall request has a higher probability of experiencing slow behavior.

This is why distributed systems often pay special attention to:

```text
p95
p99
p99.9
```

rather than only average latency.

---

# 6. Resource Utilization

A backend consumes resources:

```text
CPU
Memory
Disk
Network
Database connections
Threads
File descriptors
```

Performance engineering asks:

> **Which resource is limiting the system?**

For example:

```text
CPU → 95%
Memory → 40%
DB connections → 30%
```

The CPU may be the bottleneck.

Another situation:

```text
CPU → 30%
Memory → 40%
DB connections → 100%
```

Now the database connection pool may be the bottleneck.

---

# 7. Bottleneck

A bottleneck is the part of the system limiting overall performance.

Example:

```text
API
 ↓
Service
 ↓
Database
```

If:

```text
API processing → 20ms
Service logic → 30ms
Database → 900ms
```

then optimizing:

```text
20ms → 10ms
```

barely matters.

The database dominates the request.

---

# 8. Don't Optimize Before Measuring ⭐

A classic engineering principle:

> **Measure first. Optimize second.**

Bad:

```text
"I think Redis will make this faster."
```

Better:

```text
Measure
 ↓
Find bottleneck
 ↓
Understand cause
 ↓
Optimize
 ↓
Measure again
```

Otherwise you may optimize the wrong component.

---

# 9. Profiling

Profiling helps identify where application resources are being spent.

You might discover:

```text
Function A → 5%
Function B → 10%
Function C → 70%
Function D → 15%
```

Now you know where optimization could have meaningful impact.

Profiling can investigate:

```text
CPU
Memory
I/O
Database queries
Lock contention
```

---

# 10. Scaling

Scaling means increasing the system's ability to handle additional workload.

There are two fundamental approaches:

```text
Vertical Scaling
Horizontal Scaling
```

---

# 11. Vertical Scaling

Vertical scaling means:

> **Make the machine bigger.**

For example:

```text
2 CPU
4 GB RAM
```

becomes:

```text
8 CPU
32 GB RAM
```

Conceptually:

```text
        BIGGER MACHINE
              ↑
        Vertical Scaling
```

---

# 12. Advantages of Vertical Scaling

It's relatively simple.

You may not need to change the application architecture significantly.

For example:

```text
Server
 ↓
Upgrade instance
 ↓
More CPU/RAM
```

This can be useful for:

```text
Small systems
Databases
Early-stage applications
Workloads difficult to distribute
```

---

# 13. Limitations of Vertical Scaling

A machine has physical/cloud limits.

You eventually reach:

```text
Maximum CPU
Maximum RAM
Maximum network capacity
```

There is also a reliability problem:

```text
One huge server
      ↓
Single point of failure
```

If it goes down, the entire application may go down.

---

# 14. Horizontal Scaling ⭐

Horizontal scaling means:

> **Add more machines/instances.**

Instead of:

```text
1 server
```

you have:

```text
Server A
Server B
Server C
Server D
```

A load balancer distributes traffic:

```text
                Load Balancer
                /     |     \
               ↓      ↓      ↓
             App A  App B  App C
```

---

# 15. Why Horizontal Scaling Is Powerful

You can increase capacity:

```text
2 instances
 ↓
4 instances
 ↓
8 instances
 ↓
20 instances
```

You can also improve availability:

```text
Server A ❌
Server B ✅
Server C ✅
```

The application can potentially continue serving traffic.

---

# 16. Stateless Applications ⭐

Horizontal scaling becomes much easier when application servers are stateless.

Suppose:

```text
Request 1 → Server A
Request 2 → Server B
```

If Server B needs state that exists only in Server A's memory:

```text
Server A
└── User session
```

then Server B can't handle the second request correctly.

Instead, shared state can live in:

```text
Redis
Database
External storage
```

Conceptually:

```text
App A ─┐
App B ─┼──→ Shared State
App C ─┘
```

---

# 17. Sticky Sessions

One way to handle stateful servers is sticky sessions.

The load balancer tries to send the same user to the same instance:

```text
User A
 ↓
Server A
 ↓
Server A
 ↓
Server A
```

But this creates problems:

```text
Uneven load
Failover complexity
Reduced flexibility
```

Stateless architectures are generally easier to scale.

---

# 18. Load Balancing

A load balancer distributes traffic among backend instances.

```text
                     Clients
                        │
                        ↓
                 ┌─────────────┐
                 │Load Balancer│
                 └──────┬──────┘
                  ┌─────┼─────┐
                  ↓     ↓     ↓
                 A      B      C
```

Its goals can include:

```text
Distribute traffic
Improve availability
Enable horizontal scaling
Remove unhealthy instances
```

---

# 19. Load Balancing Strategies

Common approaches include:

### Round Robin

```text
Request 1 → A
Request 2 → B
Request 3 → C
Request 4 → A
```

Simple and useful when instances are similar.

---

### Least Connections

Send new requests toward the instance with fewer active connections.

```text
A → 100 connections
B → 30 connections
C → 50 connections

New request → B
```

---

### Weighted Routing

Give different instances different weights.

```text
A → 50%
B → 30%
C → 20%
```

Useful when machines have different capacities or for controlled rollouts.

---

# 20. Health Checks

The load balancer needs to know:

> **Which instances are healthy?**

For example:

```text
GET /health
```

If:

```text
Server A → healthy
Server B → unhealthy
Server C → healthy
```

the load balancer can stop routing traffic to B.

This connects directly to your previous **Graceful Shutdown** chapter.

---

# 21. Auto Scaling

Instead of manually deciding:

```text
"Add another server."
```

an autoscaling system can respond to demand.

Conceptually:

```text
Traffic increases
      ↓
CPU / request rate increases
      ↓
Threshold reached
      ↓
Add instances
```

And when demand falls:

```text
Traffic decreases
      ↓
Instances become unnecessary
      ↓
Scale down
```

---

# 22. Scaling Has a Cost

Scaling isn't automatically good.

Adding instances means:

```text
More infrastructure
More network traffic
More operational complexity
More database connections
More monitoring
More cost
```

You should scale based on an actual bottleneck or capacity requirement.

---

# 23. Database as a Bottleneck ⭐

Your application might scale from:

```text
2 API servers
```

to:

```text
20 API servers
```

but all 20 connect to:

```text
One PostgreSQL database
```

Now:

```text
20 servers
    ↓
Thousands of requests
    ↓
One database
    ↓
🔥 Bottleneck
```

Scaling the API layer doesn't automatically scale the database.

---

# 24. Connection Pooling

Opening a database connection for every request is expensive.

Instead:

```text
Application
     ↓
Connection Pool
 ┌───┼───┬───┐
 ↓   ↓   ↓   ↓
 DB connections
```

Connections can be reused.

This improves:

```text
Performance
Resource utilization
Connection establishment overhead
```

---

# 25. Connection Pool Size

Bigger isn't always better.

Suppose:

```text
10 application servers
```

and each has:

```text
100 DB connections
```

Potentially:

```text
10 × 100 = 1,000 connections
```

Your PostgreSQL database may not handle that efficiently.

So:

> **Database connection pools must be sized with the entire system in mind.**

---

# 26. N+1 Query Problem 🚨

Suppose you fetch:

```text
100 users
```

Then for every user:

```text
SELECT orders WHERE user_id = ?
```

You might execute:

```text
1 query → users
+
100 queries → orders
=
101 queries
```

That's the:

> **N+1 query problem**

---

# 27. Better Querying

Instead of:

```text
1 + N queries
```

you may use:

```text
JOIN
```

or a batched query.

Conceptually:

```text
Users
  +
Orders
  ↓
One optimized database operation
```

The exact strategy depends on the data access pattern.

---

# 28. Database Indexing ⭐

An index can dramatically speed up reads for suitable query patterns.

Suppose:

```sql id="wz3dy0"
SELECT *
FROM users
WHERE email = ?;
```

Without an appropriate index, the database may need to inspect many rows.

With:

```text id="i1gtam"
INDEX(email)
```

the database can find matching rows much more efficiently.

But indexes have costs.

---

# 29. Index Tradeoffs

Indexes improve some reads but consume:

```text id="s4x4z9"
Storage
Memory
Write time
Maintenance overhead
```

So:

> **Don't index every column.**

Index based on actual query patterns.

---

# 30. Query Optimization

A slow query might be caused by:

```text id="6e9ovh"
Missing index
Poor join
Large scan
Unnecessary columns
Bad filtering
Inefficient query plan
Too much returned data
```

Database tools such as query planners/explain facilities help understand what the database is actually doing.

---

# 31. Avoid `SELECT *` When Appropriate

Instead of:

```sql id="q2d9zj"
SELECT *
FROM users;
```

if you only need:

```text id="0e8k23"
id
name
email
```

request only those fields.

This can reduce:

```text id="u3cbr0"
Database work
Network transfer
Serialization
Memory usage
```

especially for large rows.

---

# 32. Pagination

Suppose an API has:

```text
1 million records
```

and the client asks:

```text
GET /users
```

Returning everything is a terrible idea.

Instead:

```text id="8u2m13"
GET /users?page=1&limit=20
```

or cursor-based pagination.

---

# 33. Offset Pagination

Example:

```text id="w3k4e9"
LIMIT 20
OFFSET 1000
```

Simple and useful for many applications.

But large offsets can become expensive because the database may need to skip many rows.

---

# 34. Cursor Pagination ⭐

Instead of saying:

```text id="t72f1x"
"Give me rows 1001–1020"
```

you say:

```text id="n8zqsi"
"Give me the next 20 rows after this cursor."
```

Conceptually:

```text id="0r3xkh"
Page 1
 ↓
cursor=ABC
 ↓
Page 2
 ↓
cursor=XYZ
 ↓
Page 3
```

This can perform better for large, continuously changing datasets when designed appropriately.

---

# 35. Caching

You already studied caching in an earlier chapter.

From a performance perspective:

```text id="6i3l9h"
Without cache:

Request
 ↓
Database
 ↓
Response
```

With cache:

```text id="w9b8qy"
Request
 ↓
Cache
 ↓
Hit → Response
```

This can significantly reduce database load and latency.

---

# 36. Cache Hit Ratio

A useful metric:

```text id="4w73cq"
Cache hits
──────────────
Total requests
```

Example:

```text id="2uqj4s"
900 cache hits
100 cache misses

Hit ratio = 90%
```

A higher hit ratio can mean fewer requests reach the underlying database or service, but a high hit ratio isn't automatically the goal if the cache is storing the wrong things.

---

# 37. Cache Invalidation

Caching creates a fundamental problem:

> **What happens when the underlying data changes?**

Suppose:

```text id="8t6q6c"
Database
price = ₹100

Cache
price = ₹100
```

Then:

```text id="3e1r8k"
Database
price = ₹120
```

but:

```text id="q4c1sr"
Cache
price = ₹100
```

Now you have stale data.

This is why cache invalidation is one of the difficult parts of system design.

---

# 38. Asynchronous Processing

Not every operation needs to happen inside the request.

Suppose:

```text id="3k8v34"
User uploads image
```

and processing takes:

```text id="c0jzfj"
10 seconds
```

Instead of:

```text id="ypf83d"
Request
 ↓
Process image
 ↓
Wait 10 seconds
 ↓
Response
```

you can:

```text id="l7x4w2"
Request
 ↓
Queue job
 ↓
Immediate response
```

Then:

```text id="uwb9b7"
Worker
 ↓
Process image
```

This connects directly to your **Task Queues and Background Jobs** chapter.

---

# 39. Batch Processing

Instead of:

```text id="2tw6jx"
1,000 individual DB writes
```

you may batch them:

```text id="r8z9kx"
100 × 10-row batches
```

or use bulk operations.

Benefits can include:

```text id="f0w2ls"
Fewer round trips
Lower overhead
Better throughput
```

But very large batches can increase memory usage or lock duration.

---

# 40. Network Overhead

A backend isn't only limited by CPU.

Network communication has costs:

```text id="k7o1ue"
Serialization
Transfer
Latency
Bandwidth
TLS overhead
```

Sending:

```text id="q0tq6m"
10 MB
```

when you only need:

```text id="m17r4o"
100 KB
```

is wasteful.

---

# 41. Reduce Payload Size

Ways to reduce network overhead:

```text id="my6h5k"
Return only necessary fields
Pagination
Compression
Efficient serialization
Avoid redundant requests
```

This connects to your earlier **Serialization and Deserialization** chapter.

---

# 42. Compression

For suitable responses:

```text id="k8c2wy"
Large JSON
   ↓
Compression
   ↓
Smaller payload
   ↓
Network
```

This can reduce bandwidth consumption and transfer time.

But compression itself consumes CPU.

So again:

> **Every optimization has a tradeoff.**

---

# 43. Concurrency

Concurrency means dealing with multiple tasks that are in progress during overlapping periods.

For example:

```text id="j5i3uk"
Request A → waiting for DB
Request B → waiting for API
Request C → processing
```

The system can make progress on other work while one operation is waiting.

This is especially useful for:

```text id="g2w8ts"
I/O-bound workloads
```

---

# 44. Parallelism

Parallelism means actually executing multiple operations simultaneously, typically across multiple CPU cores.

Example:

```text id="z65lxx"
CPU Core 1 → Task A
CPU Core 2 → Task B
CPU Core 3 → Task C
```

Useful for:

```text id="3s8m5r"
CPU-intensive workloads
```

---

# 45. Concurrency vs Parallelism

| Concept         | Idea                                  | Typical benefit |
| --------------- | ------------------------------------- | --------------- |
| **Concurrency** | Multiple tasks make progress          | I/O-bound work  |
| **Parallelism** | Multiple tasks execute simultaneously | CPU-bound work  |

Mental model:

```text id="j3t0sl"
Concurrency
→ Managing many things

Parallelism
→ Doing many things simultaneously
```

---

# 46. Memory Leaks

A memory leak happens when memory that is no longer needed remains referenced and therefore cannot be reclaimed.

Conceptually:

```text id="0a2wby"
Request
 ↓
Allocate memory
 ↓
Request finishes
 ↓
Reference accidentally remains
 ↓
Memory cannot be released
```

Over time:

```text id="6yq8t2"
Memory
 ↓
500 MB
 ↓
800 MB
 ↓
1.2 GB
 ↓
2 GB
 ↓
💥
```

---

# 47. Common Sources of Resource Leaks

Not just memory.

You can leak:

```text id="xj2f1c"
Memory
Database connections
File handles
Sockets
Timers
Threads
```

Every acquired resource needs an appropriate lifecycle.

This connects directly to **Graceful Shutdown**.

---

# 48. Garbage Collection Doesn't Fix Everything

A garbage-collected language can automatically reclaim unreachable memory.

But if your program keeps a reference:

```text id="5l4e2x"
Global cache
 ↓
Object
```

the garbage collector sees:

```text id="q0b1a8"
Object is still reachable
```

and won't free it.

So:

> **Garbage collection does not prevent logical memory leaks.**

---

# 49. Backpressure ⭐

Suppose:

```text id="7a7hyo"
Producer
→ 10,000 jobs/sec
```

but:

```text id="n6v52n"
Consumer
→ 1,000 jobs/sec
```

The queue grows:

```text id="f1w8ts"
1,000
10,000
100,000
1,000,000
```

Eventually something breaks.

The system needs **backpressure**.

Conceptually:

```text id="r2d2w3"
Producer
    ↓
Can consumer keep up?
    ↓
NO
    ↓
Slow producer / limit queue / reject work
```

---

# 50. Why Backpressure Matters

Without backpressure:

```text id="f5j8l3"
Incoming load
      ↓
More work
      ↓
More queue
      ↓
More memory
      ↓
Resource exhaustion
      ↓
System failure
```

With backpressure:

```text id="2y9xq1"
Incoming load
      ↓
Capacity reached
      ↓
Slow / reject / shed load
      ↓
Protect system
```

This is a major scalability principle.

---

# 51. Load Shedding

Sometimes the system simply cannot handle all incoming work.

Instead of allowing everything to fail slowly:

```text id="yq20v1"
100,000 requests
      ↓
Everything becomes slow
      ↓
Everything times out
```

you can deliberately reject some work:

```text id="j35f54"
100,000 requests
      ↓
System capacity = 20,000
      ↓
Accept 20,000
Reject/defer remaining
```

This protects the system from total collapse.

---

# 52. Graceful Degradation

If a non-critical dependency fails:

```text id="t7p4bz"
Recommendation Service ❌
```

the entire application doesn't necessarily need to fail.

Instead:

```text id="o6q8c4"
Main product
   ↓
Continue working
   ↓
Recommendations unavailable
```

This is:

> **Graceful degradation**

It connects directly to your previous chapters on **Error Handling** and **Graceful Shutdown**.

---

# 53. Timeouts

Every external dependency can potentially become slow.

For example:

```text id="a7n3o1"
Backend
 ↓
Payment API
 ↓
No response
```

Without a timeout:

```text id="5w2p9r"
Request waits...
```

With a timeout:

```text id="p7t8k4"
Request
 ↓
Payment API
 ↓
Timeout after 2 sec
 ↓
Handle failure
```

Timeouts prevent one slow dependency from consuming resources indefinitely.

---

# 54. Retries Can Make Performance Worse

A common mistake:

```text id="s3f5c9"
Request fails
 ↓
Retry
 ↓
Fails
 ↓
Retry
 ↓
Fails
 ↓
Retry
```

If thousands of requests do this simultaneously, the dependency can become even more overloaded.

This can create a:

> **Retry storm**

---

# 55. Exponential Backoff

Instead of retrying immediately:

```text id="5ly2y7"
Retry 1 → 100ms
Retry 2 → 200ms
Retry 3 → 400ms
Retry 4 → 800ms
```

The delay increases.

Usually you'd also add:

```text id="e6r7i1"
Jitter
```

so many clients don't retry at exactly the same moment.

---

# 56. Circuit Breaker

Suppose an external service is failing repeatedly.

Without protection:

```text id="3g1u5y"
Request
 ↓
External API ❌
 ↓
Retry
 ↓
External API ❌
 ↓
Retry
```

A circuit breaker can temporarily stop sending requests:

```text id="r5v8up"
Healthy
   ↓
Failures increase
   ↓
Circuit OPEN
   ↓
Stop calling dependency
   ↓
Wait
   ↓
Test recovery
   ↓
Circuit CLOSED
```

This prevents your application from continuously hammering a failing dependency.

---

# 57. Performance and Reliability Are Connected

Consider:

```text id="4x9f9y"
Dependency becomes slow
      ↓
Requests wait
      ↓
Threads/connections consumed
      ↓
Queue grows
      ↓
Memory grows
      ↓
More timeouts
      ↓
Retries
      ↓
More load
      ↓
System collapses
```

Performance problems can therefore become reliability problems.

This is why performance engineering isn't just about making responses faster.

---

# 58. Capacity Planning

You should know approximately:

```text id="c2e2ik"
How much traffic can one instance handle?
```

For example:

```text id="3rv7m1"
1 server
→ 2,000 req/sec
```

If traffic reaches:

```text id="c1d3sk"
8,000 req/sec
```

you may need approximately:

```text id="v4p8so"
4 instances
```

assuming the workload scales reasonably and the database/dependencies aren't bottlenecks.

Real systems need safety margins and testing rather than relying on simple arithmetic alone.

```text id="9l9rj5"
 ↓

 ↓
1,000
 ↓

 ↓
```

# 60. Stress Testing

Load testing asks:

> **Can the system handle expected traffic?**

Stress testing pushes beyond expected capacity:

```text id="c4s5du"
Expected → 5k req/sec

Stress → 10k
        20k
        50k
```

You want to understand:

```text id="7p5n3c"
Where does it break?
How does it fail?
Does it recover?
```

---

# 61. Performance Testing Loop

A useful engineering loop:

```text id="h8x2ck"
Define target
     ↓
Measure baseline
     ↓
Generate load
     ↓
Find bottleneck
     ↓
Change system
     ↓
Measure again
     ↓
Compare
```

Never assume an optimization worked.

Measure it.

---

# 62. Premature Optimization

Bad:

```text id="5m7e4r"
"I'll optimize everything before I know whether it's slow."
```

Better:

```text id="slw1v0"
Make it correct
 ↓
Make it maintainable
 ↓
Measure
 ↓
Optimize bottlenecks
```

A theoretically faster implementation isn't useful if it makes the system much harder to maintain without solving a real problem.

---

# 63. Performance vs Maintainability

Suppose optimization makes:

```text id="b9e2s3"
Code
→ 10% faster
```

but:

```text id="a8o0p7"
Complexity
→ 500% higher
```

It may not be worth it.

Performance engineering is about **tradeoffs**.

Ask:

```text id="xw3w8v"
How much faster?
At what cost?
Does it matter to users?
Does it increase operational complexity?
```

# 64. Scaling the Application Layer

A common scalable architecture:

```text id="1d6d7q"
                  USERS
                    │
                    ↓
              Load Balancer
```

> **Don't shard simply because your application has multiple servers.**

# 🧠 Interview Mental Models

### What is performance engineering?

> The process of measuring system behavior, identifying bottlenecks, and improving latency, throughput, resource efficiency, and scalability based on evidence.

---

### Latency vs throughput?

```text id="q9h6r4"
Latency
→ Time for one operation

Throughput
→ Amount of work completed per unit time
```

---

### Vertical vs horizontal scaling?

```text id="1w3xq6"
Vertical
→ Bigger machine

Horizontal
→ More machines
```

---

### Why are stateless services easier to scale?

> Because any instance can handle a request without depending on state stored only in another instance's memory.

---

### What is a bottleneck?

> The component or resource that limits the overall performance or capacity of the system.

---

### Why monitor p95/p99 instead of average latency?

> Because averages can hide slow requests. Percentiles expose tail latency and provide a better picture of user experience.

---

### What is the N+1 problem?

> A pattern where fetching N entities results in an additional query for each entity, producing 1 + N database queries instead of a more efficient batched or joined approach.

---

### Why aren't more database connections always better?

> Because database connections consume resources, and excessive connections can overwhelm the database rather than increase throughput.

---

### What is backpressure?

> A mechanism that prevents producers from overwhelming consumers by slowing, limiting, buffering, or rejecting work when downstream capacity is insufficient.

---

### What is load shedding?

> Deliberately rejecting or dropping lower-priority work when the system is overloaded so that critical functionality remains available.

---

### What is graceful degradation?

> Maintaining core functionality when non-critical components or dependencies fail, rather than allowing the entire system to fail.

---

### Why can retries make an outage worse?

> Because large numbers of clients retrying simultaneously can increase load on an already failing dependency, creating a retry storm.

# 🔥 Core Takeaways

* **Performance engineering starts with measurement, not assumptions.**
* Latency is the time taken by an operation; throughput is the amount of work completed per unit time.
* Average latency can hide slow requests, so **p95 and p99** are important production metrics.
* A **bottleneck** is the component limiting overall system performance.
* Profiling and observability help identify where resources are actually being consumed.
* **Vertical scaling** means making a machine larger.
* **Horizontal scaling** means adding more machines.
* Horizontal scaling improves both capacity and potentially availability, but requires architecture that supports distributing work.
* **Stateless application servers** are generally easier to scale horizontally.
* Load balancers distribute traffic and can remove unhealthy instances.
* Autoscaling can dynamically adjust capacity based on demand.
* Scaling the API layer doesn't automatically solve a **database bottleneck**.
* Connection pooling avoids repeatedly establishing database connections, but pools must be sized carefully.
* Too many database connections can actually reduce performance.
* N+1 queries can cause huge numbers of unnecessary database operations.
* Indexes can dramatically improve suitable reads but add storage and write-maintenance costs.
* Pagination prevents APIs from returning enormous datasets.
* Cursor pagination can be preferable for large/changing datasets in appropriate cases.
* Caching can reduce latency and database load, but introduces stale-data and invalidation problems.
* Network payload size matters; unnecessary data wastes bandwidth, serialization time, and memory.
* Compression reduces transfer size at the cost of CPU.
* **Concurrency** is especially useful for overlapping I/O work; **parallelism** is useful for CPU-intensive work.
* Memory, database connections, sockets, file descriptors, and other resources can all leak.
* **Backpressure** prevents a fast producer from overwhelming a slower consumer.
* Load shedding protects critical functionality when demand exceeds capacity.
* Graceful degradation allows non-critical features to fail without taking down the entire system.
* Timeouts prevent slow dependencies from consuming resources indefinitely.
* Retries can amplify outages; use limited retries, exponential backoff, and jitter where appropriate.
* Circuit breakers can prevent repeatedly calling a failing dependency.
* Queues can absorb traffic bursts but **do not create infinite capacity**.
* Load testing measures behavior under expected traffic; stress testing explores behavior beyond expected capacity.
* Capacity planning helps determine how much workload your infrastructure can sustain.
* Better algorithms and queries can be more valuable than adding hardware.
* **Premature optimization is dangerous**: optimize measured bottlenecks rather than imagined ones.
* Performance, scalability, reliability, and cost are interconnected.
