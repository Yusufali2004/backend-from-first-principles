# 11. Complete REST API Design 🌐

> **A REST API is not just a collection of endpoints. It is an interface that other software will depend on.**
>
> Good API design makes the behavior predictable. A developer should be able to look at one endpoint and reasonably predict how the rest of the API works.

This chapter is **2+ hours** and is specifically about designing the API interface *before* writing the implementation. The video covers REST principles, resources, routes, HTTP methods, idempotency, payloads, responses, pagination, filtering, sorting, defaults, and documentation. ([Transcribe][1])

---

# 1. What Are We Actually Designing?

When building an API, there are two separate problems:

```text
API Design
    ↓
"What should the interface look like?"

API Implementation
    ↓
"How do I make it work?"
```

The video strongly emphasizes doing the **design first**.

For example, before writing:

```javascript
app.post("/users", ...)
```

you should first decide:

```text
POST /users

Request:
{
    "name": "...",
    "email": "..."
}

Response:
201 Created
{
    ...
}
```

Only after the interface makes sense should you implement it.

---

# 2. REST Is an Architectural Style

REST stands for:

> **Representational State Transfer**

REST is **not**:

* A programming language
* A framework
* A database
* JSON
* HTTP itself

It is an architectural style for designing networked applications.

The video focuses specifically on **REST APIs**, even though other API styles exist:

```text
API Styles
│
├── REST
├── RPC
├── GraphQL
└── Others
```

This chapter focuses on REST.

---

# 3. What Does "Representational" Mean?

A resource exists on the server.

For example:

```text
User
Project
Task
Organization
```

The client doesn't necessarily receive the server's internal representation.

Instead, the server provides a **representation** of the resource.

For example:

```json
{
  "id": 42,
  "name": "Yusuf"
}
```

JSON is the most common representation.

Other possible representations include:

```text
JSON
XML
HTML
```

The important distinction:

```text
Resource
   ↓
Representation
```

The resource exists conceptually; JSON is one way of representing it.

---

# 4. Start With Resources

One of the most important REST design rules:

> **Identify the resources in your system.**

Resources are generally **nouns**, not actions.

Imagine you're building a project-management application.

From the product/UI requirements you might identify:

```text
Organization
Project
Task
User
Tag
```

These become your API resources.

Think:

```text
"What things exist in my system?"
```

rather than:

```text
"What actions do I need endpoints for?"
```

---

# 5. Nouns, Not Verbs

A common bad API:

```text
/createUser
/getUser
/updateUser
/deleteUser
```

This describes actions in URLs.

A REST-style API instead uses the resource:

```text
/users
```

and uses HTTP methods to describe the operation.

```text
POST   /users
GET    /users
GET    /users/123
PATCH  /users/123
DELETE /users/123
```

The **HTTP method provides the action**.

The URL identifies the resource.

---

# 6. Plural Resource Names

A consistent convention is to use plural resource names:

```text
/users
/projects
/tasks
/organizations
```

rather than mixing:

```text
/user
/projects
/task
```

Why?

Because:

```text
/users
```

naturally represents a collection.

And:

```text
/users/123
```

represents one member of that collection.

```text
/users
   ↓
Collection

/users/123
   ↓
Individual resource
```

Consistency matters more than inventing clever naming schemes.

---

# 7. Collections and Individual Resources

Consider:

```text
/projects
```

This represents the collection.

```text
/projects/123
```

represents one project.

So:

```text
GET /projects
```

means:

> Give me the collection of projects.

While:

```text
GET /projects/123
```

means:

> Give me project 123.

This pattern can be reused everywhere.

```text
/users
/users/123

/tasks
/tasks/456

/organizations
/organizations/10
```

---

# 8. Nested Resources

Suppose projects belong to organizations.

You can represent that relationship:

```text
/organizations/10/projects
```

Meaning:

> Projects belonging to organization 10.

And:

```text
/organizations/10/projects/42
```

Meaning:

> Project 42 inside organization 10.

This makes resource relationships visible through the URL.

But don't create unnecessarily deep URLs.

Avoid things like:

```text
/organizations/1/projects/2/tasks/3/comments/4/users/5
```

if a simpler resource relationship works.

---

# 9. HTTP Methods

REST heavily relies on HTTP semantics.

The common methods are:

```text
GET
POST
PUT
PATCH
DELETE
```

A useful mapping:

| Method | Typical purpose  |
| ------ | ---------------- |
| GET    | Read             |
| POST   | Create           |
| PUT    | Replace          |
| PATCH  | Partially update |
| DELETE | Delete           |

---

# 10. GET

Use GET to retrieve resources.

```http
GET /users
```

Get users.

```http
GET /users/123
```

Get user 123.

GET should not normally modify server state.

Conceptually:

```text
GET /users/123

Database
   ↓
Read
   ↓
Response
```

---

# 11. POST

POST is generally used when creating a new resource.

```http
POST /users
```

Request:

```json
{
  "name": "Yusuf",
  "email": "yusuf@example.com"
}
```

The server creates the resource and assigns an identifier.

```text
POST /users
      ↓
Create User
      ↓
id = 123
```

Response might be:

```http
201 Created
```

---

# 12. PUT

PUT is generally used to **replace** a resource.

```http
PUT /users/123
```

Conceptually:

```text
Existing User
      ↓
Replace representation
      ↓
New User
```

For example:

```json
{
  "name": "Yusuf",
  "email": "new@example.com"
}
```

The exact API contract determines whether omitted fields are rejected or interpreted in some other way, but the important semantic distinction is:

> **PUT represents replacement.**

---

# 13. PATCH

PATCH is generally used for a **partial modification**.

```http
PATCH /users/123
```

Request:

```json
{
  "email": "new@example.com"
}
```

Only the requested field changes.

```text
Existing User
      ↓
Modify selected fields
      ↓
Updated User
```

A useful mental model:

```text
PUT
→ Replace

PATCH
→ Modify
```

---

# 14. DELETE

DELETE removes a resource.

```http
DELETE /users/123
```

Conceptually:

```text
/users/123
     ↓
Delete
```

A successful DELETE might return:

```http
204 No Content
```

when there is no response body to return.

---

# 15. Custom Actions

Sometimes an operation doesn't naturally fit CRUD.

For example:

```text
POST /users/123/deactivate
```

or:

```text
POST /orders/123/cancel
```

The video discusses using POST for custom actions that don't fit the normal CRUD operations.

The important point is:

> **Don't force every business operation into a fake CRUD operation.**

If an operation is genuinely an action, represent that clearly.

---

# 16. Idempotency

This is one of the most important concepts in REST API design.

An operation is **idempotent** when making the same request multiple times has the same intended effect as making it once.

Conceptually:

```text
Request
Request
Request
Request

        ↓

Same resulting server state
```

For example:

```http
PUT /users/123
```

with the same complete representation can be repeated without continually creating additional users.

---

# 17. Why Idempotency Matters

Imagine a network failure.

The client sends:

```text
POST /orders
```

but doesn't receive the response.

The client doesn't know whether:

```text
Order wasn't created
```

or:

```text
Order was created but response was lost
```

If it retries:

```text
POST /orders
```

it could create another order.

This is why idempotency is extremely important in reliable distributed systems.

---

# 18. HTTP Method Idempotency

A useful interview-level mental model:

```text
GET     → Idempotent
PUT     → Idempotent
DELETE  → Idempotent
PATCH   → generally designed to be idempotent, but depends on the operation
POST    → generally non-idempotent
```

Be careful with wording.

Idempotency is a **property of the operation**, not simply a magic property of the method name.

For example, a PATCH operation that increments a counter:

```text
PATCH /counter
{
    "increment": 1
}
```

could produce a different result each time.

So don't blindly say:

> "Every PATCH is idempotent."

# 19. Resource Design Example

Suppose we're building a project-management platform.

Our resources are:

```text
organizations

tasks
```

We could design:

```text

GET    /organizations/1

```

Projects:

```text
GET    /projects

GET    /projects/1
PATCH  /projects/1
DELETE /projects/1
```

Tasks:

```text
GET    /tasks
POST   /tasks

GET    /tasks/1
PATCH  /tasks/1
DELETE /tasks/1
```

The patterns are predictable.

# 20. Consistency Is Everything

Suppose your API uses:

```text
GET /users
```

but then:

```text
GET /getProjects
```

and:

```text
GET /task-list
```

Now consumers have to memorize arbitrary conventions.

A better API follows consistent rules.

```text
/users
/projects
/tasks
```

The consumer can predict new endpoints.

The video repeatedly emphasizes **consistency** as one of the most important characteristics of good API design. ([Transcribe][1])

---

# 21. Payload Consistency

Consistency isn't only about URLs.

Suppose users use:

```json
{
  "name": "...",
  "description": "..."
}
```

But projects use:

```json
{
  "project_name": "...",
  "desc": "..."
}
```

and tasks use:

```json
{
  "taskName": "...",
  "taskDescription": "..."
}
```

This increases cognitive overhead.

Pick a convention and stick to it.

For example:

```text
name
description
createdAt
updatedAt
```

across resources.

---

# 22. Response Consistency

Suppose:

```text
GET /users
```

returns:

```json
[
  {...},
  {...}
]
```

but:

```text
GET /projects
```

returns:

```json
{
  "data": [
    {...}
  ]
}
```

and:

```text
GET /tasks
```

returns:

```json
{
  "results": [
    {...}
  ]
}
```

Now consumers have to learn three patterns.

Choose a consistent response structure.

The exact structure can vary between APIs.

The important principle is:

> **Once you establish a convention, use it consistently.**

---

# 23. List APIs

A list endpoint:

```http
GET /projects
```

should generally return a collection.

For example:

```json
[
  {
    "id": 1,
    "name": "Project A"
  },
  {
    "id": 2,
    "name": "Project B"
  }
]
```

If there are no projects:

```json
[]
```

not:

```http
404 Not Found
```

for the collection itself.

---

# 24. Empty Collection vs Missing Resource

This distinction is extremely important.

### List

```http
GET /projects
```

No projects exist.

Response:

```http
200 OK
```

```json
[]
```

The collection exists.

It's simply empty.

---

### Individual Resource

```http
GET /projects/123
```

Project 123 doesn't exist.

Response:

```http
404 Not Found
```

Mental model:

```text
GET /projects
    ↓
Collection exists
    ↓
Maybe empty

GET /projects/123
    ↓
Specific resource doesn't exist
    ↓
404
```

The source explicitly highlights this distinction. ([Transcribe][1])

# 25. Pagination

Imagine:

```text
GET /users
```

and there are:

```text
10,000,000 users
```

Returning all of them is obviously undesirable.

Instead:

```http
GET /users?page=2&limit=20
```

or another pagination scheme.

The API returns a manageable subset.

---

# 26. Why Pagination Matters

Without pagination:

```text
Database
   ↓
10 million rows
   ↓
Backend
   ↓
Huge JSON
   ↓
Network
   ↓
Client
```

This creates unnecessary:

* Database load
* CPU usage
* Memory usage
* Network traffic
* Client processing

Pagination limits the amount of data transferred.

---

# 27. Pagination Defaults

The client shouldn't always have to specify everything.

For example:

```http
GET /users
```

could have sensible defaults:

```text
page = 1
limit = 20
```

Then:

```http
GET /users?page=3&limit=50
```

can override them.

The video emphasizes **sensible defaults** as part of good API design. ([Transcribe][1])

---

# 28. Limit Maximum Page Size

Don't allow:

```http
GET /users?limit=999999999
```

without restrictions.

A backend might define:

```text
default limit = 20
maximum limit = 100
```

Then:

```text
limit=5000
```

could be rejected or capped according to the API contract.

This prevents clients from accidentally or intentionally requesting huge datasets.

---

# 29. Filtering

List APIs often need filtering.

Example:

```http
GET /tasks?status=completed
```

or:

```http
GET /users?role=admin
```

The URL describes the collection and query parameters describe the desired subset.

```text
/tasks
   +
?status=completed
```

---

# 30. Sorting

Clients often need to control ordering.

For example:

```http
GET /projects?sort=createdAt
```

or:

```http
GET /projects?sort=-createdAt
```

where the API defines:

```text
createdAt
→ ascending

-createdAt
→ descending
```

The exact syntax is your API's contract.

Again:

> **Choose a convention and use it consistently.**

---

# 31. Filtering + Sorting + Pagination

Real list APIs often combine them:

```http
GET /tasks
    ?status=completed
    &sort=-createdAt
    &page=2
    &limit=20
```

Conceptually:

```text
All Tasks
   ↓
Filter
   ↓
Sort
   ↓
Paginate
   ↓
Response
```

These operations should be designed as part of the API interface rather than added randomly later.

---

# 32. Path Parameters vs Query Parameters

Use a **path parameter** when identifying a specific resource:

```http
GET /users/123
```

Here:

```text
123
```

identifies the resource.

Use **query parameters** for modifying the way a collection is retrieved:

```http
GET /users?role=admin
```

```http
GET /users?page=2
```

```http
GET /users?sort=-createdAt
```

Mental model:

```text
Path
→ Which resource?

Query
→ How do I want the collection?
```

---

# 33. Status Codes

A well-designed API uses HTTP status codes consistently.

Common ones:

| Status | Meaning                                      |
| ------ | -------------------------------------------- |
| 200    | Successful request                           |
| 201    | Resource created                             |
| 204    | Success with no content                      |
| 400    | Invalid request                              |
| 401    | Authentication required/failed               |
| 403    | Forbidden                                    |
| 404    | Resource not found                           |
| 409    | Conflict                                     |
| 422    | Unprocessable content, where used by the API |
| 429    | Too many requests                            |
| 500    | Server error                                 |

The exact choice depends on the semantics of the failure and the API contract.

# 34. Create Response

For:

```http
POST /users
```

successful creation commonly returns:

```http
201 Created
```

and may return the created representation:

```json
{
  "id": 123,
  "name": "Yusuf"
}
```

---

# 35. Update Response

For:

```http
PATCH /users/123
```

you might return:

```http
200 OK
```

with the updated representation.

Or:

```http
204 No Content
```

if there is no response body.

The key is consistency.

---

# 36. Delete Response

For:

```http
DELETE /users/123
```

a common response is:

```http
204 No Content
```

when the operation succeeds and there's nothing useful to return.

---

# 37. Error Responses

Errors should also follow a consistent structure.

Instead of every endpoint inventing something different:

```json
{
  "message": "..."
}
```

```json
{
  "error_message": "..."
}
```

```json
{
  "reason": "..."
}
```

define a consistent contract.

For example:

```json
{
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "User does not exist"
  }
}
```

The exact structure is less important than consistency and useful semantics.

---

# 38. Don't Expose Internal Errors

Never blindly return:

```text
PostgreSQL error
Stack trace
Internal file path
Database schema
```

to the API consumer.

Instead:

```text
Internal Error
      ↓
Map to API-level error
      ↓
Safe response
```

Internally you can log the detailed error.

Externally you provide a stable contract.

---

# 39. API Versioning

APIs evolve.

Suppose you have:

```text
/users
```

and later you need a breaking change.

Common approaches include:

```text
URI versioning

/v1/users
/v2/users
```

or:

```text
Header versioning
```

or:

```text
Media-type versioning
```

or other explicit versioning strategies.

The key principle:

> **Don't unexpectedly break existing consumers.**

```text

    ↓

    ↓
```

# 47. Predictability

A great API lets developers predict behavior.

If they know:

```text
GET /users
```

then they should be able to reasonably guess:

```text
GET /users/123
POST /users
PATCH /users/123
DELETE /users/123
```

Likewise, if:

```text
GET /projects?page=2
```

supports pagination, developers should expect similar behavior from:

```text
GET /tasks?page=2
GET /users?page=2
```

That's the power of consistency.

# 🧠 Interview Mental Models

### What is REST?

> REST is an architectural style for designing networked systems around resources and their representations, using standardized interactions such as HTTP methods.

### Why use nouns in REST URLs?

> URLs identify resources, while HTTP methods describe the operation being performed on those resources.

### Why plural resource names?

> They naturally represent collections and make collection/member relationships predictable, e.g. `/users` and `/users/123`.

### PUT vs PATCH?

> PUT generally represents replacing a resource representation, while PATCH represents a partial modification.

### Why pagination?

> To prevent large collections from creating excessive database, memory, network, and client-side costs.

### Why return `[]` instead of 404 for an empty list?

> Because the collection exists; it simply contains zero resources. A 404 is appropriate when a specific requested resource doesn't exist.

### Why design before coding?

> Because API design is a contract. Designing first allows you to reason about the consumer experience, consistency, payloads, errors, and resource relationships without being constrained by implementation details.

# ⚠️ Interview Traps

### ❌ "REST means using JSON."

**No.**

JSON is a representation format. REST is an architectural style.

---

### ❌ "PUT and PATCH are the same."

**No.**

```text
PUT
→ Replacement semantics

PATCH
→ Partial modification
```

---

### ❌ "Every PATCH request is idempotent."

**Not necessarily.**

Idempotency depends on the operation's semantics.

---

### ❌ "Empty collection means 404."

**Usually no.**

```text
GET /users
→ 200
→ []
```

A specific missing resource is different:

```text
GET /users/123
→ 404
```

---

### ❌ "API design starts when you start coding."

**No.**

A good workflow is:

```text
Requirements
→ Resources
→ Interface
→ Contract
→ Implementation
```

---

### ❌ "Good API design means having clever URLs."

**No.**

Good API design is primarily about:

```text
Predictability
Consistency
Clear semantics
Good contracts
Useful errors
Documentation
```

# 🔥 Core Takeaways

* **Design the API before implementing it.**
* REST is an architectural style, not a framework or programming language.
* REST APIs are designed around **resources**.
* Resource URLs should generally use **nouns**, not verbs.
* Plural resource names make collection/member relationships predictable.
* HTTP methods provide the operation semantics.
* `GET` reads.
* `POST` generally creates.
* `PUT` generally replaces.
* `PATCH` partially modifies.
* `DELETE` deletes.
* Custom actions can be represented explicitly when CRUD doesn't naturally fit.
* **Idempotency matters because networks fail and clients retry.**
* List endpoints should support pagination when collections can become large.
* Filtering, sorting, and pagination should follow consistent conventions.
* Use sensible defaults and maximum limits.
* An empty collection is normally represented as `200 OK` with `[]`, not `404`.
* Specific missing resources can return `404`.
* API responses and errors should have predictable structures.
* API versioning protects existing consumers from breaking changes.
* OpenAPI provides a machine-readable API contract and enables interactive documentation.
* **Consistency is more important than cleverness.**
* The API is a contract between the backend and its consumers.

> ### The interview-level mental model
>
> **Don't start by asking "What endpoints should I code?"**
>
> Start with:
>
> **What are my resources? → How are they related? → How should clients interact with them? → What should requests and responses look like? → What are the failure cases? → How do I make all of this predictable and consistent?**
>
> Once that contract is right, the implementation becomes much easier.
