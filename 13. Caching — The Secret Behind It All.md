# 13. Caching — The Secret Behind It All ⚡

> **Caching is one of the simplest ideas in backend engineering: do expensive work once, remember the result, and reuse it when possible.**
>
> It appears everywhere — from CPU caches to DNS, CDNs, browsers, and backend databases such as Redis. The implementation changes, but the underlying idea remains the same:
>
> **Avoid expensive work by keeping frequently needed data somewhere faster.**

This chapter is about **1 hour 4 minutes** and focuses specifically on caching from a backend-engineering perspective: real-world examples, network/hardware/software cache levels, CDNs, DNS, in-memory databases, caching strategies, eviction policies, Redis-like systems, and practical use cases such as database-query caching and rate limiting. ([Transcribe][1])

---

# 1. What Is Caching?

At the simplest level:

> **Caching is storing a subset of data somewhere faster so that it can be retrieved more quickly later.**

Imagine:

```text
Without Cache

Request
   ↓
Expensive computation
   ↓
Result
   ↓
Client
```

Every request repeats the expensive work.

With caching:

```text
First Request
     ↓
Expensive computation
     ↓
Result
     ↓
Cache
     ↓
Client


Next Request
     ↓
Cache
     ↓
Result
```

The expensive operation happens only when necessary.

---

# 2. Why Do We Need Caching?

There are two major reasons.

### 1. Avoid expensive computation

For example:

```text
Google Search
```

A search engine may need to perform enormous amounts of computation to determine relevant results.

Doing all that work for every identical request would be wasteful.

Instead:

```text
Query
 ↓
Cache?
 ├── YES → Return cached result
 └── NO  → Compute → Cache → Return
```

---

### 2. Avoid transferring large amounts of data

Consider Netflix.

A video file can be enormous.

Instead of repeatedly transferring the same content from a central server across the internet:

```text
Origin Server
     ↓
Internet
     ↓
User
```

Netflix can place frequently requested content closer to users through CDNs.

```text
Origin
   ↓
CDN Edge
   ↓
User
```

This reduces latency and network overhead. ([Video Highlight][2])

---

# 3. The Fundamental Caching Pattern

Almost every cache can be understood using this:

```text
             Request
                ↓
          ┌───────────┐
          │   Cache   │
          └─────┬─────┘
             Hit│  │Miss
                │  │
                ↓  ↓
             Return  Expensive
             Result  Operation
                        ↓
                      Result
                        ↓
                      Cache
                        ↓
                      Return
```

Two words are extremely important:

### Cache Hit

Data exists in the cache.

```text
Request
   ↓
Cache
   ↓
Found
   ↓
Return
```

### Cache Miss

Data isn't in the cache.

```text
Request
   ↓
Cache
   ↓
Not Found
   ↓
Fetch / Compute
   ↓
Cache Result
   ↓
Return
```

---

# 4. Cache Hit vs Cache Miss

Suppose:

```text
product:123
```

is stored in Redis.

First request:

```text
GET product:123
```

Cache:

```text
MISS
```

Backend:

```text
PostgreSQL
   ↓
Product
```

Then:

```text
PostgreSQL result
       ↓
Redis
       ↓
Client
```

Second request:

```text
GET product:123
```

Redis:

```text
HIT
```

and the database isn't queried.

---

# 5. Cache Hit Ratio

A useful performance metric is:

```text
Cache Hit Ratio =
Cache Hits / Total Cache Requests
```

For example:

```text
100 requests

80 hits
20 misses
```

Then:

```text
Hit ratio = 80%
```

A higher hit ratio generally means the cache is successfully serving more requests.

But:

> **A high hit ratio isn't automatically good if the cached data is stale or the cache is incorrectly designed.**

# 8. CDN — Content Delivery Network

A CDN is a network of geographically distributed servers, commonly called **edge servers** or **points of presence (PoPs)**.

Instead of every user requesting content from the origin server:

```text
User in India
      ↓
      ↓
Origin in USA
```

the CDN can serve cached content from a nearby location:

```text
User in India
      ↓
Nearby CDN Edge
      ↓
Cached Content
```

The result:

```text
Lower latency
Less origin traffic
Better scalability
```

---

# 9. Netflix Example

Imagine Netflix has:

```text
Movie A
Movie B
Movie C
Movie D
...
```

Users in India might heavily watch:

```text
Movie A
Movie C
```

while users in Europe might prefer:

```text
Movie B
Movie D
```

It doesn't make sense to cache every piece of content at every edge location.

Instead, caching decisions can depend on demand.

```text
India Edge

Movie A  ← frequently requested
Movie C  ← frequently requested

Movie Z  ← rarely requested
```

The goal is:

> **Keep the content that is most valuable to users at the location where it is most useful.**

# 10. DNS Caching

DNS translates:

```text
google.com
```

into an IP address.

Without caching, every request would potentially require DNS resolution again.

Instead:

```text
Domain
   ↓
DNS Lookup
   ↓
IP Address
   ↓
Cache
```

Later:

```text
google.com
   ↓
DNS Cache
   ↓
IP Address
```

No complete lookup is necessary every time.

```text
   ↓
DNS Resolver
   ↓
Resolver Cache
   ↓
If MISS
   ↓
DNS hierarchy
   ↓
IP Address
   ↓
Cache result
```

Caching reduces:

```text
Latency

Repeated DNS work
```

# 12. Hardware-Level Caching

Now move closer to the CPU.

Modern computers have a memory hierarchy.

Conceptually:

```text
CPU
 ↓
L1 Cache
 ↓
L2 Cache
 ↓
L3 Cache
 ↓
RAM
 ↓
Disk / SSD
```

The closer the storage is to the CPU:

```text
Faster
Smaller
More expensive
```

The farther away:

```text
Slower
Larger
Cheaper
```

---

# 13. Why CPU Caches Exist

Suppose the CPU repeatedly needs the same data.

Instead of:

```text
CPU
 ↓
RAM
 ↓
Get data
```

every time:

```text
First access
CPU → RAM
       ↓
      Data
       ↓
     Cache


Next access
CPU → Cache
       ↓
      Data
```

This exploits **locality**.

Programs often reuse:

* recently accessed data
* nearby memory locations
* frequently executed instructions

Caching takes advantage of this behavior.

# 14. Software-Level Caching

This is where backend engineers spend most of their time.

The idea:

```text
Application
    ↓
Fast in-memory store
    ↓
Database / external service
```

Instead of querying PostgreSQL repeatedly:

```text
Request
  ↓
PostgreSQL
  ↓
Response
```

we can use:

```text
Request
  ↓
Redis
  ↓
HIT → Response
```

and only go to PostgreSQL when necessary.

# 15. In-Memory Databases

Technologies such as:

```text

Memcached

```

# 16. Why Are They Fast?

Traditional relational databases such as PostgreSQL rely heavily on persistent storage.

In-memory databases keep active data in:

```text
RAM
```

RAM is significantly faster to access than persistent storage.

Conceptually:

```text
PostgreSQL

Application
    ↓
Database
    ↓
Storage
```

versus:

```text
Redis

Application
    ↓
Redis
    ↓
RAM
```

This makes Redis-like systems excellent for workloads where very fast access is required.

---

# 17. But Doesn't Redis Need Persistence?

Important distinction:

> **An in-memory database doesn't necessarily mean it has zero persistence.**

Redis can persist data using mechanisms that write to secondary storage.

Conceptually:

```text
             Redis
               │
        ┌──────┴──────┐
        ↓             ↓
       RAM           Disk
     Fast access    Persistence
```

When accessing or modifying cached data, the primary path is memory.

The video explains this distinction while introducing Redis and similar technologies. ([Transcribe][1])


```text

 ↓
```

```text
 ↓
Value
```

# 20. Cache Aside / Lazy Caching

One of the most important caching strategies in the video is:

> **Cache Aside**, also called **Lazy Caching**.

Flow:

```text
Request
   ↓
Check Cache
   │
   ├── HIT ─────→ Return
   │
   └── MISS
          ↓
       Database
          ↓
       Result
          ↓
        Cache
          ↓
        Return
```

The application explicitly manages the cache.

---

# 21. Why Is It Called Lazy?

Because you don't populate the cache proactively.

You wait until someone actually requests the data.

```text
Nobody requests product A
        ↓
Don't cache it


Someone requests product A
        ↓
Fetch product A
        ↓
Cache product A
```

That's why:

> **The cache is populated lazily.**

The video calls this one of the most common caching patterns in backend engineering. ([Transcribe][1])

---

# 22. Cache Aside Example

Suppose:

```text
GET /products/501
```

### Step 1

Check:

```text
Redis
product:501
```

Result:

```text
MISS
```

### Step 2

Query:

```text
PostgreSQL
```

### Step 3

Store:

```text
Redis
product:501 → product data
```

### Step 4

Return response.

Next request:

```text
GET /products/501
```

becomes:

```text
Redis
 ↓
HIT
 ↓
Response
```

PostgreSQL isn't touched.

# 23. Write-Through Caching

Another strategy discussed is:

> **Write-through caching**

Here, when data changes, the cache is updated along with the primary storage.

Conceptually:

```text
Write Request
      ↓
Database
      +
Cache
      ↓
Both updated
```

For example:

```text
PATCH /products/501
        ↓
Update PostgreSQL
        +
Update Redis
```

The goal is to keep the cache synchronized with writes.

The video describes write-through primarily as a cache-update strategy associated with writes. ([Transcribe][1])

---

# 24. Cache Aside vs Write Through

|                  | Cache Aside                     | Write Through                 |
| ---------------- | ------------------------------- | ----------------------------- |
| Cache population | On read miss                    | During writes                 |
| Read miss        | Fetch DB → cache                | Usually cache already updated |
| Write path       | DB, cache may update separately | DB + cache                    |
| Complexity       | Simple                          | More coordinated              |
| Common use       | Read-heavy data                 | Systems wanting fresher cache |

Mental model:

```text
Cache Aside

READ:
Cache → MISS → DB → Cache


Write Through

WRITE:
Application → DB + Cache
```

# 25. Cache Eviction

A cache has limited memory.

Imagine:

```text
Cache Capacity = 1 GB
```

but you want to cache:

```text
10 GB
```

You need to decide:

> **Which data should be removed when the cache is full?**

This is called:

> **Cache eviction**

---

# 26. No Eviction Policy

If there is no eviction policy and the cache is full:

```text
New item
   ↓
Cache full
   ↓
Cannot insert
```

This is usually undesirable for a bounded cache.

So caches generally need a strategy for deciding what to remove.

---

# 27. LRU — Least Recently Used

LRU removes the item that hasn't been accessed recently.

Imagine:

```text
A → accessed recently
B → accessed recently
C → not accessed for a long time
```

Cache becomes full.

New item:

```text
D
```

LRU removes:

```text
C
```

because it was least recently used.

```text
A  ← recently used
B  ← recently used
C  ← least recently used → EVICT
D  ← new
```

---

# 28. Why LRU Makes Sense

Applications often exhibit **temporal locality**:

> If something was accessed recently, it may be accessed again soon.

For example:

```text
Trending product
Popular profile
Recently viewed page
```

LRU tries to preserve recently useful data.

---

# 29. LFU — Least Frequently Used

LFU focuses on **frequency**, not recency.

Suppose:

```text
Product A → accessed 1000 times
Product B → accessed 50 times
Product C → accessed 2 times
```

Cache becomes full.

LFU may evict:

```text
Product C
```

because it has the lowest access frequency.

---

# 30. LRU vs LFU

```text
LRU
→ When was it last used?


LFU
→ How often has it been used?
```

Example:

```text
A → accessed 1000 times last month
B → accessed 50 times today
```

Depending on the access history and exact implementation:

* LFU may favor A.
* LRU may favor B.

The correct choice depends on workload characteristics.

---

# 31. TTL — Time To Live

TTL is different.

> **TTL defines how long a cache entry should remain valid.**

Example:

```text
product:501

TTL = 10 minutes
```

After 10 minutes:

```text
Entry expires
```

The next request:

```text
Cache MISS
   ↓
Fetch fresh data
   ↓
Cache again
```

The video explicitly points out that TTL is **not technically an eviction policy in the same sense as LRU/LFU**; it defines the lifetime of an entry. ([Transcribe][1])

---

# 32. Why TTL Is Useful

Suppose your product price changes occasionally.

You don't want:

```text
Price
 ↓
Cache forever
```

because the user might see stale information.

Instead:

```text
Cache price
 ↓
TTL = 5 minutes
 ↓
Expire
 ↓
Fetch fresh price
```

TTL provides a simple freshness boundary.

---

# 33. Cache Invalidation

One of the hardest caching problems is:

> **What happens when the original data changes?**

Suppose:

```text
PostgreSQL
price = ₹1000
```

and Redis contains:

```text
price = ₹1000
```

Then the database changes:

```text
price = ₹900
```

But Redis still contains:

```text
₹1000
```

Now:

```text
Database = ₹900
Cache    = ₹1000
```

This is stale data.

---

# 34. The Cache Invalidation Problem

This is why people often say:

> **There are only two hard things in Computer Science: cache invalidation and naming things.**

The difficulty is keeping:

```text
Primary Data
      ↕
Cached Data
```

consistent enough for the application's requirements.

Possible approaches:

```text
TTL
Explicit invalidation
Write-through updates
Event-driven invalidation
```

The exact mechanism depends on the system.

# 36. Cache Keys

A cache needs a key.

For example:

```text
product:501
```

or:

```text
user:123
```

For query results:

```text
products:category:phones:page:1
```

The key must represent the inputs that affect the result.

For example:

```text
GET /products?category=phones&page=1
```

shouldn't share the exact same cached result with:

```text
GET /products?category=laptops&page=1
```

So the cache key might encode:

```text
category
page
sort
filters
```

---

# 37. Bad Cache Key Design

Suppose you cache:

```text
products
```

for every request.

Then:

```text
/products?category=phones
```

and:

```text
/products?category=laptops
```

could accidentally return the same cached result.

That's a correctness bug.

Therefore:

> **Cache keys must include every relevant input that changes the result.**

# 41. Caching and Rate Limiting

Another important use case:

> **Rate limiting**

Suppose your API allows:

```text
50 requests / minute / IP
```

The backend needs to maintain a counter.

Redis is a natural choice because it provides fast in-memory operations.

Conceptually:

```text

      ↓
count = 37
```

Request arrives:

```text

```

Eventually:

```text
count > 50
      ↓
429 Too Many Requests
```


# 44. Caching Doesn't Replace Your Database

This is a critical distinction.

Don't think:

```text
PostgreSQL → slow
Redis → fast
Therefore remove PostgreSQL
```

That's wrong.

Instead:

```text
PostgreSQL
   ↓
Source of persistent truth

Redis
   ↓
Fast temporary / derived copy
```

Often:

```text
PostgreSQL = source of truth
Redis      = performance layer
```

# 45. Cache vs Database

|                 | PostgreSQL         | Redis                                       |
| --------------- | ------------------ | ------------------------------------------- |
| Primary purpose | Persistent storage | Fast access/cache                           |
| Data model      | Relational         | Key-value/data structures                   |
| Complex queries | Excellent          | Not the main purpose                        |
| Joins           | Yes                | No relational joins                         |
| Persistence     | Core capability    | Optional/persistence mechanisms exist       |
| Speed           | Fast               | Extremely fast for suitable access patterns |
| Typical role    | Source of truth    | Cache / temporary state                     |

# 46. The Real Cost of Caching

Caching sounds amazing:

```text
Faster!
Less database load!
```

But it introduces complexity.

Now you have:

```text
Application
     ↓
Redis
     ↓
PostgreSQL
```

instead of:

```text
Application
     ↓
PostgreSQL
```

You now have to think about:

```text
Stale data
Invalidation
TTL
Eviction
Memory limits
Cache misses
Cache stampedes
Key design
Consistency
```

So:

> **Don't add a cache simply because Redis is fast.**

Add it when the workload benefits from it.

# 47. Cache Stampede

Imagine a popular cache entry:

```text
homepage
```

has expired.

Suddenly:

```text
10,000 requests
```

arrive at almost exactly the same time.

All see:

```text
CACHE MISS
```

Then all hit:

```text
PostgreSQL
```

simultaneously.

Instead of reducing database load, your cache expiration caused a huge spike.

This phenomenon is commonly called:

> **Cache stampede / thundering herd**

The video doesn't go deeply into this problem, but it follows directly from the cache-miss model and is useful interview knowledge.

# 48. Cache Design Questions

Whenever you decide to cache something, ask:

```text
1. What am I caching?
2. Why is it expensive?
3. How frequently is it accessed?
4. How frequently does it change?
5. How stale can it be?
6. What should the key be?
7. How long should it live?
8. How should it be invalidated?
9. What happens on cache miss?
10. What happens if Redis is unavailable?
```

This is much more important than simply knowing:

```text
redis.set()
redis.get()
```

---

# 49. What Happens If Cache Goes Down?

Suppose:

```text
Application
   ↓
Redis ❌
```

Should the entire application stop working?

Ideally, not always.

If Redis is only a performance cache:

```text
Redis unavailable
      ↓
Cache bypass
      ↓
PostgreSQL
      ↓
Application continues
```

The application becomes slower, but remains functional.

This is an example of:

> **Graceful degradation**

If Redis is being used for something more critical, such as distributed coordination or authentication state, the failure behavior may be different.

The correct behavior depends on the cache's role.

# 🧠 Interview Mental Models

### What is caching?

> Caching is storing frequently or strategically accessed data in a faster location so that future requests can avoid expensive computation or slower data retrieval.

---

### What is a cache hit?

> When the requested data is found in the cache.

---

### What is a cache miss?

> When the requested data isn't present or valid in the cache, requiring the system to retrieve or compute it elsewhere.

---

### Why is caching useful?

> It reduces latency, expensive computation, database load, network traffic, and sometimes external API usage.

---

### What is cache-aside?

> The application checks the cache first; on a miss it fetches the data from the primary store, puts the result into the cache, and returns it.

---

### What is write-through caching?

> Writes update the primary store and the cache together, keeping the cached representation synchronized with writes.

---

### LRU vs LFU?

> LRU evicts data that hasn't been used recently; LFU evicts data that has been accessed least frequently.

---

### What is TTL?

> Time To Live defines how long a cached entry remains valid before expiring.

---

### Why Redis?

> Redis provides very fast in-memory access and useful data structures, making it suitable for caching, counters, sessions, rate limiting, and other low-latency workloads.

---

### Does Redis replace PostgreSQL?

> Usually no. PostgreSQL can remain the persistent source of truth while Redis serves frequently accessed or derived data as a performance layer.

# ⚠️ Interview Traps

### ❌ "Caching means storing everything in RAM."

Not exactly.

Caching is the broader concept of storing useful data in a faster-access location.

It exists at:

```text
Network
Hardware
Software
```

and many other levels.

---

### ❌ "Redis is just a faster PostgreSQL."

No.

They solve different problems.

```text
PostgreSQL
→ Relational persistence + complex queries

Redis
→ Fast in-memory access + caching/data structures
```

---

### ❌ "TTL is an eviction algorithm like LRU."

Not exactly.

```text
LRU
→ Which item should be removed?

TTL
→ How long should this entry remain valid?
```

The video explicitly distinguishes TTL from traditional eviction policies. ([Transcribe][1])

---

### ❌ "Cache hit means the data is always correct."

No.

A cache can contain:

```text
STALE DATA
```

Correctness depends on your invalidation/freshness strategy.

---

### ❌ "Just cache every database query."

Bad idea.

Caching introduces:

```text
Memory cost
Invalidation complexity
Staleness
Key management
Failure modes
```

Cache when there is a meaningful performance or load benefit.

---

### ❌ "If Redis goes down, the backend must go down."

Not necessarily.

If Redis is only a performance cache:

```text
Redis fails
   ↓
Cache bypass
   ↓
PostgreSQL
   ↓
Slower but functional
```

That's often preferable to total failure.

# 🔥 Core Takeaways

* **Caching avoids expensive work by reusing previously obtained data.**
* A **cache hit** means the requested data is available in the cache.
* A **cache miss** means the system must retrieve/compute it elsewhere.
* Caching exists at network, hardware, and software levels.
* CDNs cache content near users to reduce latency and origin load.
* DNS caches domain-to-IP resolution results.
* CPU caches exploit locality to reduce memory-access latency.
* Redis and similar systems provide very fast in-memory access.
* **Cache-aside/lazy caching** populates the cache when a request actually needs the data.
* **Write-through caching** updates the cache as part of the write path.
* LRU considers recency.
* LFU considers frequency.
* TTL controls how long an entry remains valid.
* Caching database query results can dramatically reduce repeated database work.
* Cache keys must include the inputs that affect the result.
* Stale data and invalidation are fundamental caching problems.
* Redis can be useful for sessions, external API caching, and rate-limit counters.
* Caching is a performance layer; it doesn't automatically replace your primary database.
* A cache failure should ideally degrade performance rather than destroy functionality when the cache is non-critical.
* **Caching is a trade-off, not free performance.**

> ### The interview-level mental model
>
> Don't say:
>
> **"Redis makes my backend faster."**
>
> Say:
>
> **"I identify an expensive or frequently repeated operation, determine whether its result can tolerate some staleness, choose an appropriate cache key and freshness strategy, and place a faster cache in front of the expensive data source. On a cache hit I avoid the expensive operation; on a miss I fetch the source data and populate the cache."**
>
> **That is caching as a backend engineer — not just `redis.get()` and `redis.set()`.**
