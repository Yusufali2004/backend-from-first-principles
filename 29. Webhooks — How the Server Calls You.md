# 29. Webhooks — How the Server Calls You 🔔

> A **webhook** is a mechanism where one server automatically sends an HTTP request to another server when an event happens.

The normal API model is:

```text
Client
  ↓
Server
  ↓
Response
```

A webhook reverses who initiates the communication:

```text
Event happens
     ↓
External Server
     ↓
HTTP Request
     ↓
Your Server
```

---

# 1. The Problem Webhooks Solve ⭐⭐⭐

Imagine you are integrating a payment system.

A customer pays.

Your application needs to know:

```text
"Was the payment successful?"
```

One approach is polling.

```text
Your Server
    ↓
"Is payment complete?"
    ↓
Payment Server

Your Server
    ↓
"Is payment complete?"
    ↓
Payment Server

Your Server
    ↓
"Is payment complete?"
    ↓
Payment Server
```

This is inefficient.

Instead, use a webhook:

```text
Customer pays
     ↓
Payment Provider
     ↓
POST /webhooks/payment
     ↓
Your Backend
     ↓
Update database
```

The external service **calls you when something happens**.


The key difference:

```text
API:
You ask → They answer

Something happens → They tell you
```

# 5. Webhooks Use HTTP ⭐⭐⭐

# 7. Webhook Endpoint ⭐⭐⭐

Your application exposes a special endpoint.

Example:

```text
POST /webhooks/payment
```

Node.js:

```javascript
app.post("/webhooks/payment", (req, res) => {
    console.log(req.body);

    res.status(200).send("OK");
});
```

FastAPI:

```python
@app.post("/webhooks/payment")
async def payment_webhook(payload: dict):
    print(payload)

    return {"status": "ok"}
```

The external service sends requests to this endpoint.

# 12. Event Types

A provider may send different event types.

For example:

```text
payment.created
payment.success
payment.failed
payment.refunded
```

Your webhook can route them:

```javascript
switch (event.type) {
    case "payment.success":
        handlePaymentSuccess(event);
        break;

    case "payment.failed":
        handlePaymentFailure(event);
        break;

    case "payment.refunded":
        handleRefund(event);
        break;
}
```

# 13. Webhook Security ⭐⭐⭐

Webhooks are exposed HTTP endpoints.

Anyone could potentially try:

```text
POST /webhooks/payment
```

So your application must verify that the request actually came from the trusted provider.

Do **not** blindly trust the payload.

Bad:

```javascript
app.post("/webhook", (req, res) => {
    markPaymentAsSuccessful(req.body);
});
```

An attacker could send:

```json
{
  "payment": "success"
}
```

and potentially manipulate your system.

---

# 14. Webhook Signatures ⭐⭐⭐

A common security mechanism is a signature.

The provider sends:

```http
X-Webhook-Signature: abc123...
```

Your server calculates its own signature using a shared secret.

```text
Provider
   │
   │ Payload + Secret
   ↓
Signature
   │
   ↓
HTTP Request
   │
   ↓
Your Server
   │
   │ Payload + Same Secret
   ↓
Calculate Signature
   │
   ↓
Compare
```

If signatures match:

```text
✅ Trusted
```

If they don't:

```text
❌ Reject
```

---

# 15. HMAC Signature ⭐⭐⭐

A common technique is HMAC.

Conceptually:

```text
HMAC(
    secret,
    request_body
)
```

The provider calculates:

```text
Signature A
```

Your server calculates:

```text
Signature B
```

Then:

```text
Signature A == Signature B
        ↓
      Valid
```

Otherwise:

```text
❌ Invalid webhook
```

---

# 16. Never Trust the Payload Alone 🚨

This is extremely important.

Receiving:

```json
{
  "status": "success"
}
```

doesn't prove that the request came from the payment provider.

You need:

```text
Request
  ↓
Authenticate / Verify
  ↓
Validate Payload
  ↓
Process Event
```

Not:

```text
Request
  ↓
Immediately trust
```

# 17. HTTPS ⭐⭐⭐

Webhook endpoints should use HTTPS.

Bad:

```text
http://example.com/webhook
```

Better:

```text
https://example.com/webhook
```

HTTPS protects the request while it travels over the network.

# 19. Idempotency ⭐⭐⭐

One of the most important webhook concepts.

A provider may send the same event more than once.

Example:

```text
Event 123
   ↓
Webhook
   ↓
Your Server

Network timeout

Provider thinks:
"Maybe it failed."

   ↓
Webhook Event 123 again
```

Now your backend receives:

```text
Event 123
Event 123
```

If your code blindly processes both:

```text
Payment +₹500
Payment +₹500
```

You could accidentally process the same event twice.

---

# 20. Idempotent Webhook Handling

Store the event ID.

Example:

```text
webhook_events
-----------------
event_id
processed_at
```

When an event arrives:

```text
Event ID
   ↓
Already processed?
   │
 ┌─┴──────────┐
 ↓            ↓
Yes           No
 ↓             ↓
Ignore       Process
               ↓
          Save Event ID
```

---

# 21. Example

Incoming:

```json
{
  "id": "evt_123",
  "type": "payment.success"
}
```

Check:

```sql
SELECT *
FROM webhook_events
WHERE event_id = 'evt_123';
```

If found:

```text
Already processed
      ↓
Return success
```

If not found:

```text
Process event
      ↓
Save evt_123
      ↓
Return success
```

# 22. Why Duplicate Webhooks Happen

Duplicates can happen because of:

```text
Network failures
Timeouts
Retries
Server crashes
Temporary provider failures
```

For example:

```text
Provider
   │
   │ Webhook
   ↓
Your Server
   │
   │ Process
   ↓
Database
   │
   X
Response lost
   │
   ↓
Provider retries
```

The provider doesn't know whether you successfully processed the event.

So it retries.

---

# 23. Webhook Retry ⭐⭐⭐

Many webhook providers retry failed deliveries.

Example:

```text
Attempt 1
   ↓
Timeout

Attempt 2
   ↓
Timeout

Attempt 3
   ↓
Success
```

The exact retry policy depends on the provider.

Therefore:

> Your webhook handler must be prepared to receive the same event multiple times.

---

# 24. Return HTTP Status Codes ⭐⭐⭐

Your webhook endpoint should respond appropriately.

Success:

```http
200 OK
```

or sometimes:

```http
204 No Content
```

Temporary failure:

```http
500 Internal Server Error
```

Invalid request:

```http
400 Bad Request
```

Unauthorized:

```http
401 Unauthorized
```

The provider may use these responses to determine whether it should retry.

---

# 25. Acknowledge Quickly ⭐⭐⭐

Webhook providers usually don't want your endpoint to take a very long time.

Bad:

```text
Webhook
   ↓
Validate
   ↓
Process huge job
   ↓
Call 10 APIs
   ↓
Generate report
   ↓
Database operations
   ↓
Finally return 200
```

This can cause timeouts.

Better:

```text
Webhook
   ↓
Verify
   ↓
Store event
   ↓
Queue job
   ↓
Return 200
   ↓
Worker processes job
```

# 35. Webhook Database Design

A simple event table could look like:

```sql
CREATE TABLE webhook_events (
    id SERIAL PRIMARY KEY,
    event_id VARCHAR(255) UNIQUE NOT NULL,
    event_type VARCHAR(255) NOT NULL,
    received_at TIMESTAMP DEFAULT NOW(),
    processed_at TIMESTAMP
);
```

The unique constraint helps prevent duplicate processing.

```text
event_id UNIQUE
      ↓
Same event twice
      ↓
Database rejects duplicate
```

# 39. Dead-Letter Queue ⭐⭐

Sometimes an event repeatedly fails.

```text
Webhook
   ↓
Queue
   ↓
Worker
   ↓
Failure
   ↓
Retry
   ↓
Failure
   ↓
Retry
   ↓
Failure
```

Eventually it can go to a:

```text
Dead-Letter Queue
```

```text
DLQ
 ↓
Manual investigation
```

This prevents one permanently broken event from blocking normal processing.

# 40. Common Webhook Mistakes 🚨

### Mistake 1 — Trusting the payload

```text
POST /webhook
     ↓
"status=success"
     ↓
Mark payment successful
```

❌ Never blindly trust it.

---

### Mistake 2 — No signature verification

Attackers can send fake events.

```text
Attacker
   ↓
POST /webhook
   ↓
Your Server
```

❌ Verify authenticity.

---

### Mistake 3 — No idempotency

```text
Same event
   ↓
Processed twice
```

❌ Can cause duplicate payments/orders/emails.

---

### Mistake 4 — Slow webhook processing

```text
Webhook
   ↓
Long-running work
   ↓
Timeout
   ↓
Provider retries
```

❌ This can create duplicates.

---

### Mistake 5 — No logging

When something goes wrong:

```text
"Why didn't payment update?"
```

Without logs, debugging becomes difficult.

---

### Mistake 6 — No retry strategy

Temporary failures happen.

Your system should be designed around them.

# 43. Interview Questions ⭐⭐⭐

### Q1. What is a webhook?

A webhook is an HTTP callback where an external service sends a request to your server when a particular event occurs.

---

### Q2. Webhook vs API?

```text

Client asks → Server responds

Webhook:

```

---

### Q3. Webhook vs polling?

```text
Polling:
Repeatedly ask for changes.

Webhook:
Receive notification when change occurs.
```

---

### Q4. Why must webhook handlers be idempotent?

Because webhook providers may retry events, causing the same event to be delivered multiple times.

### Q5. How do you secure a webhook?

Common techniques:

```text
HTTPS
Signature verification
HMAC
Authentication
Replay protection
Payload validation
```

---

Because providers may timeout and retry if the endpoint takes too long to respond.

```text

   ↓

   ↓
```

### Q9. Why do webhook providers retry?

Usually because they didn't receive a successful response or encountered a delivery failure.
