# 22. Concurrency & Parallelism: I/O-Bound vs CPU-Bound ⚙️

> **Concurrency and parallelism are not the same thing.**
>
> A backend engineer needs to understand *what the program is waiting for* before deciding how to execute work.
>
> The key question is:
>
> **Is the workload I/O-bound or CPU-bound?**

---

# 1. The Big Picture

A backend server is usually doing two broad types of work:

```text
                    BACKEND WORK
                         │
              ┌──────────┴──────────┐
              ↓                     ↓
          I/O-Bound              CPU-Bound
              │                     │
       Waiting for I/O        Computing something
              │                     │
       DB / Network / File      CPU calculations
              │                     │
        Concurrency helps       Parallelism helps
```

The distinction matters because the optimal solution can be completely different.

---

# 2. What Is Concurrency?

**Concurrency** means dealing with multiple tasks during overlapping periods of time.

It does **not** necessarily mean that tasks execute at exactly the same moment.

Imagine:

```text
Task A: ███ wait █████
Task B:    ███ wait ███
Task C:       █████
```

The system is making progress on multiple tasks.

A simple mental model:

> **Concurrency = managing multiple things at once.**

---

# 3. What Is Parallelism?

**Parallelism** means multiple tasks are actually executing simultaneously.

This generally requires multiple execution units, such as CPU cores.

```text
CPU Core 1 → Task A
CPU Core 2 → Task B
CPU Core 3 → Task C
```

Mental model:

> **Parallelism = doing multiple things at the same time.**

---

# 4. Concurrency vs Parallelism ⭐

|                              | Concurrency                             | Parallelism                           |
| ---------------------------- | --------------------------------------- | ------------------------------------- |
| Main idea                    | Multiple tasks make progress            | Multiple tasks execute simultaneously |
| Requires multiple CPU cores? | No                                      | Usually                               |
| Useful for                   | I/O-bound work                          | CPU-bound work                        |
| Example                      | Waiting for DB requests                 | Image processing                      |
| Goal                         | Keep execution productive while waiting | Use multiple CPUs simultaneously      |

A program can be:

```text
Concurrent but not parallel
```

and:

```text
Concurrent + parallel
```

---

# 5. Simple Real-World Example

Imagine a restaurant.

### Concurrency

One waiter:

```text
Take order from A
 ↓
Send order to kitchen
 ↓
While food is cooking:
Take order from B
 ↓
Check table C
 ↓
Return to A
```

The waiter isn't cooking multiple meals simultaneously.

They're **switching between tasks while waiting**.

That's concurrency.

---

### Parallelism

Multiple chefs:

```text
Chef 1 → Meal A
Chef 2 → Meal B
Chef 3 → Meal C
```

Multiple tasks are actually being performed simultaneously.

That's parallelism.

---

# 6. What Is I/O?

I/O means **Input/Output**.

Examples:

```text
Database
Network
Disk
File system
External API
Socket
User input
```

For a backend:

```text
Request
 ↓
Query PostgreSQL
 ↓
WAIT
 ↓
Database responds
 ↓
Continue
```

During that waiting period, the CPU may have very little useful work to do for that particular request.

---

# 7. I/O-Bound Work

A workload is **I/O-bound** when its performance is primarily limited by waiting for I/O.

Example:

```text
API
 ↓
Database
 ↓
WAIT 50ms
 ↓
External API
 ↓
WAIT 200ms
 ↓
File
 ↓
WAIT 100ms
```

The program spends a lot of time waiting.

The CPU isn't necessarily the bottleneck.

---

# 8. Common I/O-Bound Backend Operations

Examples:

```text
Database queries
HTTP requests
Reading files
Writing files
Calling payment APIs
Calling cloud services
Sending emails
Reading from queues
Writing to queues
Network communication
```

These are excellent candidates for concurrency.

---

# 9. Why Concurrency Helps I/O-Bound Work ⭐

Suppose you have:

```text
Request A
 ↓
Database
 ↓
WAIT 100ms
```

Instead of doing nothing during that time:

```text
Request A → waiting
                 ↓
Request B → processing
                 ↓
Request C → processing
```

The system keeps making progress.

Conceptually:

```text
WITHOUT CONCURRENCY

A: █████████████████
B:                  █████████████████
C:                                   █████████████████
```

With concurrency:

```text
WITH CONCURRENCY

A: ███ WAIT ███
B:    ███ WAIT █████
C:       ███ WAIT ███
```

The total completion time can be much lower.

---

# 10. Sequential I/O

Suppose you need information from three independent services:

```text
Service A → 100ms
Service B → 100ms
Service C → 100ms
```

Sequential:

```text
A
 ↓
100ms
 ↓
B
 ↓
100ms
 ↓
C
 ↓
100ms

≈ 300ms
```

If the calls are independent, concurrency can allow them to overlap:

```text
A ───────── 100ms
B ───────── 100ms
C ───────── 100ms

Total ≈ 100ms + overhead
```

This is one of the most important practical uses of concurrency in backend systems.

---

# 11. But Don't Parallelize Everything

Suppose:

```text
Task A
 ↓
Task B depends on A
 ↓
Task C depends on B
```

You cannot simply execute all three simultaneously.

```text
A → B → C
```

because:

```text
B needs A's result
C needs B's result
```

Concurrency is useful when work can actually overlap.

---

# 12. Independent vs Dependent Work

### Independent

```text
             ┌→ API A
Request ─────┼→ API B
             └→ API C
```

Can potentially run concurrently.

### Dependent

```text
Request
 ↓
A
 ↓
B
 ↓
C
```

Must respect the dependency chain.

---

# 13. CPU-Bound Work

A workload is **CPU-bound** when the CPU spends most of its time performing computations.

Examples:

```text
Image processing
Video encoding
Compression
Encryption
Hash calculations
Machine learning inference
Large mathematical calculations
Parsing huge datasets
Complex algorithms
```

Example:

```text
Image
 ↓
Resize
 ↓
Apply filters
 ↓
Compress
 ↓
Encode
```

The CPU is doing actual work rather than waiting for an external system.

---

# 14. Why Concurrency Alone Doesn't Solve CPU-Bound Problems

Suppose you have:

```text
CPU = 100% busy
```

Creating more concurrent tasks doesn't magically create more CPU capacity.

You may end up with:

```text
Task A ─┐
Task B ─┤
Task C ─┼→ Same CPU
Task D ─┤
Task E ─┘
```

The CPU still has to execute them.

The tasks may simply compete for CPU time.

---

# 15. Parallelism Helps CPU-Bound Work ⭐

Suppose:

```text
CPU = 4 cores
```

You have four independent CPU-heavy tasks:

```text
Task A → Core 1
Task B → Core 2
Task C → Core 3
Task D → Core 4
```

Now work can actually happen simultaneously.

Conceptually:

```text
Core 1: ███████████
Core 2: ███████████
Core 3: ███████████
Core 4: ███████████
```

That's where parallelism becomes valuable.

---

# 16. CPU-Bound Example

Suppose processing one image requires:

```text
1 second CPU time
```

You have:

```text
4 CPU cores
```

Potentially:

```text
Image 1 → Core 1
Image 2 → Core 2
Image 3 → Core 3
Image 4 → Core 4
```

Four images can be processed concurrently through actual parallel execution.

The real speedup depends on overhead, contention, algorithm, memory bandwidth, and how well the work can be parallelized.

---

# 17. A Critical Distinction

Remember:

```text
I/O-bound
→ Waiting is the problem
→ Concurrency helps keep CPU productive
```

```text
CPU-bound
→ Computation is the problem
→ Parallelism can use additional CPU cores
```

# 18. Event Loop and I/O

This is particularly important in backend development.

Languages/runtimes such as JavaScript commonly use an event-driven model.

Conceptually:

```text
             Event Loop
                 │
       ┌─────────┼─────────┐
       ↓         ↓         ↓
    Request A  Request B  Request C
       │         │         │
       ↓         ↓         ↓
      DB        API       File
       │         │         │
      WAIT      WAIT      WAIT
       │         │         │
       └─────────┼─────────┘
                 ↓
             Continue
```

While one operation is waiting for I/O, the runtime can work on other tasks.

---

# 19. Event Loop Mental Model

Think of the event loop as:

```text
Get work
 ↓
Start I/O
 ↓
Don't block unnecessarily
 ↓
Work on other tasks
 ↓
I/O completes
 ↓
Handle result
```

This is why event-driven systems can handle many concurrent I/O operations efficiently.

---

# 20. Important: Async Doesn't Mean Parallel

This is a common interview trap.

```text
async
≠
parallel
```

Asynchronous programming often means:

> **Don't block while waiting for an operation to complete.**

Parallelism means:

> **Actually execute multiple computations simultaneously.**

You can have:

```text
Async + single thread
```

without CPU parallelism.

---

# 21. Example: Async Database Requests

Suppose:

```javascript
const users = await getUsers();
```

The `await` does not necessarily mean:

```text
"Stop the entire server."
```

In an asynchronous runtime, the operation can be waiting for the database while other work continues.

Conceptually:

```text
Request A
 ↓
DB query
 ↓
WAIT

Event loop
 ↓
Request B
 ↓
Process B
```

When the DB responds:

```text
DB
 ↓
Result ready
 ↓
Resume Request A
```

# 22. CPU Work Can Block an Event Loop

This is extremely important for Node.js/backend interviews.

Suppose you execute a huge CPU-intensive loop:

```text
for (...)
    extremelyExpensiveCalculation();
```

If that work runs on the main event-loop thread:

```text
CPU-heavy task
      ↓
Event loop blocked
      ↓
New requests wait
      ↓
Latency increases
```

Even if the application is normally excellent at handling I/O concurrency.

---

# 23. Example

Imagine:

```text
Node.js server
```

receives:

```text
Request A → huge CPU calculation
```

Then:

```text
Request B
Request C
Request D
```

arrive.

If A monopolizes the event-loop thread:

```text
A ███████████████████
B                    █████
C                         █████
D                              █████
```

Latency for B, C and D increases.

A useful simplified model:

# 26. Threads

A thread is an execution path within a process.

Conceptually:

```text
Process
│
├── Thread 1
├── Thread 2
├── Thread 3
└── Thread 4
```

Multiple threads can allow multiple tasks to execute concurrently, and on multiple cores they can execute in parallel.

---

# 27. Processes

A process is an independently running program instance with its own address space.

Conceptually:

```text
Machine
│
├── Process A
│    └── Memory
│
├── Process B
│    └── Memory
│
└── Process C
     └── Memory
```

Multiple processes can also execute in parallel on multiple CPU cores.

---

# 28. Threads vs Processes

|               | Threads                             | Processes                    |
| ------------- | ----------------------------------- | ---------------------------- |
| Memory        | Usually shared within process       | Separate address spaces      |
| Communication | Easier but requires synchronization | IPC required                 |
| Overhead      | Generally lower                     | Generally higher             |
| Isolation     | Lower                               | Higher                       |
| Parallelism   | Yes, when supported/runtime allows  | Yes                          |
| Common use    | Concurrent/parallel tasks           | Workers, isolation, services |

The exact behavior depends heavily on the language/runtime.

---

# 29. Shared Memory

Threads within a process may share memory:

```text
Thread A ─┐
Thread B ─┼──→ Shared Memory
Thread C ─┘
```

This is powerful but dangerous.

Two threads might modify the same data simultaneously.

This creates concurrency problems.

---

# 30. Race Condition 🚨

A race condition occurs when the result depends on the timing/order of concurrent operations.

Example:

```text
balance = ₹100
```

Two requests arrive:

```text
Request A → withdraw ₹80
Request B → withdraw ₹80
```

Both read:

```text
balance = ₹100
```

Then both attempt the withdrawal.

Without proper synchronization:

```text
A → reads 100
B → reads 100

A → writes 20
B → writes 20
```

The system may incorrectly allow both operations.

---

# 31. Concurrency Doesn't Automatically Mean Safe

This is important.

Concurrency introduces problems such as:

```text
Race conditions
Deadlocks
Data corruption
Lost updates
Inconsistent state
```

Therefore concurrent systems need appropriate synchronization and data-consistency mechanisms.

---

# 32. Locks

A lock can protect shared resources.

Conceptually:

```text
Thread A
 ↓
Acquire lock
 ↓
Modify shared data
 ↓
Release lock
```

While A holds the lock:

```text
Thread B
 ↓
WAIT
```

This prevents certain classes of race conditions.

---

# 33. But Locks Have a Cost

Too much locking can reduce concurrency:

```text
Thread A ───── lock ─────
Thread B       WAIT
Thread C       WAIT
Thread D       WAIT
```

Now multiple cores may sit idle waiting for one shared resource.

So:

> **Concurrency requires balancing safety and parallelism.**

---

# 34. Deadlock

A deadlock occurs when tasks wait for each other indefinitely.

Example:

```text
Thread A
 ↓
Locks Resource 1
 ↓
Waits for Resource 2

Thread B
 ↓
Locks Resource 2
 ↓
Waits for Resource 1
```

Result:

```text
A → waiting for B
B → waiting for A
```

Nobody progresses.

---

# 35. Common Ways to Reduce Deadlocks

One strategy is to establish a consistent lock order.

For example:

```text
Always acquire:

Resource 1
 ↓
Resource 2
```

Never:

```text
Thread A:
1 → 2

Thread B:
2 → 1
```

Other approaches include:

```text
Timeouts
Reducing lock scope
Avoiding unnecessary shared state
Using higher-level concurrency primitives
```

---

# 36. Async Concurrency

You don't necessarily need threads to perform concurrent I/O.

For example:

```text
Start API A
Start API B
Start API C

Wait for all
```

Conceptually:

```text
A ────────────────┐
B ────────────────┼→ Results
C ────────────────┘
```

The runtime can manage the I/O operations concurrently.

---

# 37. Promise.all Mental Model

In JavaScript:

```javascript
const [a, b, c] = await Promise.all([
  getA(),
  getB(),
  getC()
]);
```

This is useful when:

```text
A
B
C
```

are independent operations.

Instead of:

```javascript
const a = await getA();
const b = await getB();
const c = await getC();
```

which waits sequentially.

---

# 38. But `Promise.all()` Isn't CPU Parallelism

This:

```javascript
Promise.all([
  expensiveCalculationA(),
  expensiveCalculationB()
]);
```

doesn't automatically mean:

```text
Core 1 → A
Core 2 → B
```

If both calculations execute on the same JavaScript thread, they can still block one another.

For CPU-heavy work, you need an execution model that actually provides CPU parallelism, such as workers or multiple processes.

# 39. Concurrency Limits

Unlimited concurrency can be dangerous.

Suppose:

```text
10,000 requests
```

each starts:

```text
10 database operations
```

You could create:

```text
100,000 DB operations
```

and overwhelm the database.

So we often need:

```text
Concurrency Limit
```

Example:

```text
Maximum 20 concurrent requests
```

or:

```text
Maximum 10 database operations
```

per worker.

# 41. Thread Pool

Many runtimes use a pool of worker threads for certain operations.

Conceptually:

```text
Incoming work
      ↓
   Thread Pool
 ┌────┼────┐
 ↓    ↓    ↓
 T1   T2   T3
```

Instead of creating unlimited threads:

```text

```

This controls resource consumption.

# 42. Why Unlimited Threads Are Bad

Every thread consumes resources.

Too many threads can cause:

```text
Memory overhead
Context switching
CPU contention
Scheduling overhead
```

Eventually:

```text
More threads
→ Less useful work
```

# 43. Context Switching

When the CPU switches between tasks:

```text
Task A
 ↓
Task B
 ↓
Task C
 ↓
Task A
```

the operating system/runtime has overhead.

This is called **context switching**.

A small amount is normal.

Too much can hurt performance.

---

# 44. CPU Saturation

Suppose:

```text
CPU utilization = 100%
```

Adding more CPU-bound work won't make the existing work faster.

You may need:

```text
Better algorithm
More CPU cores
Parallel workers
More instances
Batching
Caching
Less computation
```

depending on the bottleneck.

---

# 45. I/O Wait

Now imagine:

```text
CPU = 20%
```

but:

```text
Requests are slow
```

This could indicate the system spends a lot of time waiting for:

```text
Database
Network
External APIs
Disk
```

In such cases, adding CPU may accomplish very little.

You should investigate the I/O bottleneck.

---

# 46. How to Determine I/O-Bound vs CPU-Bound

Look at system behavior.

### CPU-bound indicators

```text
High CPU utilization
Low I/O wait
Long computation time
CPU profiler shows hotspots
```

### I/O-bound indicators

```text
Low/moderate CPU
High waiting time
Slow DB/network calls
Many pending requests
Connection pools saturated
```

Use measurements rather than guessing.

# 50. Fan-Out

When one request triggers multiple downstream requests:

```text
                  API
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
   Service A   Service B   Service C
```

this is called **fan-out**.

Fan-out can reduce latency when calls are independent.

But it can also multiply load.

If:

```text
1 API request
→ 10 downstream requests
```

then:

```text
10,000 API requests
→ 100,000 downstream requests
```

This is why concurrency needs capacity planning.

---

# 51. Fan-In

After parallel work completes:

```text
Service A ─┐
Service B ─┼→ Aggregate
Service C ─┘
```

the results are combined.

This is **fan-in**.

Common pattern:

```text
Fan-out
 ↓
Parallel work
 ↓
Fan-in
 ↓
Response
```

Possible strategies:

The answer depends on business requirements.

This connects to:

```text

```

# 58. Idempotency

An operation is idempotent if repeating it produces the same intended final effect.

For example:

```text
SET status = "cancelled"
```

can be designed to be idempotent.

Whereas:

```text
ADD ₹100
```

is not naturally idempotent.

Idempotency is extremely important when:

```text
Retries
Concurrent requests
Payments
Webhooks
Distributed systems
```

are involved.

# 🧠 Interview Mental Models

### What is concurrency?

> Concurrency is the ability to make progress on multiple tasks during overlapping periods, often by switching between tasks while others are waiting.

### What is parallelism?

> Parallelism is the simultaneous execution of multiple tasks, typically using multiple CPU cores or execution units.

### I/O-bound vs CPU-bound?

```text
I/O-bound
→ Waiting dominates

CPU-bound
→ Computation dominates
```

### What helps I/O-bound workloads?

```text
Concurrency
Async I/O
Connection pooling
Batching
Caching
```

### What helps CPU-bound workloads?

```text
Better algorithms
Parallelism
Worker threads/processes
More CPU cores
Horizontal scaling
```

### Does async mean parallel?

> No. Asynchronous execution primarily means not blocking while waiting. Parallelism means actual simultaneous execution.

### Why is CPU-heavy work dangerous on Node.js's event loop?

> Because CPU-intensive synchronous work can block the event-loop thread, preventing it from efficiently handling other requests and increasing latency.

### Why can't we create unlimited concurrent operations?

> Because every operation consumes resources such as memory, connections, CPU, and downstream capacity. Unlimited concurrency can overload the system.

### What is a race condition?

> A race condition occurs when the result depends on the timing or ordering of concurrent operations accessing shared state.

### What is a deadlock?

> A situation where concurrent tasks wait indefinitely for resources held by one another.

# ⚠️ Interview Traps

### ❌ "Concurrency means doing everything simultaneously."

Not necessarily.

Concurrency means multiple tasks can make progress during overlapping periods.

---

### ❌ "Concurrency and parallelism are the same."

No.

```text
Concurrency
→ Managing overlapping work

Parallelism
→ Simultaneous execution
```

---

### ❌ "Async means multithreading."

No.

Async programming can happen on a single thread.

---

### ❌ "`Promise.all()` makes JavaScript CPU operations parallel."

No.

It is useful for concurrent asynchronous operations, especially I/O.

CPU-heavy JavaScript on the same event-loop thread can still block execution.

---

### ❌ "More concurrent requests always means better performance."

No.

Eventually:

```text
More concurrency
 ↓
More resource consumption
 ↓
Contention
 ↓
Overload
 ↓
Worse performance
```

---

### ❌ "If CPU is low, the application isn't slow."

Wrong.

The application could be waiting for:

```text
Database
Network
External API
Disk
```

---

### ❌ "If CPU is high, add more concurrent tasks."

That can make things worse.

If CPU is already saturated, you need to investigate:

```text
Algorithm
Parallelism
Workers
CPU capacity
```

---

### ❌ "Locks solve concurrency."

Locks solve **some shared-state correctness problems**.

But excessive locking introduces:

```text
Contention
Deadlocks
Reduced throughput
```

# 🔥 Core Takeaways

* **Concurrency ≠ parallelism.**
* Concurrency is about managing multiple overlapping tasks.
* Parallelism is about actually executing multiple tasks simultaneously.
* **I/O-bound workloads are dominated by waiting.**
* **CPU-bound workloads are dominated by computation.**
* Concurrency is particularly valuable for I/O-bound backend workloads.
* Parallelism is particularly valuable for CPU-bound workloads.
* Async programming does not automatically mean multithreading or parallel execution.
* `Promise.all()` is useful for concurrent independent I/O operations, but does not automatically make CPU-heavy JavaScript parallel.
* Node.js can handle many concurrent I/O operations efficiently through its event-driven model.
* CPU-intensive synchronous work can block Node.js's event loop.
* CPU-heavy work can be moved to workers, processes, background jobs, or separate services.
* Unlimited concurrency can overwhelm your own system or downstream dependencies.
* **Concurrency limits are important.**
* Threads can share memory, which creates potential race conditions.
* Locks can protect shared state but can introduce contention and deadlocks.
* A race condition occurs when the result depends on the timing/order of concurrent operations.
* A deadlock occurs when tasks wait indefinitely for resources held by each other.
* Fan-out allows independent downstream operations to run concurrently, but multiplies load.
* Fan-in combines the results of concurrent operations.
* Timeouts, cancellation, backpressure, and rate limits are important companions to concurrency.
* Database concurrency is handled through mechanisms such as transactions, locks, and MVCC.
* Idempotency is especially important when concurrent requests and retries can repeat operations.
* **Always identify whether you're waiting or computing before deciding how to optimize.**

# 🎯 The One Question to Remember

When an interviewer gives you a performance problem, don't immediately say:

> **"I'll use multithreading."**

First ask:

```text
                 WHAT IS THE SYSTEM DOING?
                         │
              ┌──────────┴──────────┐
              ↓                     ↓
           WAITING              COMPUTING
              │                     │
              ↓                     ↓
          I/O-BOUND              CPU-BOUND
              │                     │
              ↓                     ↓
        CONCURRENCY              PARALLELISM
```

Then ask:

```text
What resource is limiting us?
```

Because **the right concurrency model depends on the bottleneck.**
