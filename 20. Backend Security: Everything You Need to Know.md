# 20. Backend Security: Everything You Need to Know 🔐

> **Security is not a feature you add after building the backend. It is a mindset you apply whenever data crosses a boundary.**
>
> The central idea of this chapter is simple:
>
> **What assumption am I making, and what happens if that assumption is wrong?**
>
> Attackers don't use your application the way you expect a normal user to. They modify requests, parameters, headers, tokens, inputs, and URLs. The backend must therefore treat boundaries and external input as potential attack surfaces. ([Use Transcribe][1])
>
> The video covers injection attacks, authentication and authorization, XSS, secrets management, security misconfiguration, security headers, and layered defenses. ([Use Transcribe][1])

---

# 1. What Does Backend Security Mean?

Backend security is about protecting:

```text
Users
  ↓
API
  ↓
Application
  ↓
Database
  ↓
Infrastructure
  ↓
External Services
```

against:

```text
Unauthorized access
Data theft
Data modification
Service disruption
Code execution
Credential theft
Privilege escalation
```

Security isn't limited to the backend code itself.

There are several layers:

```text
Security
│
├── Browser / Client Security
├── Network Security
├── Server / OS Security
└── Application / Backend Security
```

This chapter focuses primarily on the **backend/application layer**, while recognizing that security is a much broader domain. ([Use Transcribe][1])

---

# 2. The Most Important Security Mindset ⭐

The most useful question in this entire chapter is:

> **Where did the developer make an assumption?**

For example:

```text
"I assume the user input is clean."

"I assume the user is who they claim to be."

"I assume this request came from my frontend."

"I assume nobody will modify this parameter."

"I assume nobody knows this URL."

"I assume this token cannot be tampered with."
```

An attacker specifically tries to break these assumptions.

So instead of thinking:

```text
Normal User
   ↓
Correct Request
   ↓
Backend
```

think:

```text
Attacker
   ↓
Can modify ANY request
   ↓
Can send ANY parameters
   ↓
Can call APIs directly
   ↓
Can replay requests
   ↓
Can manipulate inputs
```

This mindset is more valuable than memorizing a list of vulnerabilities.

---

# 3. Security Is About Boundaries ⭐⭐⭐

One of the strongest mental models from this chapter is:

> **Pay special attention whenever data crosses a boundary.**

Examples:

```text
User input
     ↓
SQL query
```

Boundary:

```text
Application → SQL language
```

---

Another:

```text
User content
     ↓
HTML
```

Boundary:

```text
User data → Browser executable content
```

---

Another:

```text
Request
     ↓
Protected resource
```

Boundary:

```text
Untrusted user → Authorized resource
```

---

Another:

```text
Application
     ↓
Operating system command
```

Boundary:

```text
Application data → OS command
```

The pattern is:

```text
UNTRUSTED DATA
      ↓
   BOUNDARY
      ↓
INTERPRETATION
```

That's where you need to be careful.

# 4. Injection Attacks

Injection attacks happen when data supplied by an attacker is interpreted as part of a command or language.

The fundamental problem:

```text
DATA
+
CODE
=
DANGEROUS
```

The application accidentally allows user-controlled data to become executable instructions.

Common examples:

```text
SQL Injection
NoSQL Injection
Command Injection
LDAP Injection
Template Injection
```

---

# 5. SQL Injection

Suppose you construct SQL using string concatenation:

```javascript
const query =
  "SELECT * FROM users WHERE email = '" + email + "'";
```

You intended:

```text
email
↓
DATA
```

But an attacker may provide specially crafted input that changes the meaning of the SQL statement.

The problem is:

```text
User Input
     ↓
String Concatenation
     ↓
SQL Code
```

The input has crossed into the SQL language without proper separation.

---

# 6. Parameterized Queries ⭐

Instead of constructing SQL manually:

```text
SQL + user input
```

use parameterized queries:

```text
SQL statement
      +
parameters
```

Conceptually:

```sql
SELECT * FROM users WHERE email = $1
```

and separately:

```text
$1 = user@example.com
```

Now the database knows:

```text
SQL → Code
$1  → Data
```

The attacker cannot simply turn the parameter into SQL syntax.

Parameterized operations are one of the core defenses emphasized in the source. ([Use Transcribe][1])

---

# 7. The General Rule for Injection

Don't construct commands through string concatenation when the platform provides parameterized APIs.

This applies beyond SQL.

Think:

```text
Database queries
OS commands
File operations
Template systems
Search queries
```

Whenever:

```text
User Input
      ↓
Another Language
```

ask:

> **Can this input become code?**

---

# 8. Authentication vs Authorization

These two are frequently confused.

### Authentication

> **Who are you?**

Example:

```text
Login
 ↓
Verify credentials
 ↓
User = Yusuf
```

### Authorization

> **What are you allowed to do?**

Example:

```text
User = Yusuf
Role = USER

Can read own profile
Can edit own profile

Cannot delete another user's account
Cannot access admin dashboard
```

Think:

```text
Authentication
→ Identity

Authorization
→ Permission
```

---

# 9. Stateful Authentication

In a stateful authentication system:

```text
Login
 ↓
Server verifies credentials
 ↓
Server creates session
 ↓
Session stored server-side
 ↓
Session ID sent to client
```

The client receives something like:

```text
session_id = random_cryptographic_value
```

Usually stored in a cookie.

---

# 10. Stateful Authentication Flow

```text
                LOGIN

Client ─────────────────→ Server
                           │
                           ↓
                    Verify password
                           │
                           ↓
                    Create session
                           │
                           ↓
                  Store session
                           │
Client ←── session cookie ─┘
```

Then:

```text
Client
  ↓
Request + session cookie
  ↓
Server
  ↓
Look up session
  ↓
Identify user
  ↓
Authorize request
```

---

# 11. Advantages of Stateful Sessions

Because the server stores the session:

```text
Session
  ↓
User
  ↓
Server-side state
```

you can easily revoke a session.

For example:

```text
User clicks "Log out of all devices"
       ↓
Invalidate sessions
       ↓
Existing session IDs stop working
```

This can be an important advantage.

---

# 12. Stateful Authentication Tradeoff

The server needs to maintain session state.

That can introduce:

```text
Session storage
Redis / Database
Session cleanup
Session replication
Scaling considerations
```

In a distributed system:

```text
Load Balancer
 ├── Server A
 ├── Server B
 └── Server C
```

all servers need access to the relevant session state.

A shared session store can solve this:

```text
Server A ─┐
Server B ─┼──→ Redis
Server C ─┘
```

---

# 13. Stateless Authentication with JWT

Another approach is a signed JWT.

Conceptually:

```text
Login
 ↓
Verify credentials
 ↓
Create JWT
 ↓
Sign JWT
 ↓
Send JWT to client
```

The JWT contains claims such as:

```text
userId
role
issuedAt
expiry
```

The server signs it using a secret/private key depending on the signing algorithm.

---

# 14. JWT Verification

On subsequent requests:

```text
Client
 ↓
Authorization: Bearer <JWT>
 ↓
Server
 ↓
Verify signature
 ↓
Validate claims
 ↓
Identify user
 ↓
Authorize request
```

The server can verify the token without looking up a session record for every request.

This is one reason JWT-based stateless authentication can simplify horizontal scaling. ([Use Transcribe][1])

---

# 15. JWT Is Signed, Not Encrypted

This is extremely important.

A JWT's payload is generally **encoded**, not automatically encrypted.

Therefore:

```text
JWT
 ↓
Decode payload
 ↓
Read claims
```

is possible.

The signature protects integrity:

```text
Original payload
      ↓
Signature
      ↓
Server verifies
```

If someone modifies the payload:

```text
Modified payload
      ↓
Signature no longer matches
      ↓
❌ Reject
```

---

# 16. Don't Put Sensitive Information in JWTs

Because the payload may be readable by the client, don't put secrets inside it.

Bad:

```json
{
  "password": "...",
  "creditCard": "...",
  "secretKey": "..."
}
```

Instead, only include information that is appropriate to expose in the token.

---

# 17. JWT Storage

A major security question is:

> **Where should the client store the token?**

Common options include:

```text
Memory
Local Storage
Cookies
```

Each has tradeoffs.

---

# 18. Local Storage and XSS

Local Storage is accessible to JavaScript.

If an attacker successfully executes JavaScript through an XSS vulnerability:

```text
Malicious JS
   ↓
localStorage.getItem("token")
   ↓
Token stolen
```

Therefore storing authentication tokens in browser-accessible storage can increase the impact of XSS.

The source explicitly discusses this tradeoff. ([Use Transcribe][1])

---

# 19. Cookies

Authentication information can also be stored in cookies with appropriate security attributes.

Important cookie attributes include:

```text
HttpOnly
Secure
SameSite
```

### HttpOnly

Prevents ordinary JavaScript from reading the cookie.

Useful against token theft through JavaScript.

### Secure

Cookie should only be transmitted over HTTPS.

### SameSite

Controls cross-site cookie behavior and can help mitigate CSRF depending on the configuration and application design.

---

# 20. Authentication Is Not Authorization

A valid token does not automatically mean:

```text
"User can access everything."
```

For example:

```text
User 123
 ↓
Authenticated ✅
 ↓
GET /users/456
```

The server still needs to ask:

```text
Is user 123 allowed to access user 456?
```

Authentication answers:

```text
Who?
```

Authorization answers:

```text
Allowed to do what?
```

---

# 21. Broken Access Control

Imagine:

```http
GET /users/123/invoices
```

The backend checks:

```text
Is user logged in?
```

Yes.

Then returns invoices.

But what if:

```text
GET /users/456/invoices
```

also works?

The problem isn't authentication.

The user is authenticated.

The problem is **authorization**.

---

# 22. Broken Object-Level Authorization

This happens when the application fails to verify whether the current user is allowed to access a particular resource.

For example:

```text
GET /orders/123
```

The application verifies:

```text
User is authenticated
```

but forgets:

```text
Order 123 belongs to this user
```

That's a critical security problem.

---

# 23. Authorization Must Happen at the Point of Access ⭐

A powerful principle from the source:

> **Verify authorization at the actual point where the resource is accessed.**

Suppose:

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

Checking authorization only in the controller may be insufficient if another code path can call the service/repository directly.

Think:

```text
Who is requesting?
      +
What resource?
      +
What operation?
      +
Is this operation allowed?
```

at the actual access boundary.

---

# 24. Centralized Authorization

Authorization logic should not be scattered randomly throughout the codebase.

Bad:

```text
Controller A → authorization
Controller B → maybe authorization
Service C → different authorization
Controller D → forgot authorization
```

Better:

```text
Request
  ↓
Authorization Layer
  ↓
Permission decision
  ↓
Resource access
```

Centralization makes the policy easier to reason about and maintain.

---

# 25. Default Deny ⭐

A very useful security principle:

> **If something isn't explicitly allowed, deny it.**

Bad approach:

```text
Allow everything
 ↓
Block a few dangerous cases
```

Better:

```text
Deny everything
 ↓
Explicitly allow permitted actions
```

Why?

Suppose tomorrow you add:

```text
POST /admin/export-users
```

If your default policy is deny:

```text
New endpoint
 ↓
Not explicitly permitted
 ↓
❌ Denied
```

You must consciously grant access.

This is much safer than accidentally exposing new functionality. ([Use Transcribe][1])

---

# 26. Security Through Obscurity

A dangerous assumption:

```text
Nobody knows this URL.
```

Therefore:

```text
/admin/export-users
```

is supposedly secure.

No.

Attackers can:

```text
Inspect frontend code
Observe network requests
Discover URLs
Guess endpoints
Read documentation
Analyze traffic
```

A secret URL is not authorization.

Security should come from:

```text
Authentication
+
Authorization
+
Validation
+
Security controls
```

not from hiding endpoints.

---

# 27. XSS — Cross-Site Scripting

XSS happens when an attacker manages to get malicious JavaScript executed in another user's browser in the context of your application. ([Use Transcribe][1])

Conceptually:

```text
Attacker input
      ↓
Application stores/renders it
      ↓
Victim opens page
      ↓
Browser executes malicious script
```

---

# 28. Why XSS Is Dangerous

An XSS attack may allow malicious JavaScript to:

```text
Read page content
Modify page content
Perform actions as the victim
Steal accessible browser data
Interact with APIs
```

The exact impact depends on the application's architecture and browser security controls.

---

# 29. XSS and Trust Boundaries

The core problem:

```text
User-controlled data
       ↓
HTML / JavaScript context
```

The application accidentally treats:

```text
DATA
```

as:

```text
CODE
```

Again:

```text
Data
 ↓
Boundary
 ↓
Code interpretation
```

This is the same fundamental pattern as injection attacks.

---

# 30. Preventing XSS

Common defenses include:

```text
Output encoding
Input validation
Safe rendering APIs
Content Security Policy
Avoiding unsafe HTML injection
Sanitization when HTML is genuinely required
```

The important point is:

> **Don't blindly trust user-controlled content just because it came from your own database.**

Data stored in your database may originally have come from an attacker.

---

# 31. Content Security Policy

**CSP (Content Security Policy)** allows a website to specify which sources of content/scripts the browser is permitted to load or execute.

Conceptually:

```text
Browser
   ↓
CSP policy
   ↓
Allow trusted scripts
   ↓
Block unexpected scripts
```

CSP is a **defense-in-depth** mechanism.

It should not replace safe application design.

---

# 32. CSRF

**Cross-Site Request Forgery** involves tricking a user's browser into making an unwanted authenticated request to a site where the user is already authenticated.

Conceptually:

```text
Victim logged into bank
       ↓
Visits malicious website
       ↓
Browser sends authenticated request
       ↓
Bank receives request
```

The attack relies heavily on how browsers automatically attach authentication credentials, especially cookies.

---

# 33. CSRF Defenses

Depending on the architecture, defenses can include:

```text
SameSite cookies
CSRF tokens
Origin checks
Referer checks where appropriate
Avoiding unsafe cross-site credential behavior
```

The correct defense depends on the authentication mechanism and application architecture.

---

# 34. CORS Is Not Authentication

A very common misunderstanding:

```text
CORS
≠
Authentication
```

CORS controls which browser origins are permitted to make certain cross-origin requests.

It does **not** prevent:

```text
curl
Postman
custom scripts
another backend
```

from calling your API.

Your backend must still implement:

```text
Authentication
Authorization
Validation
```

independently.

---

# 35. Rate Limiting

Attackers can repeatedly hit endpoints.

Examples:

```text
Login
OTP verification
Password reset
Search
Expensive APIs
```

Without rate limiting:

```text
Attacker
 ↓
10,000 requests/sec
 ↓
Backend
 ↓
Resource exhaustion
```

Rate limiting can restrict request frequency.

For example:

```text
100 requests / minute / IP
```

or more appropriately:

```text
Login:
5 attempts / minute / account
```

depending on the use case.

---

# 36. Brute Force Attacks

Suppose a login endpoint allows unlimited attempts:

```text
password1
password2
password3
...
```

An attacker can automate guesses.

Defenses can include:

```text
Rate limiting
Account lockout / progressive delays
Strong password hashing
MFA
Credential-stuffing detection
Monitoring
```

Be careful with lockouts because attackers can sometimes abuse them to deny service to legitimate users.

---

# 37. Password Storage

Never store:

```text
password = "mypassword123"
```

in plaintext.

Instead:

```text
Password
   ↓
Password hashing function
   ↓
Stored password hash
```

During login:

```text
Submitted password
       ↓
Password verification
       ↓
Compare against stored hash
```

---

# 38. Hashing ≠ Encryption

### Hashing

```text
Input
 ↓
Hash
```

Designed to be one-way.

### Encryption

```text
Plaintext
 ↓
Encryption
 ↓
Ciphertext
 ↓
Decryption
 ↓
Plaintext
```

Encryption is reversible with the appropriate key.

Passwords should generally use password-specific hashing algorithms rather than reversible encryption.

---

# 39. Salting

A salt is unique random data combined with a password before hashing.

Conceptually:

```text
Password
   +
Random Salt
   ↓
Password Hash
```

Why?

Without salts:

```text
password123
 ↓
same hash everywhere
```

With unique salts:

```text
password123 + saltA → hashA
password123 + saltB → hashB
```

This makes precomputed attacks such as rainbow tables less useful.

The source explicitly discusses why hashing alone isn't enough for password security. ([Use Transcribe][1])

---

# 40. Rainbow Tables

A rainbow table is a precomputed collection of password/hash relationships.

If many passwords use unsalted hashing:

```text
password123
 ↓
known hash
```

attackers can use precomputed data to speed up password recovery.

Unique salts make this significantly harder because each password hash has a different salt.

---

# 41. Secure Password Hashing

Use established password-hashing algorithms rather than inventing your own.

Examples include:

```text
Argon2
bcrypt
scrypt
```

Don't create:

```text
SHA256(password)
```

and assume you've built a secure password-storage system.

Password hashing needs properties specifically designed to make large-scale guessing expensive.

---

# 42. Secrets Management 🔑

Secrets include:

```text
Database passwords
API keys
JWT signing secrets
Encryption keys
OAuth secrets
Cloud credentials
Private keys
```

Never put them directly in source code.

Bad:

```javascript
const jwtSecret = "super-secret-key";
```

Then:

```text
git push
```

Now the secret can exist in:

```text
Repository
Git history
Backups
Forks
CI systems
```

---

# 43. Environment Variables

A basic approach is:

```text
Application
      ↓
Environment
      ↓
SECRET_VALUE
```

For example:

```text
JWT_SECRET=...
DATABASE_URL=...
```

The source specifically recommends keeping secrets outside the source code, using environment variables or an external secrets mechanism. ([Heuristica][2])

For production systems, dedicated secret-management systems are often preferable.

---

# 44. Secret Rotation

Secrets shouldn't necessarily live forever.

Example:

```text
Old API key
    ↓
Create new key
    ↓
Deploy new key
    ↓
Verify
    ↓
Revoke old key
```

This reduces the impact if a credential is compromised.

---

# 45. Security Misconfiguration

Sometimes the code is correct but the system is configured incorrectly.

Examples:

```text
Debug mode enabled
Default passwords
Exposed admin interfaces
Open storage buckets
Overly permissive permissions
Verbose error messages
Missing security headers
Improper CORS configuration
Secrets exposed in logs
```

Security is therefore not only about writing secure code.

It is also about:

> **How the system is deployed and operated.**

Security misconfiguration is recognized as a major application-security category. ([Google for Developers][3])

---

# 46. Don't Leak Internal Errors

Bad API response:

```json
{
  "error": "Postgres connection failed at 10.2.4.13:5432 using password xyz..."
}
```

The client doesn't need internal implementation details.

Better:

```json
{
  "error": "Internal server error"
}
```

while the server logs the detailed diagnostic information securely.

---

# 47. Security Headers

Security-related HTTP headers can provide additional browser protections.

Examples include:

```text
Content-Security-Policy
Strict-Transport-Security
X-Content-Type-Options
```

Depending on the application, additional headers/policies may be appropriate.

These are defense-in-depth mechanisms, not substitutes for secure application logic.

---

# 48. HTTPS / TLS

Never assume the network is trustworthy.

Without encryption:

```text
Client
   ↓
Internet
   ↓
Server
```

traffic may be exposed to interception.

With HTTPS:

```text
Client
   ↓
Encrypted TLS connection
   ↓
Server
```

TLS protects data in transit and provides server authentication through certificates.

---

# 49. Man-in-the-Middle Attacks

Conceptually:

```text
Client ─────→ Attacker ─────→ Server
```

If traffic isn't properly protected, an attacker may be able to observe or manipulate communication.

HTTPS/TLS helps prevent this by providing:

```text
Encryption
Integrity
Authentication
```

# 50. Input Validation

This connects directly to your previous **Validation and Transformation** chapter.

Every external input should be treated as untrusted.

Sources include:

```text
Request body
Query parameters
Path parameters
Headers
Cookies
Uploaded files
Webhooks
Third-party API responses
```

Validate at the boundary.

---

# 51. Validation as the First Security Layer

A useful architecture:

```text
Incoming Request
       ↓
Authentication
       ↓
Validation
       ↓
Authorization
       ↓
Business Logic
       ↓
Database
```

The validation layer should ensure the data has the expected structure and constraints before deeper application logic processes it.

The source explicitly emphasizes strict validation at the backend boundary. ([Use Transcribe][1])

---

# 52. Defense in Depth ⭐

Never rely on one security mechanism.

For example:

```text
Input Validation
       ↓
Parameterized Queries
       ↓
Authentication
       ↓
Authorization
       ↓
Rate Limiting
       ↓
Security Headers
       ↓
Monitoring
```

If one layer fails:

```text
Layer 1 ❌
   ↓
Layer 2
   ↓
Layer 3
```

you still have additional defenses.

---

# 53. Least Privilege

A component should have only the permissions it actually needs.

Bad:

```text
Backend
 ↓
Database superuser
```

Better:

```text
Backend
 ↓
Application DB user
 ↓
Only required tables/operations
```

Similarly:

```text
Service A
 ↓
Only required API permissions
```

not:

```text
Service A
 ↓
Full access to everything
```

---

# 54. Defense in Depth + Least Privilege

These principles work together.

### Defense in depth

> Have multiple independent layers of protection.

### Least privilege

> Give each component the minimum permissions required.

Together:

```text
Attacker
   ↓
Validation
   ↓
Authentication
   ↓
Authorization
   ↓
Least-privileged service
   ↓
Restricted database
```

---

# 55. Secure Defaults

A secure system should start from:

```text
DENY
```

rather than:

```text
ALLOW
```

Examples:

```text
New endpoint
→ protected by default

New database user
→ minimum privileges

New bucket
→ private by default
```

Secure defaults reduce accidental exposure.

# 56. Dependency Security

Your code isn't the only code running in your application.

You also depend on:

```text
npm packages
Python packages
Go modules
Frameworks
OS libraries
Docker images
```

A vulnerability in a dependency can become a vulnerability in your application.

Therefore:

```text
Dependencies
 ↓
Updates
 ↓
Vulnerability scanning
 ↓
Remove unnecessary packages
```

Dependency security is part of the modern application-security lifecycle. ([Microsoft][4])

---

# 57. Don't Trust the Frontend

This is a major backend principle.

Suppose the frontend sends:

```json
{
  "role": "admin"
}
```

Never assume:

```text
Frontend says admin
→ user is admin
```

An attacker can simply modify the request:

```text
role=user
```

to:

```text
role=admin
```

The backend must determine authorization independently.

---

# 58. Never Trust Hidden Fields

Suppose your frontend hides:

```text
isAdmin
```

That doesn't provide security.

An attacker can manually send:

```json
{
  "isAdmin": true
}
```

The backend must enforce:

```text
Who is this user?
What permissions do they have?
What resource are they accessing?
```

---

# 59. Client-Side Validation Is Not Security

Frontend validation:

```text
Email must be valid
Password must be 8 characters
```

is useful for UX.

But attackers can bypass it:

```text
Postman
curl
Custom script
Modified frontend
```

Therefore:

```text
Frontend validation
→ UX

Backend validation
→ Security + correctness
```

# 60. Request Replay

Suppose an attacker captures a valid request:

```text
POST /transfer
Authorization: ...
amount=1000
```

and sends it again.

Depending on the operation, the server may perform the action twice.

Sensitive operations may need mechanisms such as:

```text
Idempotency keys
Unique transaction IDs
Replay protection
Expiration
Nonce mechanisms
```

This becomes especially important for:

```text
Payments
Transfers
Orders
Webhook processing
```

For example:

# 62. Security and Error Handling

Your previous chapter covered error handling.

Security adds another requirement:

> **Errors should be useful to developers without unnecessarily helping attackers.**

Bad:

```text
"User exists but password is incorrect."
```

This can help attackers enumerate accounts.

Better:

```text
"Invalid credentials."
```

Internally:

# 🧠 Interview Mental Models

### What is the most important security mindset?

> **Question assumptions. Treat external input as untrusted and pay special attention whenever data crosses a trust or interpretation boundary.**

---

### Authentication vs authorization?

```text
Authentication
→ Who are you?

Authorization
→ What are you allowed to do?
```

---

### What is SQL injection?

> An attack where untrusted input changes the meaning of a database query because application data was incorrectly combined with SQL code.

---

### How do you prevent SQL injection?

> Use parameterized queries/prepared statements rather than constructing SQL through string concatenation, and validate input appropriately.

---

### Why isn't JWT encrypted by default?

> JWTs are commonly signed for integrity but their payload is generally readable. Therefore sensitive secrets should not be placed inside the token.

---

### What is broken access control?

> When an authenticated user can perform an action or access a resource they are not authorized to access.

---

### What is default deny?

> Access is denied unless a policy explicitly grants the required permission.

---

### What is XSS?

> A vulnerability where attacker-controlled content causes malicious JavaScript to execute in another user's browser within the application's context.

---

### Why isn't CORS authentication?

> CORS is a browser cross-origin access control mechanism. It does not stop non-browser clients from calling an API and does not establish user identity or permissions.

---

### Why hash passwords?

> Passwords should not be stored in reversible form. Password hashing provides a one-way representation that can be verified without storing the original password.

---

### Why salt passwords?

> Unique salts prevent identical passwords from producing identical hashes and make precomputed attacks such as rainbow tables much less effective.

---

### What is defense in depth?

> Using multiple independent security controls so that failure of one layer doesn't automatically compromise the system.

# ⚠️ Interview Traps

### ❌ "The frontend validates the input, so the backend doesn't need to."

Wrong.

```text

→ UX

Backend
→ Security boundary
```

---

### ❌ "The user can't access the admin button."

That isn't authorization.

The user can simply call the API directly.

---

### ❌ "Nobody knows the admin endpoint."

Security through obscurity is not authorization.

---

### ❌ "JWTs are encrypted."

Not necessarily.

Usually:

```text
JWT
→ encoded + signed
```

not:

```text
JWT
→ encrypted
```

---

### ❌ "CORS prevents attackers from calling the API."

No.

CORS primarily controls browser cross-origin behavior.

Attackers can still use:

```text
curl
Postman
Scripts
Their own backend
```

---

### ❌ "Hashing means SHA-256."

Hashing is a general concept.

Password storage needs a password-specific hashing strategy designed to resist guessing attacks.

```text
Authentication
+
Authorization
+
Parameterized operations
+
Least privilege
+
Rate limiting
+
Secure configuration
+
Monitoring
```

# 🔥 Core Takeaways

* **Security is a mindset, not a checklist you finish once.**
* The most useful question is: **"What assumption did the developer make?"**
* Attackers can modify requests, parameters, headers, URLs, and client-side behavior.
* Pay special attention whenever **data crosses a boundary**.
* Injection occurs when untrusted data crosses into a language or command context and is interpreted as code.
* Use **parameterized queries** rather than string concatenation.
* Authentication answers **"Who are you?"**
* Authorization answers **"What are you allowed to do?"**
* A valid authentication token does not automatically grant access to every resource.
* Authorization should be enforced at the **actual point of resource access**.
* Use **default deny**: anything not explicitly permitted should be denied.
* Hiding URLs or admin interfaces is not a security mechanism.
* JWTs are commonly signed for integrity but their payload should not be treated as secret.
* XSS occurs when attacker-controlled content becomes executable JavaScript in another user's browser.
* CSRF exploits authenticated browser requests; appropriate defenses depend on the authentication architecture.
* CORS is **not authentication**.
* Passwords should be stored using appropriate password-hashing algorithms, with unique salts.
* Never hard-code secrets or commit them to Git.
* Use secure secret-management mechanisms in production.
* Security misconfiguration can be just as dangerous as insecure application code.
* Use security headers and policies as **defense in depth**.
* Apply the **principle of least privilege** to users, services, databases, and credentials.
* Validate input at the backend boundary even when the frontend already validates it.
* Rate-limit sensitive endpoints such as authentication and password-reset flows.
* Security events should be observable through logs, metrics, and alerts.
* Security requires **multiple layers**, not one magical protection.

> ### The interview-level mental model
>
> Don't say:
>
> **"I'll use JWT, validate inputs, and add CORS."**
>
> Say:
>
> **"I treat every external input and every trust-boundary crossing as untrusted. At the API boundary I'd validate and normalize inputs, use parameterized operations for database and system interactions, authenticate the caller, and enforce authorization at the point where the protected resource is accessed. I'd follow default-deny and least-privilege principles, keep secrets outside source control, use secure cookie/TLS policies where applicable, protect sensitive endpoints with rate limiting, and use security headers and monitoring as defense in depth. Most importantly, I'd continuously question what assumptions the application makes about identity, input, and trust."**
>
> **That mindset is more valuable than memorizing the OWASP Top 10.** ([Use Transcribe][1])
