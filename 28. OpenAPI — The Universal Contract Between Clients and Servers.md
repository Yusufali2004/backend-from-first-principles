# 28. OpenAPI — The Universal Contract Between Clients and Servers 🔌

> **OpenAPI is a standard way to describe an HTTP API so that humans and machines can understand how the API works without reading the implementation code.**

Think of it as a **contract** between:

```text
Client
   ↕
API Contract
   ↕
Server
```

The video focuses on OpenAPI as the universal contract between clients and servers.

---

# 1. The Problem OpenAPI Solves ⭐⭐⭐

Imagine you build a backend API.

```http
POST /users
```

A frontend developer needs to know:

```text
What URL?
What HTTP method?
What headers?
What request body?
What fields are required?
What response comes back?
What errors are possible?
```

Without documentation, they may need to ask the backend developer.

```text
Frontend Developer
       ↓
"How do I call this API?"
       ↓
Backend Developer
       ↓
"Wait, let me check the code..."
```

This does not scale.

OpenAPI solves this by creating a machine-readable contract.

```text
                OpenAPI Specification
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
       Frontend       Backend       Tools
          │             │             │
          ↓             ↓             ↓
       Client         Server       Docs/SDKs
```

---

# 2. What Is OpenAPI? ⭐⭐⭐

OpenAPI is a specification for describing HTTP APIs.

It can describe:

```text
Endpoints
HTTP methods
Parameters
Request bodies
Responses
Authentication
Schemas
Errors
Content types
```

Example:

```yaml
openapi: 3.0.0

info:
  title: User API
  version: 1.0.0

paths:
  /users:
    get:
      responses:
        "200":
          description: Successful response
```

This tells tools:

```text
There is a GET /users endpoint.
```

---

# 3. OpenAPI Is a Specification, Not a Framework ⭐⭐⭐

Important distinction:

```text
OpenAPI
   ↓
Specification / Standard
```

It is not:

```text
Express
FastAPI
Spring Boot
Django
```

Those are frameworks.

You can use OpenAPI with many backend technologies.

```text
                 OpenAPI
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
    Node.js       Python        Java
    Express       FastAPI       Spring
```

---

# 4. API Contract ⭐⭐⭐

An API contract defines what clients and servers agree upon.

For example:

```text
POST /users
```

Request:

```json
{
  "name": "Yusuf",
  "email": "yusuf@example.com"
}
```

Response:

```json
{
  "id": 101,
  "name": "Yusuf",
  "email": "yusuf@example.com"
}
```

The contract specifies:

```text
Endpoint
Method
Request structure
Response structure
Status codes
```

---

# 5. Why Call It a Contract?

Imagine two teams:

```text
Team A
Frontend
```

and:

```text
Team B
Backend
```

The frontend team shouldn't need to know how the backend is implemented.

They only need to know:

```text
What goes in?
What comes out?
```

So:

```text
Implementation
      ↓
    Hidden
      │
      ↓
     API
      │
      ↓
   Contract
      │
      ↓
    Client
```

This is abstraction.

# 7. `openapi`

This specifies the OpenAPI version.

```yaml
openapi: 3.0.0
```

Conceptually:

```text
OpenAPI Document
      ↓
Which specification version?
      ↓
3.x
```

# 8. `info`

Describes the API itself.

```yaml
info:
  title: User API
  description: API for managing users
  version: 1.0.0
```

This provides metadata.

---

# 9. `servers`

Defines where the API is available.

```yaml
servers:
  - url: https://api.example.com
```

You can define multiple environments:

```yaml
servers:
  - url: https://api.example.com
    description: Production

  - url: https://staging-api.example.com
    description: Staging
```

Now consumers know where the API exists.

---

# 10. `paths` ⭐⭐⭐

The `paths` section describes API endpoints.

Example:

```yaml
paths:
  /users:
    get:
      responses:
        "200":
          description: Success
```

This represents:

```http
GET /users
```

You can define multiple HTTP methods:

```yaml
paths:
  /users:
    get:
      ...

    post:
      ...

    put:
      ...

    delete:
      ...
```

# 14. Path Parameters ⭐⭐⭐

Suppose you have:

```http
GET /users/123
```

The `123` is a path parameter.

OpenAPI:

```yaml
/users/{id}:
  get:
    parameters:
      - name: id
        in: path
        required: true
        schema:
          type: integer
```

The `{id}` is dynamic.

```text
/users/{id}
       ↓
/users/123
/users/456
/users/789
```

---

# 15. Query Parameters ⭐⭐⭐

Example:

```http
GET /users?page=2&limit=20
```

OpenAPI:

```yaml
parameters:
  - name: page
    in: query
    schema:
      type: integer

  - name: limit
    in: query
    schema:
      type: integer
```

Difference:

```text
Path Parameter
/users/{id}

Query Parameter
/users?page=2
```

---

# 16. Headers

APIs may require headers.

Example:

```http
Authorization: Bearer token
```

OpenAPI can describe these requirements.

```yaml
parameters:
  - name: X-Request-ID
    in: header
    required: false
    schema:
      type: string
```

---

# 17. Request Body ⭐⭐⭐

Consider:

```http
POST /users
Content-Type: application/json
```

Body:

```json
{
  "name": "Yusuf",
  "email": "yusuf@example.com"
}
```

OpenAPI:

```yaml
requestBody:
  required: true
  content:
    application/json:
      schema:
        type: object
        properties:
          name:
            type: string
          email:
            type: string
```

Now the API contract describes exactly what the client should send.

---

# 18. Schemas ⭐⭐⭐

Schemas define the structure of data.

Example:

```yaml
components:
  schemas:
    User:
      type: object
      required:
        - name
        - email
      properties:
        id:
          type: integer

        name:
          type: string

        email:
          type: string
```

Conceptually:

```text
User
├── id       → integer
├── name     → string
└── email    → string
```

---

# 19. Reusable Schemas

Instead of repeating:

```yaml
type: object
properties:
  id:
    type: integer
  name:
    type: string
```

everywhere, define it once.

```yaml
components:
  schemas:
    User:
      ...
```

Then reference it:

```yaml
schema:
  $ref: "#/components/schemas/User"
```

This is extremely useful for large APIs.

---

# 20. `$ref` ⭐⭐

`$ref` means:

> Use another definition from the OpenAPI document.

Example:

```yaml
$ref: "#/components/schemas/User"
```

Instead of duplicating:

```text
User Schema
User Schema
User Schema
User Schema
```

you define it once.

```text
              User Schema
                   ↑
          ┌────────┼────────┐
          │        │        │
       GET /users POST     /users/{id}
```

---

# 21. Responses ⭐⭐⭐

An API contract must describe responses.

Example:

```yaml
responses:
  "200":
    description: Successful response
```

You can describe multiple responses:

```yaml
responses:
  "200":
    description: Success

  "400":
    description: Bad request

  "401":
    description: Unauthorized

  "404":
    description: User not found

  "500":
    description: Internal server error
```

---

# 22. HTTP Status Codes

OpenAPI can document expected status codes.

```text
2xx → Success
3xx → Redirection
4xx → Client error
5xx → Server error
```

Common API responses:

```text
200 OK
201 Created
204 No Content
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Entity
500 Internal Server Error
```

---

# 23. Response Body

You can describe the response body too.

```yaml
responses:
  "200":
    description: User returned
    content:
      application/json:
        schema:
          $ref: "#/components/schemas/User"
```

Now the client knows:

```text
GET /users/123
        ↓
200
        ↓
JSON
        ↓
User schema
```

# 25. Authentication ⭐⭐⭐

OpenAPI can describe authentication mechanisms.

Common types:

```text
API Key
Bearer Token
Basic Authentication
OAuth 2.0
OpenID Connect
```

Example:

```yaml
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
```

Then:

```yaml

  - bearerAuth: []
```

This tells consumers that the endpoint requires a bearer token.

# 29. Swagger vs OpenAPI ⭐⭐⭐

These terms are often confused.

```text
OpenAPI
   ↓
Specification / Standard
```

Swagger refers to a collection of tools and the historical name associated with the specification.

For example:

```text
OpenAPI Specification
        ↓
Swagger UI
        ↓
Interactive API documentation
```

So:

> **OpenAPI is the specification; Swagger is commonly used for tooling around it.**

# 32. Contract-First Development ⭐⭐⭐

There are two common approaches.

### Code-first

```text
Write backend
     ↓
Generate OpenAPI
     ↓
Generate docs
```

### Contract-first

```text
Write OpenAPI
     ↓
Agree on API contract
     ↓
Implement backend
     ↓
Build clients
```

Contract-first development can be useful when multiple teams work on the same API.

# 36. OpenAPI and Type Safety ⭐⭐

Suppose the schema says:

```yaml
User:
  type: object
  properties:
    id:
      type: integer
    name:
      type: string
```

A code generator can produce a type:

```typescript
interface User {
    id: number;
    name: string;
}
```

Now the API contract can influence client-side types.

```text
OpenAPI
   ↓
Generated Types
   ↓
Frontend
```

This reduces mismatch between backend and frontend.

# 37. OpenAPI and Testing ⭐⭐⭐

The contract can also help validate APIs.

Imagine OpenAPI says:

```text
POST /users
email → string
name → string
```

But the server returns:

```json
{
  "email": 123
}
```

The response violates the contract.

Tools can detect such mismatches.

```text
OpenAPI Contract
       ↓
Expected Response
       ↓
Actual Response
       ↓
Validation
       ↓
Pass / Fail
```

# 41. Example Complete OpenAPI Document

A simplified example:

```yaml
openapi: 3.0.0

info:
  title: User API
  version: 1.0.0

servers:
  - url: https://api.example.com

paths:

  /users:
    get:
      tags:
        - Users

      summary: Get users

      responses:
        "200":
          description: Successful response

          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: "#/components/schemas/User"

    post:
      tags:
        - Users

      summary: Create user

      requestBody:
        required: true

        content:
          application/json:
            schema:
              $ref: "#/components/schemas/CreateUser"

      responses:
        "201":
          description: User created

components:

  schemas:

    User:
      type: object

      properties:
        id:
          type: integer

        name:
          type: string

        email:
          type: string

    CreateUser:
      type: object

      required:
        - name
        - email

      properties:
        name:
          type: string

        email:
          type: string
```

This single document describes:

```text
GET /users
POST /users
User schema
CreateUser schema
Request body
Response body
Status codes
```

OpenAPI does not tell your application:

```text
How to write business logic
How to design your database internally
How to structure your service layer
How to implement authentication internally
How to optimize SQL queries

```

It primarily describes the **API interface**.

```text
Internal Implementation
        ↓
       Hidden
        │
        ↓
   HTTP API Contract
        │
        ↓
```

# 44. API Contract vs Implementation ⭐⭐⭐

Suppose the backend changes:

```text
PostgreSQL
   ↓
MongoDB
```

The client may not care.

As long as:

```text
GET /users
```

still returns the agreed response.

This is the power of abstraction.

```text
             Client
                │
                ↓
          API Contract
                │
        ┌───────┴───────┐
        ↓               ↓
 PostgreSQL         MongoDB
```

The implementation can change while the contract remains stable.

# 45. Breaking Changes 🚨

Suppose the API originally returns:

```json
{
  "id": 1,
  "name": "Yusuf"
}
```

Then you change it to:

```json
{
  "user_id": 1,
  "full_name": "Yusuf"
}
```

Existing clients may break.

```text
Old Client
    ↓
Expected: id
    ↓
API returns: user_id
    ↓
❌ Broken
```

API contracts help teams identify such changes.

---

# 46. Backward Compatibility ⭐⭐⭐

A good API should avoid unnecessary breaking changes.

Instead of:

```text
v1 → suddenly incompatible
```

you may use:

```text
/api/v1/users
/api/v2/users
```

or introduce compatible changes.

Example:

```text
Existing field
    ↓
Keep working

New optional field
    ↓
Add
```

# 48. Common Mistakes 🚨

### Mistake 1 — Treating OpenAPI as a backend framework

```text
OpenAPI ≠ Express
OpenAPI ≠ FastAPI
```

It is a specification.

---

### Mistake 2 — Documentation that doesn't match reality

```text
OpenAPI says:
email → string

Server actually:
email → number
```

This destroys trust in the contract.

---

### Mistake 3 — Not documenting errors

Only documenting:

```text
200 OK
```

is insufficient.

Also document important errors:

```text
400
401
403
404
409
500
```

---

### Mistake 4 — Duplicating schemas

Don't repeatedly define:

```text
User
User
User
User
```

Use reusable schemas and `$ref`.

---

### Mistake 5 — Exposing implementation details

The API contract should describe the public interface, not every internal detail.

OpenAPI is a standard specification for describing HTTP APIs in a machine-readable format.

```text
OpenAPI → Specification
```

```text
Contract
```
