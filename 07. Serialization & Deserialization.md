# 07. Serialization & Deserialization 📦

> **How do two applications written in different languages understand the same data?**

At first glance, an HTTP request looks simple:

```text
Client → HTTP Request → Server
```

But there is a fundamental problem.

The client and server may be written in completely different languages.

For example:

```text
Frontend
JavaScript
   ↓
Object

Backend
Rust
   ↓
Struct
```

A JavaScript object cannot simply be sent directly to a Rust application as an in-memory object.

Both systems need to agree on a **common representation of the data**.

That is where serialization and deserialization come in.

---

# 1. The Core Problem

Imagine a frontend has:

```javascript
const user = {
    name: "Yusuf",
    age: 22
};
```

Internally, JavaScript understands this as an object.

A backend written in Go might represent the same information as:

```go
type User struct {
    Name string
    Age  int
}
```

The two applications have different:

* Programming languages
* Type systems
* Runtime representations
* Data structures

They need a common format to communicate.

```text
JavaScript Object
       ↓
   Common Format
       ↓
    Network
       ↓
   Common Format
       ↓
   Go Struct
```

This common representation is the key idea behind serialization.

---

# 2. What Is Serialization?

**Serialization** is the process of converting data from its native in-memory representation into a format that can be transmitted or stored.

Think:

```text
Application Data
      ↓
Serialization
      ↓
Transport / Storage Format
```

For example:

```javascript
const user = {
    name: "Yusuf",
    age: 22
};
```

can be serialized into JSON:

```json
{
  "name": "Yusuf",
  "age": 22
}
```

In JavaScript:

```javascript
const json = JSON.stringify(user);
```

Now the data has been converted into a transferable representation.

---

# 3. What Is Deserialization?

**Deserialization** is the reverse process.

It converts the serialized representation back into a form that the receiving application can work with.

```text
Serialized Data
      ↓
Deserialization
      ↓
Native Application Data
```

For example:

```javascript
const json = '{"name":"Yusuf","age":22}';

const user = JSON.parse(json);
```

Now the application has a JavaScript object again.

---

# 4. The Complete Cycle

The easiest way to remember the concept:

```text
        CLIENT
           │
           │ Native Object
           ▼
     Serialization
           │
           ▼
      JSON / Bytes
           │
           │ Network
           ▼
      JSON / Bytes
           │
           ▼
    Deserialization
           │
           ▼
       SERVER
           │
           │ Native Object
           ▼
      Business Logic
```

And the response follows the reverse direction:

```text
Server Object
     ↓
Serialization
     ↓
JSON
     ↓
Network
     ↓
JSON
     ↓
Deserialization
     ↓
Client Object
```

This is the fundamental process behind client-server communication.

---

# 5. Why Can't We Just Send Objects?

Because an object is a **runtime concept**.

For example:

```text
JavaScript
   ↓
Object

Python
   ↓
Dictionary

Go
   ↓
Struct

Java
   ↓
Class/Object

Rust
   ↓
Struct
```

These are represented differently in memory.

The network doesn't understand:

```text
JavaScript Object
Go Struct
Python Dictionary
Java Class
```

Instead, communication eventually involves **data/bytes** that can be transported.

Therefore, applications agree on a standardized representation.

```text
Application-specific representation
              ↓
      Serialization
              ↓
   Standard representation
              ↓
           Network
              ↓
      Deserialization
              ↓
Application-specific representation
```

# 7. Text-Based Formats

Text-based formats represent information as readable text.

Examples:

```text
JSON
XML
YAML
```

Example JSON:

```json
{
  "name": "Yusuf",
  "age": 22
}
```

### Advantages

* Human-readable
* Easy to debug
* Easy to inspect
* Widely supported
* Convenient for APIs

### Disadvantages

* Usually larger than equivalent binary representations
* Parsing can have additional overhead

---

# 8. Binary Formats

Binary serialization represents information in a compact binary representation.

Examples include:

```text
Protocol Buffers
Avro
MessagePack
```

Conceptually:

```text
Object
  ↓
Binary Serialization
  ↓
Compact Bytes
  ↓
Network
```

Binary formats are generally less human-readable but can provide advantages in:

* Payload size
* Serialization/deserialization efficiency
* High-throughput communication

# 9. JSON

JSON stands for:

> **JavaScript Object Notation**

Despite its name, JSON is **language-independent**.

It is not limited to JavaScript.

It can be used by:

```text
JavaScript
Python
Java
Go
Rust
C#
PHP
...
```

This language independence is one of the reasons JSON works so well as a communication format.



# 14. JSON Is a Representation, Not a Native Object

This distinction is important.

Consider:

```json
{
  "age": 22
}
```

Before serialization, the application may have:

```text
User Object
```

After serialization:

```text
JSON representation
```

The JSON itself is not the original in-memory object.

It is a **representation of that object's data**.

```text
Native Object
      ↓
   Serialize
      ↓
JSON Representation
```

# 15. HTTP + Serialization

Now connect this with the previous HTTP chapter.

Suppose a client wants to create a book.

The client has:

```javascript
const book = {
    title: "Backend Engineering",
    author: "Yusuf"

```

It serializes the object:

```text
JavaScript Object
       ↓

```

and sends:

```http

```

with:

```json

  "title": "Backend Engineering",

```

The server receives the JSON and deserializes it.

```text
HTTP Request
     ↓
JSON
     ↓
Deserialization
     ↓
Server-native object
     ↓
Business Logic
```

# 20. Serialization and the Network

A common misconception is:

> "JSON is sent directly through the internet."

At the application level, we can think of it this way, but underneath, the network stack performs additional transformations.

A simplified mental model:

```text
Application
    ↓
HTTP
    ↓
Transport
    ↓
Network
    ↓
Link
    ↓
Physical transmission
```

The JSON exists at the application level.

The lower layers handle how that information is transported across the network.

As a backend engineer, you don't need to manually convert the JSON into electrical or optical signals.

The networking stack handles that.

---

# 21. Serialization vs Deserialization

| Concept         | Direction       | Purpose                               |
| --------------- | --------------- | ------------------------------------- |
| Serialization   | Object → Format | Prepare data for transmission/storage |
| Deserialization | Format → Object | Reconstruct usable application data   |

Easy memory trick:

```text
SERIALIZE
↓
Send it

DESERIALIZE
↓
Use it
```

Or:

```text
Object → JSON → Network → JSON → Object
```

---

# 22. JSON vs Binary Formats

A simplified comparison:

|                    | JSON            | Binary                            |
| ------------------ | --------------- | --------------------------------- |
| Human-readable     | ✅               | ❌                                 |
| Easy debugging     | ✅               | ❌                                 |
| Payload size       | Usually larger  | Usually smaller                   |
| Parsing efficiency | Moderate        | Often higher                      |
| Ecosystem          | Extremely broad | Depends on format                 |
| Common use         | REST APIs       | High-performance/internal systems |

The important lesson isn't:

> "JSON is always better."

Instead:

> **The serialization format should match the requirements of the system.**

---

# 23. Why Binary Can Be Faster

Consider a large payload.

With JSON, information is represented as text:

```json
{
  "userId": 123,
  "active": true
}
```

There are characters representing:

* Field names
* Quotes
* Punctuation
* Values

A binary format can encode the same information more compactly.

Conceptually:

```text
JSON
 ↓
More bytes
 ↓
Network
 ↓
More parsing

Binary
 ↓
Fewer bytes
 ↓
Network
 ↓
Efficient parsing
```

This can matter when systems have:

* Huge traffic
* Large payloads
* Strict latency requirements
* High-frequency service-to-service communication

---

# 24. Human Readability vs Efficiency

This is the fundamental trade-off.

```text
JSON
│
├── Easy to read
├── Easy to debug
├── Widely supported
└── Larger / potentially less efficient

Binary
│
├── Compact
├── Efficient
├── Good for high-performance systems
└── Harder to inspect manually
```

Neither is universally superior.

# 25. Type Conversion Problems

Serialization creates an important issue:

> **Not every programming language has the same types.**

For example, one language might distinguish between:

```text
int32
int64
float32
float64
```

while another language represents numbers differently.

Similarly:

```text
Date
Timestamp
Decimal
Binary Data
Enum
Map
Set
```

may have different representations in different languages.

Therefore, serialization isn't merely:

> "Convert object to JSON."

It also involves agreeing on **how data types should be represented**.

---

# 26. Dates

JSON doesn't have a dedicated native Date type.

A date might be represented as a string:

```json
{
  "createdAt": "2026-08-31T15:30:00Z"
}
```

The receiving application must interpret that string as a timestamp/date.

Conceptually:

```text
Date Object
     ↓
ISO String
     ↓
JSON
     ↓
ISO String
     ↓
Date Object
```

The exact representation needs to be agreed upon by the systems.

---

# 27. Missing vs Null

These are not always the same.

Consider:

```json
{
  "name": null
}
```

versus:

```json
{}
```

The first explicitly says:

```text
name exists
name = null
```

The second says:

```text
name is absent
```

This distinction can matter significantly in APIs, especially for updates.

# 28. Serialization Errors

Serialization can fail.

For example:

```text
Unsupported Type
Invalid Value
Circular Reference
Unexpected Data
```

The application needs to decide how these errors should be handled.

Similarly, deserialization can fail when the received data doesn't match the expected format.

```text
JSON
 ↓
Parse
 ↓
❌ Invalid JSON
```

---

# 29. Deserialization Is Not Validation

This distinction is important.

Suppose the server receives:

```json
{
  "age": "hello"
}
```

Deserialization may successfully parse the JSON.

The JSON itself is valid.

But the application may expect:

```text
age → number
```

So:

```text
Deserialization
      ↓
"Can I parse this data?"
      ↓
Validation
      ↓
"Does this data satisfy my requirements?"
```

These are different responsibilities.

# 31. Serialization and Security

Never assume that because data was successfully deserialized, it is safe.

The receiving system should still:

```text
Receive
  ↓
Deserialize
  ↓
Validate
  ↓
Sanitize / Transform where required
  ↓
Process
```

The backend must treat external data as **untrusted input**.

# 33. Serialization and API Contracts

Once two systems communicate using a format, they implicitly have a contract.

For example:

```json
{
  "id": 123,
  "name": "Yusuf",
  "active": true
}
```

The consumer may expect:

```text
id     → number
name   → string
active → boolean
```

Changing the structure can break consumers.

Therefore, serialization is also connected to:

* API compatibility
* Schema evolution
* Versioning
* Backward compatibility

# 🔑 Core Takeaways

* **Serialization converts native application data into a transferable/storable representation.**
* **Deserialization converts that representation back into application-usable data.**
* The fundamental reason is **interoperability between different systems and programming languages**.
* JSON is language-independent despite its name.
* JSON is widely used because it is simple, readable, and supported almost everywhere.
* Binary formats can provide better compactness and efficiency, at the cost of human readability.
* Serialization isn't limited to HTTP APIs; it also appears in queues, caches, storage, and microservice communication.
* Serialization and deserialization are **not the same as validation**.
* Successfully parsing JSON does not mean the data is valid for your business logic.
* Different languages may represent the same conceptual data differently, so the serialization format becomes a contract between systems.
* Serialization affects **payload size, performance, compatibility, and API evolution**.

> **The first-principles idea to remember:**
>
> **Objects are application-specific. Data crossing a system boundary needs a shared representation. Serialization creates that representation; deserialization turns it back into something the receiving application understands.**
