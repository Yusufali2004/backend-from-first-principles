# 16. Error Handling & Building Fault-Tolerant Systems 🛡️

> **A production backend is not defined by what happens when everything works. It is defined by what happens when something goes wrong.**
>
> Databases fail. Networks time out. APIs become unavailable. Users send invalid data. Processes crash. Dependencies become slow.
>
> A good backend doesn't assume these things won't happen. **It designs for them.**
>
> Fault tolerance is fundamentally about continuing to provide acceptable service despite component failures, by detecting faults, containing their effects, and recovering appropriately. ([IEEE Technology Navigator][1])

---

# 1. The Reality of Backend Systems

Consider a simple request:

```text
Client
  ↓
API Server
  ↓
PostgreSQL
  ↓
Response
```

It looks simple.

But in production:

```text
Client
  ↓
Load Balancer
  ↓
API Server
  ↓
Redis
  ↓
PostgreSQL
  ↓
External API
  ↓
Object Storage
```

Every additional dependency creates another possible failure point.

For example:

```text
Redis        ❌
PostgreSQL   ❌
Network      ❌
Payment API  ❌
Email API    ❌
Disk         ❌
Application  ❌
```

The question isn't:

> **"Can failures happen?"**

They will.

The question is:

> **"What does my system do when they happen?"**

---

# 2. Error vs Failure vs Fault

These terms are easy to mix up.

### Fault

The underlying problem.

```text
Database server crashes
```

### Error

The incorrect state caused by that fault.

```text
Application cannot establish DB connection
```

### Failure

The system can no longer provide its required service.

```text
API returns 500 / becomes unavailable
```

Conceptually:

```text
Fault
  ↓
Error
  ↓
Failure
```

A fault-tolerant design tries to prevent the problem from propagating all the way to a system-level failure. ([IEEE Technology Navigator][1])

---

# 3. Why Error Handling Matters

Without proper error handling:

```text
Database error
      ↓
Unhandled exception
      ↓
Application crash
      ↓
Request fails
      ↓
Potential cascading failures
```

With proper handling:

```text
Database error
      ↓
Detect
      ↓
Classify
      ↓
Recover / Retry / Fallback
      ↓
Return appropriate response
      ↓
Log + Monitor
```

The goal isn't simply:

> **"Catch every exception."**

The goal is:

> **"Handle failures deliberately."**

---

# 4. Types of Errors

A backend can encounter many different categories of errors.

```text
Errors
│
├── Client errors
├── Server errors
├── Database errors
├── Network errors
├── External service errors
├── Configuration errors
├── Programming errors
└── Infrastructure failures
```

---

# 5. Client Errors

The client sends something invalid.

Examples:

```text
Invalid JSON
Missing field
Invalid email
Invalid ID
Unauthorized request
Forbidden operation
Non-existent resource
```

For example:

```http
POST /users
```

with:

```json
{
  "email": "not-an-email"
}
```

The backend should reject it.

```text
400 Bad Request
```

rather than allowing invalid data deeper into the system.

---

# 6. Server Errors

The server encounters an unexpected problem.

Examples:

```text
Unhandled exception
Database unavailable
Dependency failure
Out of memory
Configuration problem
```

These generally result in:

```text
5xx
```

responses when they affect the request.

---

# 7. Don't Leak Internal Errors

Suppose PostgreSQL throws:

```text
connection refused at 10.0.2.15:5432
```

Don't return this directly to the user:

```json
{
  "error": "Postgres connection refused at 10.0.2.15:5432"
}
```

It exposes internal implementation details.

Instead:

```json
{
  "error": "Something went wrong. Please try again."
}
```

while logging the detailed error internally.

```text
Client
  ↓
Safe error message

Backend logs
  ↓
Detailed diagnostic information
```

---

# 8. Centralized Error Handling

Instead of every controller doing:

```text
try
catch
return error
```

in a completely different format, create centralized error handling.

```text
Request
  ↓
Router
  ↓
Controller
  ↓
Service
  ↓
Error
  ↓
Global Error Handler
  ↓
Consistent Response
```

For example:

```json
{
  "success": false,
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "User not found"
  }
}
```

Every endpoint can follow the same response structure.

---

# 9. Custom Error Types

Instead of throwing generic errors everywhere:

```text
Error("something went wrong")
```

create meaningful error categories.

For example:

```text
UserNotFoundError
ValidationError
AuthenticationError
AuthorizationError
DatabaseError
ExternalServiceError
```

Then the global handler can decide what to do.

```text
UserNotFoundError
       ↓
404

ValidationError
       ↓
400

AuthenticationError
       ↓
401

AuthorizationError
       ↓
403

Unexpected Error
       ↓
500
```

---

# 10. Error Classification

A very useful backend skill is asking:

> **What kind of error is this?**

For example:

```text
Error
│
├── Expected?
│     │
│     ├── YES → Handle explicitly
│     │
│     └── NO → Unexpected failure
│
└── Transient?
      │
      ├── YES → Maybe retry
      │
      └── NO → Don't blindly retry
```

This distinction becomes extremely important for distributed systems.

---

# 11. Transient Errors

Some failures are temporary.

Examples:

```text
Network timeout
Temporary service unavailable
Connection reset
HTTP 503
HTTP 429
```

The operation might succeed if tried again later.

Microsoft's reliability guidance specifically identifies transient network failures, temporary service unavailability, timeouts, HTTP 429, and many 5xx responses as situations where retrying can be appropriate, depending on the operation. ([Microsoft Learn][2])

---

# 12. Permanent Errors

Some errors won't be fixed by retrying.

For example:

```text
Invalid email
Invalid authentication
Resource doesn't exist
Malformed request
Insufficient permissions
```

Retrying:

```text
400
 ↓
retry
 ↓
400
 ↓
retry
 ↓
400
```

is pointless.

Therefore:

> **Don't retry errors blindly.**

---

# 13. Retry

Suppose:

```text
Application
   ↓
Payment Service
```

and the payment service temporarily returns:

```text
503 Service Unavailable
```

A retry may work:

```text
Attempt 1 → 503
Attempt 2 → 503
Attempt 3 → 200
```

This can make the system resilient to temporary failures.

---

# 14. Retry With Backoff

Never blindly retry as fast as possible.

Bad:

```text
FAIL
 ↓
retry immediately
 ↓
FAIL
 ↓
retry immediately
 ↓
FAIL
 ↓
retry immediately
```

This can overload an already struggling dependency.

Instead:

```text
Attempt 1 → FAIL
             ↓
          wait 1s

Attempt 2 → FAIL
             ↓
          wait 2s

Attempt 3 → FAIL
             ↓
          wait 4s

Attempt 4 → FAIL
             ↓
          stop
```

This is **exponential backoff**.

---

# 15. Add Jitter

Imagine 10,000 application instances all experience the same failure.

If all retry after exactly:

```text
2 seconds
```

they may all hit the dependency simultaneously.

```text
10,000 clients
     ↓
wait 2 sec
     ↓
10,000 requests
     ↓
💥
```

Adding random variation:

```text
1.8s
2.1s
2.4s
1.9s
2.3s
...
```

spreads the retries over time.

This is called:

> **Jitter**

A common production retry strategy is therefore:

```text
Retry
+
Exponential Backoff
+
Jitter
+
Maximum Attempts
```

---

# 16. Maximum Retries

Retries must have a limit.

For example:

```text
maxRetries = 3
```

Then:

```text
Attempt 1 ❌
Attempt 2 ❌
Attempt 3 ❌
       ↓
Give up
```

Otherwise:

```text
Retry forever
     ↓
Resource consumption
     ↓
Queue growth
     ↓
Cascading failure
```

---

# 17. Timeout

One of the most important fault-tolerance mechanisms is:

> **Timeout**

Suppose:

```text
Backend
   ↓
Payment API
```

The payment API doesn't respond.

Without a timeout:

```text
Request
 ↓
Waiting...
 ↓
Waiting...
 ↓
Waiting...
```

Eventually all your server resources could become occupied by waiting requests.

With a timeout:

```text
Request
 ↓
Payment API
 ↓
wait 2 seconds
 ↓
TIMEOUT
 ↓
Recover / retry / fallback
```

Timeouts prevent indefinitely waiting for broken or slow dependencies.

---

# 18. Why Timeouts Matter So Much

Imagine your API has:

```text
100 worker threads
```

and every request waits forever for a dependency.

Soon:

```text
100 workers
 ↓
100 waiting requests
 ↓
No workers available
 ↓
New requests can't execute
```

A dependency that isn't even part of your core application can effectively take down your service.

This is one form of **cascading failure**.

---

# 19. Cascading Failure ⭐

Consider:

```text
Service A
   ↓
Service B
   ↓
Service C
   ↓
Database
```

If Service C becomes extremely slow:

```text
A
 ↓
B
 ↓
C ⏳
```

Service B starts waiting.

Then:

```text
A
 ↓
B ⏳
```

Service A starts accumulating requests.

Eventually:

```text
A 💥
B 💥
C 💥
```

One slow component causes failures across the system.

This is why fault tolerance isn't only about handling errors **locally**.

It's about preventing failures from **propagating**.

---

# 20. Circuit Breaker ⭐

One important mechanism for preventing cascading failures is the:

> **Circuit Breaker**

Imagine your service repeatedly calls:

```text
Payment API
```

and it keeps failing.

Instead of:

```text
Request
 ↓
Payment API ❌
 ↓
Request
 ↓
Payment API ❌
 ↓
Request
 ↓
Payment API ❌
```

the circuit breaker eventually says:

```text
"Stop calling it for now."
```

---

# 21. Circuit Breaker States

A circuit breaker typically has three states:

```text
CLOSED
   ↓
OPEN
   ↓
HALF-OPEN
   ↓
CLOSED
```

---

# 22. CLOSED

Normal operation.

```text
Application
   ↓
Payment API
   ↓
Success
```

Failures are monitored.

```text
Failures < threshold
```

Circuit remains:

```text
CLOSED
```

---

# 23. OPEN

Too many failures occur.

```text
Payment API
   ❌
   ❌
   ❌
   ❌
```

Circuit opens:

```text
Application
     ↓
Circuit Breaker
     ↓
❌ Don't call Payment API
```

Requests fail quickly or use a fallback.

This prevents the application from continuously hammering a failing dependency.

---

# 24. HALF-OPEN

After some waiting period:

```text
OPEN
 ↓
wait
 ↓
HALF-OPEN
```

The system allows a small number of test requests.

```text
Test request
   ↓
Payment API
```

If successful:

```text
HALF-OPEN
     ↓
CLOSED
```

If it fails:

```text
HALF-OPEN
     ↓
OPEN
```

---

# 25. Circuit Breaker Mental Model

```text
                 ┌──────────────┐
                 │    CLOSED    │
                 │ Normal calls │
                 └──────┬───────┘
                        │
                 Too many failures
                        ↓
                 ┌──────────────┐
                 │     OPEN     │
                 │ Stop calls   │
                 └──────┬───────┘
                        │
                  Wait / cooldown
                        ↓
                 ┌──────────────┐
                 │  HALF-OPEN   │
                 │ Test request │
                 └──────┬───────┘
                    ┌───┴───┐
                  Success  Failure
                    ↓        ↓
                 CLOSED     OPEN
```

---

# 26. Fallbacks

Suppose your recommendation service fails.

Instead of:

```text
Recommendations ❌
      ↓
500
```

you might return:

```text
Popular products
```

instead.

```text
Recommendation Service
          ↓
         FAIL
          ↓
Fallback
          ↓
Popular Products
```

This is called:

> **Graceful degradation**

The system isn't providing its ideal behavior, but it is still providing useful service.

Fault-tolerant systems often use redundancy, reconfiguration, or fallback behavior to maintain acceptable service despite failures. ([IEEE Technology Navigator][1])

---

# 27. Graceful Degradation

Not every feature is equally important.

Imagine an e-commerce website:

```text
Core
├── Product browsing
├── Cart
├── Checkout
│
└── Non-critical
    ├── Recommendations
    ├── Reviews
    └── Analytics
```

If recommendations fail:

```text
Recommendations ❌
```

don't take down:

```text
Checkout
```

Instead:

```text
Recommendations
      ↓
Unavailable

Products
      ↓
Still available

Cart
      ↓
Still available

Checkout
      ↓
Still available
```

That's graceful degradation.

---

# 28. Bulkhead Pattern

Another useful fault-isolation concept is the:

> **Bulkhead pattern**

The name comes from ships.

A ship is divided into compartments so that if one compartment floods:

```text
┌─────┬─────┬─────┬─────┐
│     │ 💧  │     │     │
│     │ 💧  │     │     │
└─────┴─────┴─────┴─────┘
```

the entire ship doesn't necessarily sink.

In software:

```text
Worker Pool A → Payments
Worker Pool B → Emails
Worker Pool C → Reports
```

If reports consume all their workers:

```text
Reports 💥
```

payments can continue:

```text
Payments ✅
```

---

# 29. Bulkhead + Timeout

Imagine:

```text
Payment requests
→ 20 workers

Email requests
→ 10 workers

Reports
→ 5 workers
```

Reports become slow.

Without isolation:

```text
Reports consume all workers
      ↓
Payments blocked
      ↓
Entire API degraded
```

With bulkheads:

```text
Reports 💥
     ↓
5 workers affected

Payments
     ↓
20 workers still available
```

---

# 30. Fail Fast

Sometimes the correct behavior is:

> **Don't continue processing if you already know the request cannot succeed.**

Example:

```text
User authentication fails
```

Don't continue:

```text
Authentication
 ↓
Database
 ↓
Business logic
 ↓
Payment
```

Instead:

```text
Authentication ❌
      ↓
Return 401
```

This is **fail fast**.

It reduces:

```text
Unnecessary work
Resource usage
Latency
Potential side effects
```

---

# 31. Fail Fast vs Graceful Degradation

These aren't opposites.

### Fail fast

Use when:

```text
The operation cannot safely continue.
```

Example:

```text
Invalid request
Unauthorized user
Required database unavailable
```

### Graceful degradation

Use when:

```text
The core operation can continue without a non-critical dependency.
```

Example:

```text
Recommendations unavailable
      ↓
Show popular products
```

# 32. Error Propagation

Errors travel through layers.

```text
Database
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
HTTP Response
```

The important question is:

> **Where should the error be handled?**

Not every layer should necessarily handle every error.

---

# 33. Handle Errors at the Right Layer

Suppose:

```text
Database
 ↓
"User not found"
```

The repository might translate it into:

```text
UserNotFoundError
```

The service understands:

```text
User doesn't exist
```

The HTTP layer turns it into:

```http
404 Not Found
```

Conceptually:

```text
Database Error
      ↓
Domain Error
      ↓
HTTP Error
```

Each layer adds the context appropriate to it.

---

# 34. Don't Swallow Errors

A dangerous pattern:

```text
try {
   doSomething();
}
catch {
   // ignore
}
```

Now:

```text
Something failed
      ↓
Nobody knows
```

The system may continue in an invalid state.

Instead:

```text
Catch
 ↓
Handle OR
Propagate OR
Transform
 ↓
Log appropriately
```

An error should not disappear silently unless that is explicitly the intended behavior.

---

# 35. Logging Errors

When an unexpected failure happens, you need enough context to investigate it.

A useful error log might include:

```text
timestamp
requestId
userId (if appropriate)
service
operation
error type
stack trace
dependency
latency
```

Example:

```text
ERROR
requestId=req_123
operation=CreateOrder
dependency=PaymentAPI
error=Timeout
duration=2.1s
```

But:

> **Never blindly log secrets, passwords, tokens, or sensitive personal data.**

---

# 36. Request IDs

Suppose one request travels through:

```text
API
 ↓
Order Service
 ↓
Payment Service
 ↓
Notification Service
```

How do you connect all the logs?

Generate a:

> **Request ID / Correlation ID**

Example:

```text
req_abc123
```

Then:

```text
API
req_abc123

Order Service
req_abc123

Payment Service
req_abc123
```

Now you can reconstruct the journey of a request.

This connects directly with the **request context** chapter.

```text
   ↑
   ↑
   ↑
```

# 39. Error Rate

Suppose:

```text
10,000 requests
```

and:

```text
100 failures
```

Then:

```text
Error rate = 1%
```

Track this over time.

```text
1%
 ↓
1%
 ↓
2%
 ↓
5%
 ↓
20%
```

Something is probably wrong.

# 40. Latency Is Also an Error Signal

A service doesn't have to return `500` to be unhealthy.

Suppose:

```text
Normal:
100ms

Now:
5 seconds
```

Technically:

```text
HTTP 200
```

But users experience:

```text
❌
```

So fault tolerance must consider:

```text
Correctness
+
Availability
+
Latency
```

not only HTTP error codes.

---

# 41. Tail Latency

Suppose 99 requests take:

```text
100ms
```

but one takes:

```text
10 seconds
```

Average latency might still look reasonable.

That's why distributed systems often care about:

```text
p50
p95
p99
```

For example:

```text
p50 = 100ms
p95 = 250ms
p99 = 800ms
```

Tail latency matters because the slowest requests often determine the user's actual experience and can consume server resources disproportionately.

# 42. Health Checks

Services should often expose health information.

For example:

```http
GET /health
```

or:

```http
GET /ready
```

A load balancer can use these signals to decide:

```text
Server healthy
→ Send traffic

Server unhealthy
→ Stop sending traffic
```

---

# 43. Liveness vs Readiness

### Liveness

> Is the process alive?

```text
Application process running?
```

### Readiness

> Can the service actually handle traffic?

For example:

```text
Application running
BUT
Database connection unavailable
```

The process is alive:

```text
Liveness = YES
```

but perhaps not ready:

```text
Readiness = NO
```

This distinction is especially important in containerized/cloud environments.

---

# 44. Redundancy

One of the fundamental techniques for fault tolerance is:

> **Redundancy**

Instead of:

```text
Server A
```

use:

```text
Server A
Server B
Server C
```

If:

```text
Server A ❌
```

traffic can move to:

```text
Server B
```

Fault-tolerant architectures often rely on redundant components to avoid a single component becoming a single point of failure. ([IEEE Technology Navigator][3])

---

# 45. Single Point of Failure

A **single point of failure (SPOF)** is a component whose failure can bring down the system.

Example:

```text
             API
              ↓
       One Database Server
              ↓
              ❌
              ↓
          Entire API
```

That database is a SPOF.

A more resilient architecture might use:

```text
          API
           ↓
      DB Cluster
      /       \
 Primary     Replica
```

The exact architecture depends on consistency and failover requirements.

---

# 46. Redundancy Isn't Free

More replicas mean:

```text
More infrastructure
More cost
More synchronization
More operational complexity
```

So fault tolerance is an engineering trade-off.

Ask:

```text
How much failure can we tolerate?
How much downtime is acceptable?
How much data loss is acceptable?
How much does redundancy cost?
```

---

# 47. Availability

Availability asks:

> **How often is the system operational and accessible?**

A simplified formula:

```text
Availability =
Uptime / Total Time
```

For example:

```text
99%
99.9%
99.99%
99.999%
```

---

# 48. The "Nines"

Approximate annual downtime:

```text
99%       → ~3.65 days
99.9%     → ~8.76 hours
99.99%    → ~52.6 minutes
99.999%   → ~5.26 minutes
```

This demonstrates why each additional "9" becomes increasingly expensive.

---

# 49. Reliability vs Availability

These are related but not identical.

### Reliability

Probability that the system performs correctly over a period of time.

### Availability

Probability that the system is operational when needed.

A system could:

```text
Be available
BUT
return incorrect results
```

That's not reliable.

Dependability literature commonly treats reliability, availability, maintainability, and safety as distinct but related properties. ([Wiley Online Library][4])

---

# 50. Graceful Shutdown

Imagine deploying a new version.

You don't want:

```text
Server
 ↓
Kill immediately
 ↓
Requests in progress 💥
```

Instead:

```text
Shutdown signal
      ↓
Stop accepting new requests
      ↓
Finish in-flight requests
      ↓
Close DB connections
      ↓
Close resources
      ↓
Exit
```

This is:

> **Graceful shutdown**

It prevents deployments and scaling operations from unnecessarily interrupting active requests.

---

# 51. Database Failures

Suppose:

```text
API
 ↓
PostgreSQL ❌
```

Possible strategies include:

```text
Retry
Fail fast
Fallback
Read from replica
Return controlled error
```

But don't blindly retry database operations.

For example:

```text
INSERT payment
```

may have already succeeded before the connection was lost.

Retrying it could create a duplicate payment.

This brings us back to:

> **Idempotency**

---

# 52. Idempotency + Fault Tolerance ⭐

Consider:

```text
POST /payments
```

The backend sends:

```text
₹1000
```

to the payment provider.

The provider processes it successfully.

But the response is lost:

```text
Payment Provider
      ↓
Success
      X
Response lost
```

Your backend thinks:

```text
Payment failed
```

and retries.

Now:

```text
₹1000
+
₹1000
```

could be charged.

A proper design uses an:

```text
Idempotency-Key
```

such as:

```text
payment_123
```

The provider can recognize:

```text
payment_123
```

has already been processed.

This is one of the most important real-world fault-tolerance patterns.

---

# 53. Don't Retry Non-Idempotent Operations Blindly

Before retrying, ask:

```text
Could the previous attempt have succeeded?
```

and:

```text
If I repeat this operation, could I create a duplicate side effect?
```

For example:

```text
GET
```

is generally safer to retry.

But:

```text
Charge credit card
Create order
Send money
```

require much more careful handling.

---

# 54. Fault Isolation

A good system tries to contain failures.

For example:

```text
Recommendation Service ❌
```

should ideally result in:

```text
Recommendations unavailable
```

not:

```text
Entire website unavailable
```

This is the essence of:

> **Fault isolation**

Detect the problem and prevent it from spreading.

Fault-tolerant design commonly combines **fault detection, isolation, and recovery** rather than relying on redundancy alone. ([IEEE Technology Navigator][1])

Now let's put everything together.


# 🧠 Interview Mental Models

### What is fault tolerance?

> The ability of a system to continue providing correct or acceptable service despite failures in one or more components. ([IEEE Technology Navigator][1])

---

### What is the difference between fault, error, and failure?

> A **fault** is the underlying defect or problem; an **error** is the resulting incorrect state; a **failure** occurs when that error reaches the system's externally observable behavior and violates its required service.

```text
Fault → Error → Failure
```

---

### What is a transient error?

> A temporary failure that may succeed if the operation is attempted again later.

---

### When should you retry?

> When the failure is likely transient, the operation is safe to retry or made idempotent, and retrying won't worsen the situation.

---

### Why use exponential backoff?

> To progressively increase the delay between retries and avoid overwhelming an already unhealthy dependency.

---

### What is a circuit breaker?

> A mechanism that stops repeatedly calling a failing dependency, allows it time to recover, and later tests whether it has become healthy again.

---

### What is graceful degradation?

> Continuing to provide core functionality while reducing or disabling non-critical functionality when a dependency fails.

---

### What is a timeout?

> A limit on how long the application waits for an operation, preventing indefinitely blocked resources.

---

### What is a bulkhead?

> A fault-isolation technique that partitions resources so that failure or overload in one workload doesn't consume resources needed by other workloads.

---

### Why is idempotency important?

> Because retries, network failures, and worker failures can cause an operation to execute more than once, potentially producing duplicate side effects.

# ⚠️ Interview Traps

### ❌ "Just retry whenever something fails."

No.

```text
Transient error
→ Maybe retry

Permanent error
→ Don't retry
```

And the operation must be safe to retry. ([Microsoft Learn][2])

---

### ❌ "More retries = more reliability."

Not necessarily.

Too many retries can cause:

```text
Failure
 ↓
Retry storm
 ↓
Dependency overloaded
 ↓
More failures
 ↓
More retries
 ↓
💥
```

---

### ❌ "Circuit breaker replaces retries."

No.

They solve different problems.

```text
Retry
→ Give a potentially temporary failure another chance.


Circuit Breaker
→ Stop repeatedly calling a dependency that is clearly unhealthy.
```

They are often used together.

---

### ❌ "500 means the system is unhealthy."

Not necessarily.

A system can return:

```text
200
```

while taking:

```text
10 seconds
```

to respond.

Latency and resource exhaustion matter too.

---

### ❌ "If a database connection fails, retry the transaction."

Dangerous.

The original operation may have succeeded before the connection was lost.

For side-effecting operations:

```text
Retry
+
Idempotency
```

must be considered together.

---

### ❌ "Catch every exception."

No.

Bad:

```text
try {
    everything();
} catch {
    continue;
}
```

This can hide serious bugs.

Instead:

```text
Expected error
→ Handle

Recoverable error
→ Recover

Unexpected error
→ Log + controlled failure
```

# 🔥 Core Takeaways

* **Failures are inevitable; production systems must be designed around that reality.**
* A **fault** can create an **error**, which can propagate into a system-level **failure**.
* Good error handling classifies errors instead of blindly treating every error the same.
* **Transient errors** may be retried.
* Permanent errors generally should not be retried.
* Retries should use **backoff, jitter, and maximum attempts**.
* **Timeouts** prevent resources from being blocked indefinitely.
* **Circuit breakers** stop repeated calls to unhealthy dependencies.
* **Fallbacks** allow systems to degrade gracefully.
* **Bulkheads** isolate workloads so one failure doesn't consume all shared resources.
* **Fail fast** when continuing would be unsafe or pointless.
* **Idempotency is critical when retries can repeat side effects.**
* Redundancy removes or reduces single points of failure.
* Health checks allow infrastructure to stop routing traffic to unhealthy instances.
* Liveness asks **"is it alive?"**; readiness asks **"can it serve traffic?"**
* Error logs should contain enough diagnostic context without exposing secrets.
* Request IDs allow you to trace a request across multiple services.
* Metrics such as error rate, latency, retry count, and dependency health reveal system problems.
* **Fault tolerance is not one technique. It is a collection of detection, isolation, recovery, and degradation strategies.** ([IEEE Technology Navigator][1])

> ### The interview-level mental model
>
> Don't say:
>
> **"I'll handle errors with try/catch and retry if something fails."**
>
> Say:
>
> **"I'd first classify the failure as client-side, permanent, or transient. For transient failures I'd use bounded retries with exponential backoff and jitter, provided the operation is safe or idempotent. I'd apply timeouts to prevent blocked resources and a circuit breaker to stop repeatedly calling an unhealthy dependency. For non-critical dependencies I'd provide a fallback or graceful degradation, while isolating workloads to prevent cascading failures. Finally, I'd use structured logs, metrics, traces, and health checks to detect and diagnose failures."**
>
> **That is the fault-tolerance mindset you want to carry into backend and system-design interviews.**
