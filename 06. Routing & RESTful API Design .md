# 06. Routing & RESTful API Design 🛣️

> **Routing is how an API expresses what resource the client wants and how the server should handle that request.**

Routing looks simple on the surface:

```text
HTTP Request
     ↓
   Router
     ↓
Matching Route
     ↓
   Handler
```

But good routing is more than matching URLs.

It is about designing an API that communicates **resources, relationships, and intent** clearly.

---

# 1. What Is Routing?

Routing is the process of determining **which piece of server-side logic should handle an incoming request**.

Suppose the client sends:

```http
GET /api/users/123
```

The router needs to determine:

```text
Method → GET
Path   → /api/users/123
              ↓
         Matching Route
              ↓
       User Handler
```

A route is therefore usually identified by:

```text
HTTP Method + URL Pattern
```

---

# 2. Static Routes

A static route has a fixed path.

```http
GET /api/status
```

or:

```http
GET /api/config
```

The path doesn't contain a variable resource identifier.

```text
/api/status
/api/config
/api/health
```

These routes generally represent fixed endpoints.

---

# 3. Dynamic Routes

Dynamic routes contain values that change between requests.

Example:

```http
GET /api/users/123
```

Here:

```text
/api/users/:id
          ↑
       Dynamic
```

For another user:

```http
GET /api/users/456
```

The route pattern remains:

```text
/api/users/:id
```

but the value changes.

### Important

The `123` isn't just an arbitrary number.

It identifies the **specific resource** being requested.

```text
/api/users/123
         │
         └── User resource with ID 123
```

---

# 4. Path Parameters

Dynamic route values are commonly called **path parameters**.

```http
GET /api/users/123
```

Conceptually:

```text
/api/users/:id
          │
          └── path parameter
```

The server extracts:

```text
id = 123
```

and uses it to identify the resource.

---

# 5. Query Parameters

Query parameters appear after `?`.

Example:

```http
GET /api/users?page=2&limit=20
```

The resource is:

```text
/api/users
```

while:

```text
?page=2&limit=20
```

provides additional instructions.

Query parameters are commonly used for:

* Filtering
* Searching
* Sorting
* Pagination
* Optional configuration

---

# 6. Path Parameters vs Query Parameters

This distinction is important.

### Path parameter

Identifies **which resource** you're referring to.

```http
GET /api/users/123
```

```text
123 → specific user
```

### Query parameter

Modifies **how you want to retrieve the resource**.

```http
GET /api/users?page=2&limit=20
```

```text
page / limit → retrieval options
```

Think:

```text
PATH
↓
"What resource?"

QUERY
↓
"How should I retrieve it?"
```

---

# 7. Resource Collections

Consider:

```http
GET /api/books
```

This represents a collection of books.

```text
/api/books
      ↓
   Collection
```

Then:

```http
GET /api/books/42
```

represents one specific book.

```text
/api/books
      ↓
   Collection
      │
      └── /42
           ↓
        Resource
```

This distinction becomes important when designing REST APIs.

---

# 8. Nested Resources

Resources can have relationships.

Suppose a book has chapters.

You might represent that as:

```http
GET /api/books/42/chapters
```

This communicates:

> Get the chapters belonging to book 42.

The URL itself communicates the hierarchy:

```text
books
  └── 42
       └── chapters
```

This is one of the reasons resource-oriented URL design is useful.

---

# 9. Why Routing Design Matters

A poorly designed API might expose implementation details:

```text
GET /getUserById
POST /createNewUser
POST /deleteUser
```

A resource-oriented API instead communicates the resource and lets HTTP methods express the operation:

```http
GET    /users/123
POST   /users
DELETE /users/123
```

The difference is:

```text
Function-oriented thinking
        ↓
"Call this function"

Resource-oriented thinking
        ↓
"Operate on this resource"
```

---

# 10. What Is REST?

REST stands for:

> **Representational State Transfer**

REST is an **architectural style**, not a framework and not simply a list of HTTP methods.

It describes a set of architectural constraints for designing distributed systems.

---

# 11. The REST Constraints

The major REST constraints are:

```text
REST
 │
 ├── Client-Server
 ├── Stateless
 ├── Cacheable
 ├── Uniform Interface
 ├── Layered System
 └── Code-on-Demand (Optional)
```

---

# 12. Client-Server

Client and server should have separate responsibilities.

```text
Client
 ├── UI
 └── User Interaction

        ↕

Server
 ├── Data
 ├── Business Logic
 └── Persistence
```

This separation allows the client and server to evolve independently.

For example:

```text
Same Backend API
      ↓
 ┌────┼────┐
 ↓    ↓    ↓
Web  iOS  Android
```

The clients don't need to know how the backend stores its data internally.

---

# 13. Statelessness

Each request should contain all the information required for the server to process it.

The server should not depend on remembering previous requests to understand the current request.

```text
Request 1
   ↓
Server
   ↓
Response

Request 2
   ↓
Server
   ↓
Response
```

Request 2 should contain whatever context is necessary.

### Important

Stateless does **not** mean:

> "The server cannot store data."

The server can obviously store:

* Users
* Orders
* Posts
* Payments
* etc.

It means the server should not rely on **client session state stored implicitly between requests** as part of the REST interaction.

---

# 14. Cacheability

REST allows responses to be explicitly cacheable.

```text
Client
   ↓
Request
   ↓
Server
   ↓
Response
   ↓
Cache
```

If the response is cacheable, subsequent requests may be served without reaching the origin server.

This can improve:

* Latency
* Scalability
* Server load

HTTP provides mechanisms such as:

* Cache-Control
* ETag
* Last-Modified

---

# 15. Uniform Interface

The API should expose a consistent interface.

For example:

```http
GET /users
GET /users/123

POST /users

PATCH /users/123

DELETE /users/123
```

The client doesn't need to know how the server internally implements these operations.

The interface is predictable.

---

# 16. Layered System

A client shouldn't necessarily know whether it is communicating directly with the origin server.

There could be multiple layers:

```text
Client
  ↓
CDN
  ↓
Load Balancer
  ↓
API Gateway
  ↓
Backend
  ↓
Database
```

The client interacts with the API without needing to know the entire internal architecture.

This makes it possible to add infrastructure without changing the external interface.

---

# 17. Code on Demand

This is an **optional** REST constraint.

The server can send executable code to the client.

Historically, JavaScript sent to a browser is an example of this idea.

It is optional, unlike the other core constraints.

---

# 18. What Does REST Actually Mean?

Break down the name:

### Representational

A resource has a representation.

For example:

```json
{
  "id": 42,
  "name": "Yusuf"
}
```

The resource is the user.

JSON is one representation of its state.

### State

The resource has a current state.

For example:

```text
Cart
 ├── Item A × 2
 ├── Item B × 1
 └── Total ₹1200
```

That represents the current state of the cart.

### Transfer

That representation is transferred between client and server.

```text
Server
  ↓
Representation
  ↓
Network
  ↓
Client
```

Hence:

```text
Representational
      +
State
      +
Transfer
```

---

# 19. HTTP Methods & REST

REST commonly uses HTTP methods to express operations.

```text
GET
 ↓
Read

POST
 ↓
Create

PUT
 ↓
Replace

PATCH
 ↓
Modify

DELETE
 ↓
Delete
```

This allows the URL to describe the **resource**, while the method describes the **operation**.

---

# 20. Idempotency

This is one of the most important concepts for backend interviews.

An operation is **idempotent** if making the same request multiple times produces the same intended server state as making it once.

Example:

```http
PUT /users/123
```

```json
{
  "name": "Yusuf"
}
```

First request:

```text
name → Yusuf
```

Second request:

```text
name → Yusuf
```

Third request:

```text
name → Yusuf
```

The final state remains the same.

---

# 21. POST vs Idempotency

Consider:

```http
POST /orders
```

If you send it three times:

```text
POST
 ↓
Order #1

POST
 ↓
Order #2

POST
 ↓
Order #3
```

You may create three resources.

Therefore POST is generally **non-idempotent**.

This matters enormously for operations such as:

* Payments
* Orders
* Account creation
* Message creation

because retrying a request can accidentally perform an operation more than once.

---

# 22. Idempotency and Retries

Suppose a client sends:

```http
POST /payments
```

The payment succeeds.

But the response is lost because of a network failure.

The client doesn't know whether the payment succeeded.

It retries.

```text
Client
  │
  │ POST payment
  ▼
Server
  │
  │ Payment succeeds
  │
  X Response lost
  │
  ▼
Client
  │
  │ Retry
  ▼
Server
```

Without protection, the payment could happen twice.

This is why **idempotency** is extremely important in real backend systems.

A common solution is an **idempotency key**:

```http
Idempotency-Key: abc123
```

The server remembers the result associated with that key and can safely return the same result for a retry.

---

# 23. Custom Actions

Not every operation maps perfectly to CRUD.

For example:

```text
Cancel Order
Approve Application
Reset Password
```

A common pattern is:

```http
POST /orders/123/cancel
```

Here:

```text
POST
 ↓
Action

/orders/123
 ↓
Resource

/cancel
 ↓
Specific operation
```

The important principle is not to force every business operation into an unnatural REST representation.

---

# 24. API Versioning

As APIs evolve, breaking existing clients can be dangerous.

For example:

```text
/api/v1/users
```

and later:

```text
/api/v2/users
```

Versioning allows different clients to migrate at different speeds.

Common strategies include:

* URI versioning
* Header versioning
* Query parameter versioning
* Media-type versioning

The important point is:

> **API evolution needs to consider existing consumers.**

---

# 25. Routing + REST Together

Now connect the concepts.

```text
HTTP Request
     │
     ▼
GET /api/books/42/chapters?page=2
     │
     ├── Method → GET
     │
     ├── Resource → books
     │
     ├── Identifier → 42
     │
     ├── Sub-resource → chapters
     │
     └── Query → page=2
     │
     ▼
Router
     │
     ▼
Handler
```

The URL communicates structure.

The HTTP method communicates intent.

The query parameters refine the request.

---

# 26. A Good REST API

Suppose we're building an e-commerce API.

### Users

```http
GET    /users
GET    /users/123
POST   /users
PATCH  /users/123
DELETE /users/123
```

### Orders

```http
GET    /orders
GET    /orders/123
POST   /orders
PATCH  /orders/123
DELETE /orders/123
```

### Order items

```http
GET /orders/123/items
```

### Filtering

```http
GET /orders?status=shipped
```

### Pagination

```http
GET /orders?page=2&limit=20
```

The API becomes predictable because the same principles are applied consistently.

---

# 27. Common Routing Mistakes

### ❌ Putting identifiers in query parameters unnecessarily

```http
GET /users?id=123
```

when the request is specifically asking for one resource.

Often clearer:

```http
GET /users/123
```

---

### ❌ Function-style URLs everywhere

```http
/getUser
/createUser
/deleteUser
```

Prefer resource-oriented design where appropriate:

```http
GET    /users/123
POST   /users
DELETE /users/123
```

---

### ❌ Inconsistent naming

```text
/users
/userList
/getCustomers
/customer/123
```

A consistent resource model is easier for clients to understand.

---

### ❌ Ignoring HTTP semantics

Don't use:

```http
GET /deleteUser/123
```

GET should not be used for destructive operations.

Use:

```http
DELETE /users/123
```

---

# 🧠 Interview Mental Model

When designing an endpoint, ask:

### 1. What is the resource?

```text
/users
/orders
/products
```

### 2. Am I accessing a collection or one resource?

```text
/users
/users/123
```

### 3. What operation am I performing?

```text
GET
POST
PUT
PATCH
DELETE
```

### 4. Do I need query parameters?

```text
?search=phone
?page=2
?sort=price
?status=active
```

### 5. Is the operation idempotent?

Especially important when retries are possible.

### 6. Does the URL communicate the resource hierarchy clearly?

```text
/orders/123/items
```

### 7. Will this API need to evolve?

Think about versioning and backward compatibility.

# ⭐ Core Takeaways

* **Routing maps an incoming request to server-side logic.**
* A route is generally determined by **HTTP method + path pattern**.
* **Path parameters identify resources.**
* **Query parameters refine how resources are accessed.**
* Nested routes can communicate resource relationships.
* REST is an **architectural style**, not a framework or protocol.
* REST emphasizes client-server separation, statelessness, cacheability, uniform interfaces, and layered systems.
* A good API uses HTTP methods to communicate intent while URLs represent resources.
* **Idempotency is critical when requests can be retried.**
* POST is generally non-idempotent; PUT and DELETE are generally idempotent.
* Resource-oriented API design makes APIs easier to understand and consume.
* REST doesn't mean blindly following conventions—**understand the constraint and the reason behind it.**

> **A good API should make its intent obvious from the method, resource, and representation.**
