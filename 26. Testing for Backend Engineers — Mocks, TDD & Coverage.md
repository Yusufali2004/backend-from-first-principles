# 26. Testing for Backend Engineers — Mocks, TDD & Coverage 🧪

> Testing isn't about proving that your code can never fail.
>
> It's about building confidence that the system behaves correctly, **catching regressions early, and making changes safer**.
>
> For backend engineers, testing becomes especially important because business logic often interacts with databases, APIs, queues, files, authentication systems, and other external dependencies.
>
> The three concepts to understand deeply here are:
>
> ```text
> Testing
>    │
>    ├── Mocks
>    ├── TDD
>    └── Code Coverage
> ```

---

# 1. Why Do We Test Backend Systems?

Imagine you have:

```text
POST /orders
```

It performs:

```text
Validate request
      ↓
Check user
      ↓
Check inventory
      ↓
Create order
      ↓
Charge payment
      ↓
Send notification
```

A small change to one component can break another.

Without tests:

```text
Change code
   ↓
Hope everything works
   ↓
Deploy
   ↓
🔥 Production bug
```

With tests:

```text
Change code
   ↓
Run tests
   ↓
Detect regression
   ↓
Fix
   ↓
Deploy
```

The goal is **confidence**.

---

# 2. What Should We Test?

Don't think only in terms of:

```text
"Does this function return the right value?"
```

A backend engineer should test behavior at different levels.

```text
                    TESTING
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
        Unit       Integration    E2E
          │            │            │
      One unit      Components    Whole flow
```

---

# 3. Unit Testing ⭐

A unit test focuses on a small unit of code.

For example:

```text
calculateDiscount()
```

Input:

```text
price = 1000
discount = 10%
```

Expected:

```text
900
```

Conceptually:

```text
Input
 ↓
Function
 ↓
Output
```

The test should ideally be:

```text
Fast
Isolated
Deterministic
Easy to understand
```

---

# 4. Integration Testing

Integration testing checks whether multiple components work together correctly.

Example:

```text
API
 ↓
Service
 ↓
PostgreSQL
```

A test could verify:

```text
POST /users
 ↓
User created
 ↓
Actually exists in database
```

Here we're testing integration between components rather than one isolated function.

---

# 5. End-to-End Testing

E2E testing tests a complete user/system flow.

Example:

```text
Client
 ↓
POST /login
 ↓
Authentication
 ↓
Database
 ↓
JWT/session
 ↓
GET /profile
 ↓
Response
```

The test checks the system more like a real user would interact with it.

---

# 6. Testing Pyramid ⭐⭐⭐

A useful mental model:

```text
                 /\
                /  \
               / E2E\
              /------\
             /        \
            /Integration\
           /------------\
          /              \
         /   Unit Tests   \
        /------------------\
```

Generally:

```text
Many unit tests
     ↓
Fewer integration tests
     ↓
Even fewer expensive E2E tests
```

Why?

Because unit tests are usually:

```text
Fast
Cheap
Easy to run
Easy to debug
```

while E2E tests are usually:

```text
Slower
More expensive
More fragile
Harder to debug
```

---

# 7. Test Isolation

A good unit test should avoid unnecessary dependencies.

Suppose:

```text
createUser()
```

calls:

```text
PostgreSQL
```

A unit test doesn't necessarily need a real PostgreSQL database.

Instead:

```text
createUser()
      ↓
 Mock Repository
      ↓
 Fake result
```

This allows you to test the business logic independently.

---

# 8. What Is a Mock? ⭐⭐⭐

A **mock** is a test double that stands in for a real dependency during a test.

Suppose:

```text
OrderService
      ↓
PaymentService
```

During testing:

```text
OrderService
      ↓
Mock PaymentService
```

Instead of actually charging a credit card, the mock can return:

```text
payment = successful
```

or:

```text
payment = failed
```

---

# 9. Why Do We Mock?

Imagine your test calls a real payment provider.

Every test might:

```text
Call internet
 ↓
Contact payment provider
 ↓
Wait
 ↓
Potentially charge money
```

That's obviously undesirable.

Mocks allow:

```text
Payment API
     ↓
   Mock
     ↓
Controlled response
```

You can test many scenarios safely and quickly.

---

# 10. Mocking External Dependencies

Common things to mock:

```text
Payment providers
Email services
SMS services
External APIs
Cloud services
Message queues
Time
Random number generators
Database repositories
```

But:

> **Don't mock everything blindly.**

Mocking is useful when you need isolation or control over a dependency.

# 11. Example: Payment Service

Suppose:

```text
OrderService
```

does:

```text
createOrder()
 ↓
chargePayment()
 ↓
saveOrder()
```

You can test:

### Successful payment

```text
Mock Payment
→ success
```

Expected:

```text
Order created
```

### Failed payment

```text
Mock Payment
→ failure
```

Expected:

```text

```

### Payment timeout

```text

```

Expected:

```text

```

# 12. Test Doubles

"Mock" is often used as a general term, but there are different kinds of test doubles.

```text
Test Doubles
│
├── Dummy
├── Stub
├── Mock
├── Spy
└── Fake
```

Understanding the distinction is useful in interviews.

---

# 13. Dummy

A dummy object is provided simply because the code requires an argument.

It isn't really used.

Example:

```text
sendEmail(user, logger)
```

The test doesn't care about the logger.

So:

```text
logger = Dummy
```

The dummy simply satisfies the dependency.

---

# 14. Stub

A stub provides predefined responses.

Example:

```text
UserRepository.findById(123)
```

Stub:

```text
→ return User(id=123)
```

You control what the dependency returns.

Mental model:

> **Stub = predetermined answer.**

---

# 15. Mock

A mock can be used to verify that a dependency was interacted with as expected.

For example:

```text
OrderService
 ↓
EmailService.sendConfirmation()
```

Test:

```text
Was sendConfirmation()
called exactly once?
```

Mental model:

> **Mock = verify interaction.**

---

# 16. Spy

A spy wraps or observes something and records how it was used.

For example:

```text
logger.info()
```

A spy can allow the operation while recording:

```text
Called?
How many times?
With what arguments?
```

Mental model:

> **Spy = observe what happened.**

---

# 17. Fake

A fake is a simplified working implementation.

Example:

Instead of a real database:

```text
PostgreSQL
```

use:

```text
In-memory repository
```

```text
FakeUserRepository
```

It actually implements behavior but in a simplified way.

---

# 18. Test Double Comparison

| Double | Purpose                           |
| ------ | --------------------------------- |
| Dummy  | Fills an unused argument          |
| Stub   | Returns controlled data           |
| Mock   | Verifies expected interaction     |
| Spy    | Records/observes calls            |
| Fake   | Simplified working implementation |

In real-world frameworks, terminology can overlap, so focus on the underlying behavior.

Production:

```text

      ↓

```

Test:

```text

      ↓
```

```text

```

# 20. Arrange → Act → Assert ⭐⭐⭐

A very useful testing structure is:

```text
Arrange
   ↓
Act
   ↓
Assert
```

### Arrange

Prepare the test:

```text
Create user
Create mock
Set expected behavior
```

### Act

Execute the operation:

```text
createOrder()
```

### Assert

Verify the result:

```text
Order created
```

Example:

```text
ARRANGE
Mock payment → success

ACT
createOrder()

ASSERT
Order exists
Payment called once
```

---

# 21. Given → When → Then

Another common style:

```text
Given
  user has sufficient balance

When
  user purchases product

Then
  order should be created
```

This is especially common in behavior-driven development.

---

# 22. Deterministic Tests

A good test should ideally produce the same result every time.

Bad:

```text
Test
 ↓
Random API
 ↓
Sometimes success
Sometimes failure
```

This creates **flaky tests**.

Good:

```text
Test
 ↓
Controlled dependency
 ↓
Predictable result
```

---

# 23. Flaky Tests 🚨

A flaky test sometimes passes and sometimes fails without a relevant code change.

Example:

```text
Run 1 → PASS
Run 2 → PASS
Run 3 → FAIL
Run 4 → PASS
```

Possible causes:

```text
Race conditions
Timing assumptions
Network dependency
Shared test state
Randomness
Unreliable external services
Improper cleanup
```

Flaky tests are dangerous because teams start ignoring failures.

---

# 24. Test Independence

Tests should ideally not depend on execution order.

Bad:

```text
Test A
→ creates user

Test B
→ assumes user already exists
```

Now:

```text
Test B
```

fails when run independently.

Better:

```text
Test A
→ creates its own data

Test B
→ creates its own data
```

Each test owns its setup.

---

# 25. Test Fixtures

A fixture is predefined test data/setup.

Example:

```text
UserFixture
{
    id: 123,
    name: "Test User",
    email: "test@example.com"
}
```

Fixtures make repeated setup easier.

But don't create enormous fixtures containing irrelevant data.

Keep tests focused.

---

# 26. Test Cleanup

Tests can modify:

```text
Database
Files
Cache
Environment variables
Global state
```

Clean up afterward.

For example:

```text
Before test
 ↓
Create test data
 ↓
Run test
 ↓
Delete/reset test data
```

Otherwise one test can affect another.

---

# 27. Testing Error Paths ⭐

A common mistake is testing only:

```text
SUCCESS
```

Backend code has many failure paths.

Test:

```text
Invalid input
Unauthorized
Forbidden
Not found
Database failure
Timeout
External API failure
Duplicate request
Malformed data
Unexpected dependency response
```

For production systems, error paths can be just as important as happy paths.

---

# 28. Testing Authentication

For an authenticated endpoint:

```text
GET /profile
```

test:

```text
Valid token
→ 200

Missing token
→ 401

Invalid token
→ 401

Expired token
→ 401
```

Authorization:

```text
User owns resource
→ 200

User doesn't own resource
→ 403
```

---

# 29. Testing Validation

Suppose:

```text
POST /users
```

requires:

```text
email
password
age
```

Test:

```text
Valid input
Missing email
Invalid email
Weak password
Negative age
Future date
Wrong type
Extra fields
```

Validation logic deserves explicit tests.

---

# 30. Testing Database Code

There are different approaches.

### Mock repository

```text
Service
 ↓
Mock Repository
```

Good for unit tests.

### Real test database

```text
Service
 ↓
Real PostgreSQL
```

Useful for integration tests.

A common strategy is:

```text
Unit tests
→ mock external boundaries

Integration tests
→ real database
```

This gives you both speed and confidence.

---

# 31. Don't Mock the Database Automatically

This is an important nuance.

If your goal is to test:

```text
"Does this SQL query actually work?"
```

a mock cannot answer that.

A mock can only tell you:

```text
"Did my code call the repository?"
```

A real integration test can catch:

```text
SQL syntax errors
Wrong schema assumptions
Constraint violations
Migration problems
Transaction issues
```

Therefore:

> **Mock for isolation; integrate for integration.**

---

# 32. Testing External APIs

Suppose:

```text
Backend
 ↓
Payment API
```

Unit test:

```text
Mock Payment API
```

Integration test:

```text
Sandbox Payment API
```

You might need both.

```text
Unit
→ business logic

Integration
→ actual API contract/integration
```

---

# 33. Contract Testing

When two systems communicate:

```text
Service A
 ↓
API
 ↓
Service B
```

you need to ensure their expectations agree.

Contract testing verifies assumptions such as:

```text
Request format
Response fields
Status codes
Required parameters
```

This is especially useful in distributed systems and microservices.

---

# 34. What Is TDD? ⭐⭐⭐

**TDD = Test-Driven Development.**

The basic cycle:

```text
RED
 ↓
GREEN
 ↓
REFACTOR
 ↓
RED
 ↓
GREEN
 ↓
REFACTOR
```

---

# 35. RED

First write a test for behavior that doesn't exist yet.

```text
Test
 ↓
Expected behavior
 ↓
FAIL ❌
```

This is the **Red** phase.

Example:

```text
Test:
calculateTax(1000) should return 180
```

But the implementation doesn't exist.

Test fails.

---

# 36. GREEN

Write the simplest implementation that makes the test pass.

```text
Test
 ↓
Implementation
 ↓
PASS ✅
```

Don't immediately try to create the perfect architecture.

First make the behavior work.

---

# 37. REFACTOR

Now improve the implementation while keeping the tests passing.

```text
Working code
 ↓
Clean up
 ↓
Improve design
 ↓
Tests remain GREEN
```

Examples:

```text
Remove duplication
Improve naming
Extract functions
Simplify logic
Improve structure
```

---

# 38. TDD Cycle ⭐⭐⭐

```text
       ┌─────────────┐
       │    RED ❌    │
       │ Write test  │
       └──────┬──────┘
              ↓
       ┌─────────────┐
       │  GREEN ✅   │
       │ Make it pass│
       └──────┬──────┘
              ↓
       ┌─────────────┐
       │  REFACTOR   │
       │ Improve code│
       └──────┬──────┘
              │
              └────────→ RED
```

---

# 39. Why TDD?

TDD can help you:

```text
Clarify requirements
Design smaller units
Catch regressions
Create executable specifications
Encourage testable architecture
Reduce fear of refactoring
```

The test becomes an explicit statement of expected behavior.

---

# 40. TDD Doesn't Mean "Test Everything First"

TDD is not:

```text
Write 500 tests
 ↓
Then write code
```

It is an iterative development process:

```text
Small requirement
 ↓
Test
 ↓
Implementation
 ↓
Refactor
 ↓
Next requirement
```

---

# 41. TDD Example

Requirement:

> Users with age >= 18 can register.

First:

```text
Test:
register(age=20)
→ success
```

RED ❌

Then implementation:

```text
if age >= 18:
    allow registration
```

GREEN ✅

Then:

```text
Test:
register(age=17)
→ reject
```

RED ❌

Implement:

```text
if age < 18:
    reject
```

GREEN ✅

Then refactor if needed.

---

# 42. TDD and Design

One interesting benefit:

If something is extremely difficult to test:

```text
Huge function
 ↓
20 dependencies
 ↓
Global state
 ↓
Hard to isolate
```

that can indicate a design problem.

TDD can therefore push you toward:

```text
Smaller components
Clear dependencies
Separation of concerns
Dependency injection
```

---

# 43. What Is Code Coverage? 📊

Code coverage measures how much of your code is exercised by tests.

Common metrics include:

```text
Line coverage
Statement coverage
Branch coverage
Function coverage
Condition coverage
```

---

# 44. Line Coverage

Suppose:

```text
1. validate()
2. saveUser()
3. sendEmail()
4. log()
```

If tests execute:

```text
1
2
4
```

but not:

```text
3
```

then:

```text
Coverage = 3 / 4 = 75%
```

Simplified example.

---

# 45. Branch Coverage ⭐

Consider:

```javascript id="w6qf1e"
if (user.isAdmin) {
    allow();
} else {
    deny();
}
```

There are two branches:

```text
TRUE
FALSE
```

Testing only:

```text
isAdmin = true
```

doesn't cover the `false` branch.

So branch coverage can reveal gaps that line coverage misses.

---

# 46. Why 100% Coverage Isn't Perfect

You might achieve:

```text
100% line coverage
```

and still have bugs.

Why?

Because:

```text
Executed code
≠
Correctly tested behavior
```

A test could execute a line without meaningfully asserting its result.

---

# 47. Example of Misleading Coverage

Bad test:

```text
call calculatePrice()
```

No assertion.

The function executes.

Coverage increases.

But:

```text
Did it return the correct value?
```

Nobody knows.

So:

> **Coverage measures test execution, not test quality.**

---

# 48. High Coverage Can Still Miss Bugs

Imagine:

```text
if payment_success:
    create_order()
else:
    cancel_payment()
```

A test may execute both branches but fail to verify:

```text
Was the order actually created?
Was the payment cancelled?
Was the correct user affected?
```

Coverage alone cannot answer those questions.

---

# 49. Coverage as a Signal

Use coverage to identify:

```text
Untested code
Missing branches
Important areas without tests
Regression risk
```

Don't treat:

```text
90%
```

as automatically better than:

```text
80%
```

if the additional tests don't provide meaningful confidence.

---

# 50. What Should Have High Test Coverage?

Prioritize important behavior:

```text
Business logic
Authentication
Authorization
Payments
Data transformations
Validation
Error handling
Critical workflows
```

Less important:

```text
Simple wrappers
Generated code
Trivial configuration
```

depending on the project.

---

# 51. Testing Business Logic ⭐⭐⭐

Business logic is one of the best places for strong unit tests.

Example:

```text
OrderService
```

Rules:

```text
Cannot purchase unavailable item
Discount applies only to eligible users
Cannot cancel shipped order
Refund allowed within 30 days
```

These rules should be heavily tested.

Why?

Because bugs here directly affect business behavior.

---

# 52. Testing Controllers

Controllers should usually be relatively thin:

```text
Request
 ↓
Validation
 ↓
Service
 ↓
Response
```

Tests can verify:

```text
Correct status code
Correct response structure
Validation errors
Authentication failures
Service errors
```

But you don't need to put every business-rule test into the controller tests.

Those belong closer to the business logic.

Test:


Mocks can isolate:

```text
Repository

```

# 54. Testing Repositories

Repository tests can verify:

```text
Queries
Mappings
Transactions
Constraints
Pagination

```

These are often good candidates for integration tests against a real test database.

# 55. Testing APIs

An API integration test might look like:

```text
POST /users
```

Request:

```json id="o3n9sm"
{
  "name": "Yusuf",
  "email": "test@example.com"
}
```

Expected:

```text id="3p73z5"
HTTP 201
```

and:

```text id="x7s7p2"
User exists in database
```

Now you're testing multiple layers together.

---

# 56. Testing HTTP Status Codes

Backend APIs should test correct status codes.

Examples:

```text id="7r8k5h"
200 → successful retrieval
201 → created
204 → successful operation with no response body
400 → invalid request
401 → unauthenticated
403 → unauthorized
404 → not found
409 → conflict
429 → rate limited
500 → server error
```

The exact choice depends on the API semantics.

---

# 57. Testing Error Responses

Don't test only:

```text
status = 400
```

Also consider:

```text
Response structure
Error code
Useful message
No sensitive information leaked
```

For example:

```json id="i0p6na"
{
  "error": {
    "code": "INVALID_EMAIL",
    "message": "Email address is invalid"
  }
}
```

Consistency makes client integration easier.

---

# 58. Testing Time

Time-dependent code is surprisingly difficult.

Example:

```text
subscription expires in 30 days
```

Don't make your test depend on:

```text
Actual system clock
```

Instead inject/control time:

```text
Clock
 ↓
Mock/Fake Clock
```

Then:

```text
Today = Jan 1
Expiry = Jan 31
```

This makes tests deterministic.

---

# 59. Testing Randomness

Similarly:

```text
generateRandomToken()
```

can make tests unpredictable.

Instead:

```text
Random generator
 ↓
Fake/controlled generator
```

Now you can test exact behavior.

---

# 60. Testing Retries

Suppose an external API is called:

```text
Attempt 1 → timeout
Attempt 2 → timeout
Attempt 3 → success
```

Your tests should verify:

```text
Correct retry count
Backoff behavior
Final result
Failure after maximum attempts
```

Mocks are particularly useful here.

---

# 61. Testing Idempotency

Suppose:

```text
POST /payments
```

is sent twice with the same idempotency key.

Test:

```text
Request 1
→ payment created

Request 2
→ same result / no duplicate payment
```

This is especially important in distributed systems.

---

# 62. Testing Background Jobs

Suppose:

```text
Order created
 ↓
Queue
 ↓
Send confirmation email
```

Tests can verify:

```text
Correct job created
Correct payload
Retry behavior
Failure handling
Idempotency
```

The actual email provider can be mocked.

---

# 63. Testing Webhooks

For webhook consumers:

```text
Webhook
 ↓
Verify signature
 ↓
Parse payload
 ↓

```

Test:

```text

```

---

# 64. Test Naming

A test name should explain behavior.

Bad:

```text
test1()
```

Better:

```text
should reject registration when age is below 18
```

Even better conceptually:

```text
Given age is 17
When user registers
Then registration is rejected
```

Good test names make failures understandable.

---

# 65. One Behavior Per Test

Avoid giant tests:

```text
testEverything()
```

Instead:

```text
should create valid order
should reject unavailable product
should reject failed payment
should prevent duplicate order
```

This makes failures easier to diagnose.

---

# 66. Avoid Over-Specifying Implementation

A test should usually care about:

```text
Behavior
```

rather than:

```text
Internal implementation details
```

Bad:

```text
assert function A called
then function B
then function C
```

when the order isn't part of the contract.

Better:

```text
assert final behavior is correct
```

Overly coupled tests become painful when refactoring.

---

# 67. Tests as Documentation

A good test can answer:

> "How is this component supposed to behave?"

For example:

```text
should return 409 when email already exists
```

immediately communicates an API/business rule.

This is one reason well-written tests are valuable beyond simply catching bugs.

---

# 68. Regression Testing

Suppose you discover:

```text
Bug #123:
Expired users can still access premium content.
```

Fix the bug.

Then add a test:

```text
expired user
→ premium access denied
```

Now if somebody breaks it later:

```text
Test ❌
```

The bug doesn't silently return.

This is **regression testing**.

---

# 69. Test Suite Speed

If your test suite takes:

```text
5 seconds
```

developers run it frequently.

If it takes:

```text
2 hours
```

people avoid running it.

Therefore:

```text
Fast feedback
→ More testing
→ Faster development
```

This is one reason unit tests are valuable.

---

# 70. Test Parallelization

Independent tests can often run concurrently:

```text
Test A ──────┐
Test B ──────┼→ Test Runner
Test C ──────┤
Test D ──────┘
```

This reduces total execution time.

But tests must be properly isolated.

Otherwise parallel execution can introduce:

```text
Shared-state conflicts
Database collisions
Race conditions
```

# 73. Testing Production Systems

Tests don't replace production monitoring.

Even with:

```text
100% coverage
```

production can still fail because of:

# 🧠 Interview Mental Models

### What is unit testing?

> Testing a small, isolated unit of behavior independently from its external dependencies.

### What is integration testing?

> Testing whether multiple components work correctly together.

### What is E2E testing?

> Testing a complete workflow through the system from an external user's perspective.

### What is a mock?

> A controlled test double that replaces a dependency so the system under test can be isolated and its interactions can be controlled or verified.

### Why mock external APIs?

> To avoid real side effects, network dependency, slow execution, and nondeterministic responses.

### Should you mock the database?

> For unit tests, often yes when testing business logic. But use integration tests with a real test database when you need to verify actual queries, constraints, transactions, and database integration.

### What is TDD?

> A development approach where tests are written before the implementation and development proceeds through Red → Green → Refactor cycles.

### What is code coverage?

> A metric describing which parts of the code are executed by tests.

### Does 100% coverage mean bug-free code?

> No. Coverage measures execution, not whether the tests meaningfully verify correct behavior.

# ⚠️ Interview Traps

### ❌ "More coverage always means better tests."

No.

```text
Coverage
≠
Test quality
```

---

### ❌ "100% coverage means no bugs."

No.

You can execute every line while making weak assertions.

---

### ❌ "Mock everything."

No.

Excessive mocking can make tests disconnected from reality.

Use:

```text
Mocks → isolation
Real dependencies → integration confidence
```

---

### ❌ "Integration tests are unnecessary if unit tests pass."

Wrong.

Unit tests may not catch:

```text
SQL errors
Schema mismatches
Incorrect configuration
Real API incompatibilities
Transaction problems
```

---

### ❌ "E2E tests should test everything."

Usually not.

E2E tests are expensive and slower.

Use them for important end-to-end workflows.

---

### ❌ "TDD means write all tests before coding."

No.

TDD is iterative:

```text
RED
→ GREEN
→ REFACTOR
→ repeat
```

---

### ❌ "A test should test implementation details."

Usually avoid this.

Prefer testing:

```text
Observable behavior
```

rather than unnecessarily coupling tests to internal implementation.

---

### ❌ "If a test is flaky, just rerun it."

That's a dangerous habit.

Flaky tests should be investigated because they undermine trust in the test suite.

# 🔥 Core Takeaways

* Testing gives you **confidence to change code safely**.
* Backend testing usually involves **unit, integration, and E2E tests**.
* Unit tests isolate small pieces of behavior and should generally be fast.
* Integration tests verify that components actually work together.
* E2E tests verify complete system workflows.
* **Mocks are useful for isolating dependencies**, especially external services.
* Don't mock everything; excessive mocking can make tests unrealistic.
* A **stub** provides a controlled response.
* A **mock** can verify expected interactions.
* A **spy** observes interactions.
* A **fake** is a simplified working implementation.
* A **dummy** exists only to satisfy a dependency.
* `Arrange → Act → Assert` is a useful structure for writing tests.
* Tests should ideally be **deterministic, isolated, repeatable, and understandable**.
* Flaky tests are dangerous because they reduce trust in the test suite.
* Tests should cover both **happy paths and failure paths**.
* Database unit tests and database integration tests solve different problems.
* Mocking a database can test business logic, but only a real database integration test can reveal many SQL/schema/transaction problems.
* **TDD = Red → Green → Refactor.**
* TDD is iterative, not "write every test before writing any code."
* TDD can encourage smaller, more testable components and clearer dependencies.
* Code coverage measures how much code tests execute.
* **Coverage does not measure test quality.**
* 100% coverage does not guarantee bug-free software.
* Branch coverage can reveal paths that simple line coverage misses.
* Prioritize tests around **business-critical behavior and failure scenarios**.
* Test authentication, authorization, validation, retries, idempotency, webhooks and background jobs explicitly where relevant.
* Tests should verify behavior rather than unnecessarily locking the code to implementation details.
* Tests should run automatically in CI/CD.
* Testing works together with **logging, monitoring, observability, linting, type checking and code review**.
* The real goal isn't:

  > **"How much code did we test?"**

> It's:
> **"How confident are we that the system will behave correctly when something changes or goes wrong?"**
