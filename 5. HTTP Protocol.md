# 5. HTTP Protocol 📡

> **HTTP is the application-layer protocol that allows clients and servers to communicate.**

HTTP is one of the most fundamental concepts in backend engineering.

Every time a client:

* Loads a webpage
* Calls an API
* Logs in
* Uploads a file
* Fetches data
* Sends a form

there is usually HTTP communication involved.

---

# 1. What is HTTP?

**HTTP = HyperText Transfer Protocol**

A protocol is simply a set of agreed-upon rules for communication.

HTTP defines how a client and server communicate:

```text id="8o9n9n"
Client
   │
   │ HTTP Request
   ▼
Server
   │
   │ HTTP Response
   ▼
Client
```

HTTP defines things such as:

* How requests are structured
* How responses are structured
* What methods mean
* How status is communicated
* How metadata is transferred
* How caching works
* How content is negotiated

---

# 2. Client–Server Model

HTTP follows the **client-server model**.

### Client

Initiates the request.

Examples:

* Browser
* Mobile application
* Frontend application
* Another backend service
* CLI tool

### Server

Receives the request, processes it, and returns a response.

```text id="3p9j5d"
          Request
Client ─────────────→ Server
Client ←───────────── Server
          Response
```

The client generally initiates HTTP communication.

This separation allows the client and server to evolve independently.

---

# 3. HTTP is Stateless

HTTP itself is **stateless**.

That means:

> Each request is treated independently.

The protocol itself does not automatically remember:

```text id="9p0n8h"
Request 1:
"I'm Yusuf."

        ↓

Request 2:
"Show me my profile."

HTTP doesn't automatically know
that both requests belong to Yusuf.
```

If an application needs continuity between requests, it uses additional mechanisms such as:

* Cookies
* Sessions
* Tokens
* JWTs

### Important

```text id="1n8z8e"
HTTP
  ↓
Stateless

Application
  ↓
Can build stateful behavior
using cookies/sessions/tokens
```

### Interview Question

**Is HTTP completely incapable of maintaining state?**

Not exactly.

HTTP itself is stateless, but applications can maintain state using mechanisms built around HTTP.

---

# 4. Where Does HTTP Fit?

HTTP operates at the **Application Layer**.

A simplified view:

```text id="zqv2mc"
Application
    │
   HTTP
    │
   TLS
    │
   TCP / QUIC
    │
   IP
    │
 Network
```

Backend engineers usually interact heavily with HTTP, while lower-level networking details are often abstracted by the operating system and runtime.

However, understanding those layers becomes important when debugging:

* Latency
* Connection problems
* Packet loss
* Network failures
* Performance issues

---

# 5. HTTP Needs Transport

HTTP doesn't directly handle every networking problem itself.

Traditionally:

```text id="5smq6b"
HTTP
 ↓
TCP
 ↓
IP
 ↓
Network
```

TCP provides things such as:

* Reliable delivery
* Ordered delivery
* Retransmission
* Flow control
* Congestion control

This means HTTP can focus on **application-level communication** instead of implementing reliable packet delivery itself.

---

# 6. TCP vs UDP

## TCP

TCP is:

* Connection-oriented
* Reliable
* Ordered
* Retransmitting
* Flow-controlled

Traditional HTTP versions relied on TCP.

```text id="0ch1dy"
HTTP
 ↓
TCP
 ↓
IP
```

## UDP

UDP is:

* Connectionless
* Lightweight
* Faster in some scenarios
* Not inherently reliable
* Not inherently ordered

HTTP/3 changes the underlying transport architecture by using **QUIC over UDP**.

```text id="8h7k8a"
HTTP/1.1
HTTP/2
   ↓
 TCP

HTTP/3
   ↓
 QUIC
   ↓
 UDP
```

---

# 7. Evolution of HTTP

HTTP has evolved largely to improve:

* Performance
* Connection efficiency
* Latency
* Multiplexing
* Compression
* Mobile/network performance

---

## HTTP/1.0

The older model was inefficient because requests could require separate TCP connections.

```text id="9m8t4f"
Request 1 → TCP Connection
Request 2 → TCP Connection
Request 3 → TCP Connection
```

Repeated connection establishment increases overhead.

---

# 8. HTTP/1.1

HTTP/1.1 introduced **persistent connections**.

Instead of creating a new connection for every request:

```text id="y5x0f3"
TCP Connection
 ├── Request 1
 ├── Request 2
 ├── Request 3
 └── Request 4
```

This significantly reduced connection overhead.

HTTP/1.1 also provides important features around:

* Caching
* Host headers
* Persistent connections
* Chunked transfer
* Content negotiation

### Problem

HTTP/1.1 can suffer from **Head-of-Line Blocking** at the HTTP request level.

A request earlier in the sequence can delay later requests.

---

# 9. HTTP/2

HTTP/2 introduced a major improvement:

## Multiplexing

Multiple requests and responses can share one TCP connection.

```text id="x6az3c"
             TCP Connection
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
    Request A  Request B  Request C
       ↓          ↓          ↓
   Response A Response B Response C
```

Instead of treating communication as one large sequential stream, HTTP/2 uses multiple logical streams.

### Major Features

* Multiplexing
* Binary framing
* Header compression
* Persistent connections

HTTP/2 uses **HPACK** for header compression.

### Important limitation

HTTP/2 still runs over TCP.

If TCP loses a packet, TCP must retransmit it before later data can be delivered correctly.

So transport-level **Head-of-Line Blocking** can still exist.

---

# 10. HTTP/3

HTTP/3 uses:

```text id="bb4o5f"
HTTP/3
  ↓
QUIC
  ↓
UDP
```

QUIC provides reliability and connection management at a higher layer while using UDP underneath.

### Benefits

* Reduced connection latency
* Better multiplexing
* Improved behavior under packet loss
* Avoidance of TCP-level head-of-line blocking
* Faster connection establishment

QUIC also supports mechanisms such as **0-RTT** for certain reconnection scenarios.

---

# 11. HTTP Version Comparison

| Feature                | HTTP/1.1      | HTTP/2      | HTTP/3      |
| ---------------------- | ------------- | ----------- | ----------- |
| Transport              | TCP           | TCP         | QUIC / UDP  |
| Persistent connections | ✅             | ✅           | ✅           |
| Multiplexing           | ❌             | ✅           | ✅           |
| Binary framing         | ❌             | ✅           | ✅           |
| Header compression     | Limited       | HPACK       | QPACK       |
| TCP HOL blocking       | N/A           | Yes         | No          |
| Modern focus           | Compatibility | Performance | Low latency |

### Interview Question

**Why did HTTP/3 move from TCP to UDP?**

Not because UDP itself is reliable.

Rather:

> QUIC builds the reliability and connection-management mechanisms needed by HTTP on top of UDP while avoiding some limitations of TCP.

---

# 12. Anatomy of an HTTP Request

A simplified HTTP request:

```text id="s4q5cd"
GET /api/users HTTP/1.1
Host: example.com
Accept: application/json
Authorization: Bearer <token>

```

An HTTP request consists of:

```text id="6mgl3d"
Request
 ├── Request Line
 ├── Headers
 ├── Blank Line
 └── Optional Body
```

---

# 13. Request Line

Example:

```text id="spx0qz"
GET /api/users HTTP/1.1
```

Contains:

```text id="1z4p6s"
GET        → Method
/api/users → Target / Path
HTTP/1.1   → HTTP Version
```

---

# 14. HTTP Headers

Headers contain metadata about the request or response.

Example:

```text id="7y4j0r"
Host: example.com
User-Agent: Chrome
Accept: application/json
Authorization: Bearer <token>
```

Headers can communicate:

* Authentication
* Content type
* Accepted formats
* Caching instructions
* Cookies
* Compression
* Client information
* Origin
* Connection behavior

Think of headers as the **metadata/control information surrounding the payload**.

---

# 15. Header Categories

Common categories include:

### Request Headers

Examples:

```text id="uw0y1x"
Authorization
User-Agent
Accept
Origin
```

### Representation Headers

Describe the representation/body.

```text id="1r6a6e"
Content-Type
Content-Length
Content-Encoding
```

### General / Control Information

Examples include:

```text id="w8a4h3"
Date
Connection
```

### Security Headers

Examples:

```text id="i3y0t6"
Strict-Transport-Security
Content-Security-Policy
X-Frame-Options
```

---

# 16. The Blank Line

The blank line separating headers from the body is important.

```text id="y4i3ly"
Headers
Header
Header
Header

Body
Body
Body
```

It tells the receiver:

> **The metadata is finished; the payload starts now.**

---

# 17. HTTP Request Body

The body contains the actual payload when required.

Example:

```text id="u1j6xw"
POST /users HTTP/1.1
Content-Type: application/json

{
  "name": "Yusuf",
  "age": 22
}
```

The body could contain:

* JSON
* Form data
* Multipart data
* Binary data
* Other representations

Not every HTTP request requires a body.

For example, a typical GET request may not have one.

---

# 18. HTTP Response

A response has a similar structure.

```text id="8t3c3m"
HTTP/1.1 200 OK
Content-Type: application/json

{
  "users": []
}
```

Structure:

```text id="q9v2nd"
Response
 ├── Status Line
 ├── Headers
 ├── Blank Line
 └── Body
```

---

# 19. HTTP Methods

HTTP methods communicate the **intent** of the request.

| Method  | Meaning                                  |
| ------- | ---------------------------------------- |
| GET     | Retrieve                                 |
| POST    | Create / Submit                          |
| PUT     | Replace                                  |
| PATCH   | Partially update                         |
| DELETE  | Remove                                   |
| HEAD    | Retrieve headers only                    |
| OPTIONS | Discover supported communication options |
| TRACE   | Diagnostic request                       |
| CONNECT | Establish a tunnel                       |

---

# 20. GET

Used to retrieve information.

```text id="fz8k1e"
GET /users/123
```

Ideally:

* Doesn't modify server state
* Can be cached
* Is safe
* Is idempotent

---

# 21. POST

Usually used to create a resource or submit data.

```text id="qv5z1h"
POST /users
```

```json
{
  "name": "Yusuf"
}
```

Repeated POST requests may create multiple resources.

Therefore POST is generally **not idempotent**.

---

# 22. PUT

PUT generally means **replace the target resource with the supplied representation**.

```text id="4ecyqf"
PUT /users/123
```

If the same PUT request is sent repeatedly, the resulting resource state should generally remain the same.

Therefore PUT is **idempotent**.

---

# 23. PATCH

PATCH performs a partial modification.

```text id="ly95z0"
PATCH /users/123
```

```json
{
  "name": "New Name"
}
```

Only the specified portion needs to change.

---

# 24. DELETE

Deletes a resource.

```text id="s2w5h0"
DELETE /users/123
```

DELETE is generally considered idempotent in HTTP semantics.

That doesn't necessarily mean every implementation will return exactly the same response each time.

It means repeated requests should lead to the same intended server state.

---

# 25. Idempotency

This is an important interview concept.

An operation is **idempotent** when performing it multiple times has the same intended effect on server state as performing it once.

Example:

```text id="e6k6na"
PUT /users/123
name = Yusuf
```

First request:

```text
name → Yusuf
```

Second request:

```text
name → Yusuf
```

Third request:

```text
name → Yusuf
```

The state remains the same.

Compare that with:

```text id="8y8o8s"
POST /orders
```

Repeated requests might create:

```text
Order #1
Order #2
Order #3
```

---

# 26. CORS 🌐

**CORS = Cross-Origin Resource Sharing**

Browsers enforce the **Same-Origin Policy**.

An origin consists of:

```text id="w0f7d1"
scheme + host + port
```

Example:

```text
https://example.com:443
```

If your frontend is:

```text id="p7h5w0"
https://frontend.example.com
```

and your API is:

```text id="k5y2m2"
https://api.example.com
```

they are different origins.

The browser therefore applies cross-origin restrictions.

---

# 27. Simple vs Preflighted Requests

Some cross-origin requests can be sent directly.

Others require a **preflight request**.

### Example

Suppose JavaScript wants:

```text id="0d7l3q"
DELETE /users/123

Authorization: Bearer abc
```

The browser may first send:

```text id="l8a7g9"
OPTIONS /users/123
Origin: https://frontend.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: Authorization
```

This is the **preflight**.

The browser is essentially asking:

> "Is this origin allowed to make this request using this method and these headers?"

---

# 28. CORS Response

The server may respond:

```text id="f0w3l9"
HTTP/1.1 204 No Content

Access-Control-Allow-Origin:
https://frontend.example.com

Access-Control-Allow-Methods:
GET, POST, DELETE

Access-Control-Allow-Headers:
Authorization
```

If the browser accepts the response, it sends the actual request.

```text id="g4q9r7"
OPTIONS
   ↓
Server permission
   ↓
DELETE
```

### Important

CORS is a **browser security mechanism**.

It is not:

* Authentication
* Authorization
* CSRF protection
* Encryption

---

# 29. HTTP Status Codes

Status codes communicate the result of a request.

```text id="h4q4b7"
1xx → Informational
2xx → Success
3xx → Redirection
4xx → Client Error
5xx → Server Error
```

---

## 1xx — Informational

The request has been received and processing is continuing.

Example:

```text
101 Switching Protocols
```

---

## 2xx — Success

### 200 OK

Request succeeded.

### 201 Created

A resource was successfully created.

### 204 No Content

Request succeeded but there is no response body.

Common for:

```text
DELETE
```

or successful preflight responses.

---

# 30. 3xx — Redirection

### 301

Moved permanently.

### 302

Temporary redirect.

### 304

Not Modified.

`304` is particularly important for caching.

---

# 31. 4xx — Client Errors

Common examples:

| Code | Meaning                                |
| ---- | -------------------------------------- |
| 400  | Bad Request                            |
| 401  | Unauthorized / authentication required |
| 403  | Forbidden                              |
| 404  | Not Found                              |
| 405  | Method Not Allowed                     |
| 409  | Conflict                               |
| 429  | Too Many Requests                      |

### 401 vs 403

```text id="0l6l7x"
401
→ Authentication problem

403
→ You are authenticated,
  but don't have permission
```

---

# 32. 5xx — Server Errors

Common examples:

| Code | Meaning               |
| ---- | --------------------- |
| 500  | Internal Server Error |
| 502  | Bad Gateway           |
| 503  | Service Unavailable   |
| 504  | Gateway Timeout       |

A useful distinction:

```text id="3c4w1h"
4xx
→ Request/client side problem

5xx
→ Server/infrastructure problem
```

# 33. HTTP Caching ⚡

Caching avoids repeatedly downloading or computing the same resource.

```text id="7k0f4s"
First Request
     ↓
   Server
     ↓
 Response
     ↓
 Browser Cache
```

Next time:

```text id="m2n0wy"
Request
   ↓
Cache
   ↓
Reuse
```

Caching can exist at multiple layers:

```text id="f8h3by"
Browser
   ↓
CDN
   ↓
Proxy
   ↓
Reverse Proxy
   ↓
API Gateway
   ↓
Application
```

---

# 34. Cache-Control

One of the most important caching headers.

Example:

```text id="2p0c6m"
Cache-Control: max-age=60
```

This tells the cache that the resource can be considered fresh for 60 seconds.

---

# 35. ETag

An ETag identifies a particular representation/version of a resource.

First request:

```text id="y0q0gk"
GET /app.js
```

Response:

```text id="7f8e8n"
200 OK
ETag: "v1-abc123"
```

The browser stores the resource and ETag.

Later:

```text id="6v9l3r"
GET /app.js
If-None-Match: "v1-abc123"
```

The server checks whether the resource has changed.

If it hasn't:

```text id="6d4k0j"
304 Not Modified
ETag: "v1-abc123"
```

The browser can reuse its cached copy.

---

# 36. ETag Flow

```text id="3b3lqy"
Browser                     Server
   │                           │
   │ GET /app.js               │
   ├──────────────────────────>│
   │                           │
   │ 200 OK + ETag             │
   │<──────────────────────────┤
   │                           │
   │ Store response + ETag     │
   │                           │
   │                           │
   │ GET + If-None-Match        │
   ├──────────────────────────>│
   │                           │
   │ 304 Not Modified          │
   │<──────────────────────────┤
   │                           │
   │ Use cached version        │
```

### Key idea

The server doesn't need to resend the entire resource if it hasn't changed.

---

# 37. Other Caching Headers

### Last-Modified

Indicates when the resource was last modified.

### If-Modified-Since

Client asks whether the resource changed after a specific time.

### Expires

Provides an expiration date/time.

### Cache-Control

Provides cache behavior rules.

---

# 38. Content Negotiation

The client and server can negotiate the representation of the resource.

Example:

```text id="kz5t6e"
Accept: application/json
```

The client is saying:

> "I prefer JSON."

Other headers can communicate preferences such as:

```text id="m4k3i7"
Accept
Accept-Language
Accept-Encoding
```

This allows the server to choose an appropriate representation.

---

# 39. Compression

Large responses can consume significant bandwidth.

Compression reduces the amount of data transferred.

```text id="z2c6f3"
Original Response
      ↓
  Compression
      ↓
Smaller Response
      ↓
    Network
      ↓
 Decompression
      ↓
Original Data
```

Common compression algorithms include:

* Gzip
* Deflate
* Brotli

Example:

```text
Content-Encoding: gzip
```

---

# 40. HTTPS 🔐

HTTPS is essentially:

```text id="v5k8wb"
HTTP
 +
TLS
```

```text id="v0eqt8"
HTTP
 ↓
TLS Encryption
 ↓
Internet
```

HTTPS provides:

### Confidentiality

Attackers shouldn't be able to read the encrypted traffic.

### Integrity

Attackers shouldn't be able to silently modify the traffic.

### Authentication

TLS certificates help the client verify the server's identity.

---

# 41. SSL vs TLS

SSL was the older security protocol.

Modern systems use **TLS**.

So technically:

```text id="1p3b8m"
HTTPS
   ↓
HTTP over TLS
```

not modern HTTP over SSL.

# ⭐ Key Takeaways

* **HTTP is an application-layer communication protocol.**
* HTTP itself is **stateless**.
* HTTP traditionally runs over **TCP**; HTTP/3 uses **QUIC over UDP**.
* HTTP/2 introduced **multiplexing and binary framing**.
* HTTP/3 reduces the impact of TCP-level Head-of-Line Blocking.
* An HTTP request contains a **method, target, headers, and optional body**.
* An HTTP response contains a **status code, headers, and optional body**.
* HTTP methods describe the **intent** of an operation.
* **PUT and DELETE are generally idempotent; POST generally isn't.**
* CORS is a **browser-enforced cross-origin mechanism**, not authentication.
* `OPTIONS` is commonly used for CORS preflight.
* `401` and `403` represent different authorization/authentication situations.
* `304 Not Modified` allows a client to reuse its cached resource.
* `ETag` and `If-None-Match` provide cache validation.
* HTTPS is **HTTP over TLS**.
* Understanding HTTP deeply is essential because almost every modern backend system builds on it.
