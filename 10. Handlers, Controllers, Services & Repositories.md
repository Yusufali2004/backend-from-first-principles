# 10. Handlers, Controllers, Services & Repositories 🧩

> **A good backend doesn't put everything inside the API route.**
>
> Each layer should have a clear responsibility so the system remains understandable, testable, and maintainable as it grows.

A typical backend request can be thought of as:

```text
Client
  ↓
HTTP Request
  ↓
Middleware
  ↓
Handler / Controller
  ↓
Service
  ↓
Repository
  ↓
Database
```

The important idea is **separation of concerns**.

---

# 1. Why Do We Need Different Layers?

Imagine a simple API:

```http
POST /users
```

The request needs to:

1. Read the HTTP request
2. Parse the body
3. Validate the input
4. Authenticate the user
5. Execute business rules
6. Save data
7. Return an HTTP response

You could put all of this into one function.

```text
POST /users
     ↓
One giant function
     ├── Parse
     ├── Validate
     ├── Auth
     ├── Business Logic
     ├── SQL
     ├── Error Handling
     └── Response
```

It might work initially.

But as the application grows, this becomes difficult to:

* Understand
* Test
* Modify
* Reuse
* Debug
* Maintain

Instead, we separate responsibilities.

```text
HTTP concerns
      ↓
Handler / Controller
      ↓
Business concerns
      ↓
Service
      ↓
Data concerns
      ↓
Repository
```

---

# 2. The Three Important Layers

A useful mental model is:

```text
┌─────────────────────────────┐
│ Presentation / Transport    │
│                             │
│ Handler / Controller        │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│ Business Logic               │
│                             │
│ Service                     │
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│ Data Access                 │
│                             │
│ Repository                  │
└──────────────┬──────────────┘
               ↓
          Database
```

Each layer answers a different question.

### Handler / Controller

> **How do I communicate over HTTP?**

### Service

> **What should the application actually do?**

### Repository

> **How do I store or retrieve the data?**

---

# 3. Handler / Controller

The handler or controller sits at the HTTP boundary.

It deals with things such as:

* HTTP method
* URL
* Headers
* Query parameters
* Path parameters
* Request body
* HTTP status codes
* HTTP response formatting

The handler should primarily be concerned with **transport**, not business rules.

---

# 4. Example Handler

Suppose we have:

```http
POST /users
```

A handler might conceptually do:

```text
Request
  ↓
Read body
  ↓
Deserialize
  ↓
Validate
  ↓
Call UserService
  ↓
Receive result
  ↓
Return HTTP response
```

Pseudo-code:

```javascript
async function createUser(req, res) {
    const input = parseRequest(req);

    validate(input);

    const user = await userService.createUser(input);

    return res.status(201).json(user);
}
```

Notice what the handler **doesn't** do.

It doesn't contain:

```text
SQL
Password hashing rules
Business policies
Database queries
Complex workflows
```

Those belong elsewhere.

---

# 5. Handler = HTTP Adapter

A useful way to think about a handler:

```text
HTTP World
    ↓
Handler
    ↓
Application World
```

The handler translates between the HTTP protocol and your application's internal functions.

For example:

```text
HTTP Request
    ↓
{
   name: "Yusuf"
}
    ↓
Handler
    ↓
createUser(input)
```

Then the result comes back:

```text
Service Result
    ↓
Handler
    ↓
HTTP Response
```

```http
201 Created
```

---

# 6. Why Should Handlers Stay Thin?

Consider this:

```javascript
async function createUser(req, res) {

    // parse request

    // validate

    // hash password

    // check duplicate user

    // calculate something

    // query database

    // insert user

    // send email

    // update analytics

    // build response

}
```

This handler has become responsible for everything.

That creates a **God function**.

Instead:

```text
Handler
  ↓
User Service
  ↓
User Repository
```

The handler remains small.

---

# 7. Controller vs Handler

These terms are often used interchangeably, but they can have slightly different meanings depending on the framework and architecture.

Conceptually:

### Handler

A function that handles a request.

```text
Request
 ↓
Handler
 ↓
Response
```

### Controller

Usually represents the HTTP/presentation layer more structurally.

```text
Controller
├── createUser()
├── getUser()
├── updateUser()
└── deleteUser()
```

The exact terminology is framework-dependent.

The important concept is the responsibility:

> **Handle transport-level concerns and delegate actual application work.**

---

# 8. Service Layer

The service layer contains the **business logic**.

This is the layer that answers:

> What should happen?

For example:

```text
Create Order
```

The business rules might be:

```text
1. Check user exists
2. Check product exists
3. Check inventory
4. Calculate price
5. Apply discount
6. Create order
7. Reduce inventory
8. Send confirmation
```

That isn't HTTP logic.

It's business logic.

Therefore it belongs in a service.

---

# 9. Example Service

```javascript
async function createOrder(userId, items) {

    const user = await userRepository.findById(userId);

    if (!user) {
        throw new UserNotFoundError();
    }

    const products = await productRepository.getProducts(items);

    validateInventory(products, items);

    const total = calculateTotal(products, items);

    const order = await orderRepository.create({
        userId,
        items,
        total
    });

    return order;
}
```

The service doesn't care whether it was called by:

```text
REST
gRPC
GraphQL
Background Job
CLI
Test
```

That's a major advantage.

---

# 10. Services Should Be API-Agnostic

This is one of the most important ideas from this chapter.

Suppose your service is:

```text
createOrder()
```

It shouldn't need to know:

```text
HTTP status = 201
GET /orders
POST /orders
Express request object
FastAPI request object
```

Instead:

```text
HTTP Handler
      ↓
createOrder()
```

or:

```text
Background Job
      ↓
createOrder()
```

or:

```text
gRPC Handler
      ↓
createOrder()
```

The same business logic can be reused.

The available source explicitly highlights this property: services should remain API-agnostic so the same business logic can work from REST, gRPC, jobs, or tests.

---

# 11. Repository Layer

The repository handles **data access**.

Its responsibility is essentially:

> How do I communicate with the persistence layer?

For example:

```text
UserRepository
├── findById()
├── findByEmail()
├── create()
├── update()
└── delete()
```

It might internally use:

```text
PostgreSQL
MySQL
MongoDB
Redis
```

The service shouldn't need to know the exact SQL used.

---

# 12. Example Repository

```javascript
async function findUserById(id) {

    return db.query(
        "SELECT * FROM users WHERE id = $1",
        [id]
    );
}
```

The repository is concerned with:

```text
SQL
Queries
Database connections
Persistence
Mapping database records
```

It should not contain business decisions.

---

# 13. Repository ≠ Business Logic

Suppose the requirement is:

> A user can place an order only if their account is active.

This is business logic.

It belongs in:

```text
OrderService
```

Not:

```text
OrderRepository
```

The repository should simply retrieve the relevant data.

```text
Service
   ↓
"Find user"
   ↓
Repository
   ↓
Database
```

Then:

```text
Service
   ↓
"Is user active?"
```

The source specifically describes repositories as data-access-only abstractions that should not contain business rules or orchestration.

---

# 14. The Complete Flow

Suppose the client sends:

```http
POST /orders
```

with:

```json
{
  "productId": 10,
  "quantity": 2
}
```

The flow becomes:

```text
Client
  ↓
HTTP Request
  ↓
Middleware
  ↓
Handler
  ↓
Order Service
  ↓
Product Repository
  ↓
Database
  ↓
Order Repository
  ↓
Database
  ↓
Order Service
  ↓

  ↓

```

Each component has a clear job.

# 15. Middleware vs Handler

Middleware and handlers are also different.

### Middleware

Usually handles **cross-cutting concerns**.

Examples:

```text
Authentication
Authorization
Logging
Tracing
Rate Limiting
CORS
Global error handling
```

### Handler

Handles the specific endpoint.

Example:

```text
POST /orders
GET /users/:id
DELETE /products/:id
```

A useful mental model:

```text
Request
  ↓
Middleware
  ↓
Middleware
  ↓
Handler
  ↓
Service
```

---

# 16. Cross-Cutting Concerns

A cross-cutting concern is something that applies across many parts of the application.

For example, logging.

Without middleware:

```text
createUser()
   └── logging

createOrder()
   └── logging

deleteUser()
   └── logging

getProduct()
   └── logging
```

You would repeat the same logic everywhere.

With middleware:

```text
             Request
                ↓
          Logging Middleware
                ↓
        ┌───────┼────────┐
        ↓       ↓        ↓
      User    Order    Product
```

One concern is handled centrally.

---

# 17. Authentication Middleware

Another example:

```text
Request
   ↓
Authentication Middleware
   ↓
Valid?
 ┌─┴─┐
No  Yes
↓    ↓
401  Handler
```

The handler doesn't need to repeatedly implement:

```text
Read token
Verify token
Find user
```

The middleware establishes the authenticated context first.

---

# 18. Request Context

Middleware can derive information about a request and place it into request context.

For example:

```text
Authentication Middleware
        ↓
verify token
        ↓
userId = 123
        ↓
Request Context
```

Then:

```text
Handler
   ↓
Service
```

can use:

```text
userId = 123
```

without parsing the authentication credential again.

The source describes request context as trusted per-request state useful for metadata such as user ID and request ID.

---

# 19. Why Request Context Matters

Suppose:

```text
Request ID = req_abc123
User ID = 42
Trace ID = trace_xyz
```

These values belong to **this request**.

```text
Request A
   ↓
Context A

Request B
   ↓
Context B
```

They should not be global state.

This is important for:

* Security
* Logging
* Tracing
* Debugging
* Request-specific behavior

---

# 20. Error Handling

Another important responsibility is deciding where errors should be handled.

Suppose the repository encounters:

```text
Database unavailable
```

The repository can return/throw an error.

The service can decide whether that error affects business logic.

The handler can translate the final application result into an HTTP response.

```text
Repository
    ↓
DatabaseError
    ↓
Service
    ↓
Application Error
    ↓
Handler / Global Error Handler
    ↓
HTTP Response
```

For example:

```http
500 Internal Server Error
```

---

# 21. Don't Leak Infrastructure Details

Suppose the database returns:

```text
PostgresError:
duplicate key value violates unique constraint
```

Sending this directly to the client is usually a bad idea.

Instead:

```text
Database Error
      ↓
Repository
      ↓
Domain/Application Error
      ↓
HTTP Handler
      ↓
409 Conflict
```

The client receives an appropriate API-level error rather than an internal database implementation detail.

# 23. What Should NOT Happen?

## Bad Architecture

```text
Handler
   ↓
SQL
   ↓
Business Rules
   ↓
HTTP Response
```

Everything is mixed together.

---

## Better Architecture

```text
Handler
   ↓
Service
   ↓
Repository
   ↓
Database
```

with middleware surrounding the request pipeline.

```text
Middleware
    ↓
Handler
    ↓
Service
    ↓

```

# 24. Why Separation Helps Testing

Suppose business logic is inside an HTTP handler.

To test it, you may need to:

```text
Create HTTP request
 ↓
Create response
 ↓
Create framework context
 ↓
Mock everything
 ↓
Finally reach business logic
```

That's unnecessarily complicated.

If business logic is in a service:

```text
service.createOrder(input)
```

you can test it directly.

```text
Test
 ↓
Service
 ↓
Mock Repository
```

No HTTP server required.

---

# 25. Service Testing

Imagine:

```javascript
createOrder(userId, items)
```

You can test:

```text
✓ User exists
✓ Product exists
✓ Inventory sufficient
✓ Correct price
✓ Discount applied
✓ Order created
```

without worrying about:

```text
HTTP headers
HTTP methods
JSON parsing
Status codes
```

This makes tests faster and more focused.

---

# 26. Repository Testing

Repositories can be tested separately.

For example:

```text
findUserById()
```

can be tested against:

```text
Test Database
```

or using appropriate mocks depending on the test.

The repository test is about:

```text
Does the data access work correctly?
```

Not:

```text
Is this user allowed to place an order?
```

---

# 27. Reusability

Suppose today you have:

```text
REST API
```

Tomorrow you add:

```text
gRPC API
```

If the business logic is trapped inside REST controllers:

```text
REST Controller
    ↓
Business Logic
```

you may need to duplicate it.

With a service layer:

```text
REST Handler ───┐
                ↓
             Service
                ↑
gRPC Handler ───┘
```

Both interfaces reuse the same business logic.

---

# 28. Background Jobs

The same principle applies to background processing.

Suppose:

```text
OrderService.createOrder()
```

can be called from:

```text
REST API
gRPC
Background Job
CLI
Tests
```

```text
             REST
               │
             gRPC
               │
          Background Job
               │
              CLI
               │
               ▼
            Service
               │
               ▼
          Repository
```

The business logic doesn't care who called it.

This is one of the strongest reasons to keep services API-agnostic.

---

# 29. Dependency Direction

A useful architecture is:

```text
Handler
   ↓
Service
   ↓
Repository
```

Dependencies should generally flow toward lower-level implementation details.

The service shouldn't depend directly on:

```text
Express request
HTTP response
```

Instead:

```text
Service
 ↓
Application concepts
```

This keeps the core logic independent from the transport layer.

---

# 30. Dependency Injection

One way to keep these layers loosely coupled is dependency injection.

Instead of:

```javascript
class UserService {

    userRepository = new UserRepository();

}
```

you can conceptually do:

```javascript
class UserService {

    constructor(userRepository) {
        this.userRepository = userRepository;
    }

}
```

Then:

```text
Production
   ↓
PostgresUserRepository

Testing
   ↓
FakeUserRepository
```

The service doesn't need to know which implementation it received.

---

# 31. Repository Interface

You can define the behavior expected from a repository:

```text
UserRepository

findById(id)
findByEmail(email)
create(user)
update(user)
delete(id)
```

Then implementations can vary:

```text
              UserRepository
                    │
           ┌────────┴────────┐
           ↓                 ↓
 PostgresRepository     InMemoryRepository
```

This is particularly useful for testing and replacing infrastructure.

---

# 32. Don't Over-Abstract

Separation of concerns is useful.

But abstraction for the sake of abstraction can make code harder to understand.

For a tiny application:

```text
Handler
   ↓
Database
```

might be perfectly reasonable.

You don't necessarily need:

```text
Controller
Service
UseCase
Domain
Repository
DAO
Gateway
Adapter
Factory
```

for a 200-line project.

The goal isn't:

> **Create as many layers as possible.**

The goal is:

> **Create boundaries where different responsibilities actually need to be separated.**

```text

→ Thin
```

Think:

```text

"Here is what the application should do."
```

# 🧠 Interview Mental Models

### What does a handler do?

> **Handles transport-specific concerns such as HTTP input/output and delegates application work to the service layer.**

### What does a service do?

> **Contains business logic and should ideally remain independent of the transport mechanism.**

### What does a repository do?

> **Abstracts data access and persistence without containing business rules.**

### What does middleware do?

> **Handles cross-cutting concerns that apply across requests, such as authentication, logging, tracing, rate limiting, and error handling.**

# ⚠️ Interview Traps

### ❌ "The service layer is just another function between controller and database."

### ✅

> The service layer exists to isolate **business rules and application workflows** from transport and persistence concerns.

---

### ❌ "The repository contains business logic because it queries the database."

### ✅

> The repository should focus on **data access and persistence**. Business decisions belong in the service/domain layer.

---

### ❌ "Controllers should contain all the logic because that's where the request arrives."

### ✅

> Controllers should primarily translate between the transport layer and application logic. Keeping them thin improves testability and maintainability.

---

### ❌ "Middleware is only for authentication."

### ✅

> Middleware is useful for cross-cutting concerns such as authentication, logging, tracing, rate limiting, CORS, and global error handling.

---

### ❌ "More layers always means better architecture."

### ✅

> Layers should be introduced when they provide meaningful separation of responsibilities. Excessive abstraction can make simple systems harder to understand.

# 🔥 Core Takeaways

* **Handlers/controllers belong to the transport/presentation boundary.**
* They should primarily handle HTTP-specific concerns.
* **Services contain business logic.**
* Services should ideally be **API-agnostic**.
* The same service can potentially be called by REST, gRPC, background jobs, CLI tools, or tests.
* **Repositories abstract persistence and data access.**
* Repositories should not contain business rules or application orchestration.
* **Middleware handles cross-cutting concerns** such as authentication, logging, tracing, rate limiting, and global error handling.
* Request context provides request-scoped information such as user ID and request ID.
* Separating these responsibilities makes systems easier to test, change, and maintain.
* Dependency injection can reduce coupling between services and infrastructure.
* Don't create unnecessary layers just because an architecture diagram has them.
* The goal is **clear responsibility boundaries**, not maximum abstraction.

> **The interview-level mental model:**
>
> **Handler = transport.
> Service = business.
> Repository = persistence.
> Middleware = cross-cutting concerns.**
>
> When these boundaries are clear, the business logic can survive changes in HTTP frameworks, databases, protocols, and infrastructure without being rewritten.
