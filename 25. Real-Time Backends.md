# 25. Real-Time Backends ⚡

> Real-time backends are systems where the server needs to **push information to clients as events happen**, rather than forcing the client to repeatedly ask for updates.
>
> The key idea is moving from:
>
> ```text
> Client → Server → Response
> ```
>
> to systems where communication can continue after the initial request:
>
> ```text
> Client ←→ Server
> ```

---

# 1. Why Do We Need Real-Time Systems?

Traditional HTTP APIs usually work like this:

```text
Client
  │
  │ GET /messages
  ↓
Server
  │
  │ Response
  ↓
Client
```

If the client wants to know whether something changed, it has to ask again.

For example:

```text
Client → "Any new messages?"
Server → "No"

Client → "Any new messages?"
Server → "No"

Client → "Any new messages?"
Server → "Yes"
```

This is inefficient when updates need to appear immediately.

Real-time systems allow:

```text
Client
   ↑
   │ New message
   │
Server
```

The server can proactively communicate changes.

---

# 2. Common Real-Time Applications

Real-time communication is useful for:

```text
Chat applications
Notifications
Live dashboards
Online gaming
Collaborative editing
Stock/market updates
Live sports scores
Location tracking
Ride-sharing
Delivery tracking
IoT systems
Live auctions
```

The requirement is usually:

> **When something changes, interested clients should know quickly.**

---

# 3. Polling

The simplest approach is **polling**.

The client repeatedly sends requests:

```text
Client
  │
  │ GET /notifications
  ↓
Server
  │
  ↓
Client

(wait)

Client
  │
  │ GET /notifications
  ↓
Server
```

Example:

```text
Every 5 seconds:
"Do I have new messages?"
```

---

# 4. Why Polling Is Inefficient

Suppose:

```text
100,000 users
```

poll every:

```text
5 seconds
```

That's roughly:

```text
100,000 / 5
= 20,000 requests/second
```

Even when nothing has changed.

```text
Client → Server
       "Anything new?"

Server → "No"

Client → Server
       "Anything new?"

Server → "No"
```

A huge amount of traffic produces no useful information.

---

# 5. Long Polling

A better approach is **long polling**.

The client asks:

```text
Client
  │
  │ GET /messages
  ↓
Server
```

Instead of immediately responding:

```text
Server
 ↓
WAIT
```

The server holds the request until:

```text
New event occurs
```

Then:

```text
Server
 ↓
Response
 ↓
Client
```

The client can immediately make another request.

---

# 6. Long Polling Flow

```text
Client
   │
   │ Request
   ↓
Server
   │
   │ WAIT...
   │
   │ New event
   ↓
Response
   ↓
Client
   │
   │ New long-poll request
   ↓
Server
```

This reduces unnecessary empty responses.

But it still relies on repeated HTTP requests and open connections.

---

# 7. Server-Sent Events (SSE)

SSE provides a persistent HTTP connection where the server can continuously send events to the client.

```text
Client
   │
   │ HTTP connection
   ↓
Server
   │
   ├── Event 1
   ├── Event 2
   ├── Event 3
   └── Event 4
```

The important characteristic:

> **Communication is primarily server → client.**

---

# 8. SSE Example

Imagine a stock dashboard:

```text
Client
   │
   │ Connect
   ↓
Server
   │
   ├── PRICE_UPDATE
   ├── PRICE_UPDATE
   ├── PRICE_UPDATE
   └── PRICE_UPDATE
```

The browser doesn't need to repeatedly ask:

```text
"What's the latest price?"
```

The server can push updates.

---

# 9. When Is SSE Useful?

SSE is particularly useful when you need:

```text
Server
   ↓
Client
```

Examples:

```text
Live notifications
Live dashboards
Progress updates
News feeds
Monitoring
Streaming status
```

If you need full two-way communication, WebSockets are usually a better fit.

---

# 10. WebSockets ⭐⭐⭐

WebSockets provide a persistent, two-way communication channel.

```text
Client ←────────→ Server
```

Both sides can send messages whenever necessary.

Unlike traditional request/response HTTP:

```text
Client → Request
Server → Response
```

you can have:

```text
Client → Message
Server → Message
Server → Message
Client → Message
Server → Message
```

over the same persistent connection.

---

# 11. WebSocket Connection

The general lifecycle:

```text
Client
  │
  │ HTTP request
  ↓
Server
  │
  │ Upgrade
  ↓
WebSocket Connection
  │
  ├───────────────┐
  ↓               ↓
Client          Server
  ↕               ↕
  └───────────────┘
```

Once established, both sides can exchange messages.

---

# 12. Why WebSockets?

Imagine a chat application.

With normal HTTP:

```text
Client
 ↓
POST /messages

Server
 ↓
Message stored
```

But how does another user immediately receive it?

They need to:

```text
GET /messages
```

again and again.

With WebSockets:

```text
User A
   │
   │ "Hello"
   ↓
Server
   │
   │ Push
   ↓
User B
```

No repeated polling is necessary.

---

# 13. Real-Time Chat Architecture

A basic architecture:

```text
                    WebSocket
User A ───────────────┐
                      ↓
                   Backend
                      ↓
User B ───────────────┘
                    WebSocket
```

The backend receives:

```text
User A
"Hello"
```

and forwards it to User B.

---

# 14. But Where Is the Message Stored?

Real-time communication doesn't replace persistent storage.

A chat system might use:

```text
WebSocket
    ↓
Backend
    ├── PostgreSQL
    │      ↓
    │   Message history
    │
    └── Redis
           ↓
       Real-time coordination
```

Think:

```text
WebSocket
→ How do we communicate now?

Database
→ How do we remember it?
```

---

# 15. Connection State

A WebSocket server needs to know:

```text
Which user
        ↓
is connected through
        ↓
which connection?
```

Conceptually:

```text
User 123
   ↓
Socket A

User 456
   ↓
Socket B

User 789
   ↓
Socket C
```

The server maintains connection information.

---

# 16. Authentication

Real-time connections still need authentication.

A client shouldn't simply say:

```text
"I am User 123."
```

The server needs to verify identity.

Possible approaches include:

```text
Session
JWT
Authentication cookie
Short-lived connection token
```

The exact mechanism depends on the application.

---

# 17. Authorization Still Matters

Authentication answers:

> Who are you?

Authorization answers:

> What are you allowed to do?

For example:

```text
User A
 ↓
Connect to chat room X
```

doesn't automatically mean:

```text
User A
 ↓
Can access private chat room Y
```

Every real-time action that matters should be authorized appropriately.

---

# 18. Heartbeats

What happens if the network disappears?

The server might think:

```text
User connected ✓
```

while the client is actually gone.

Real-time protocols often use **heartbeats** or ping/pong mechanisms to detect dead connections.

Conceptually:

```text
Server → Ping
Client → Pong
```

If responses stop:

```text
Connection considered dead
 ↓
Clean up connection
```

---

# 19. Why Connection Cleanup Matters

Imagine:

```text
1 million connections
```

but your server never removes dead ones.

You can eventually get:

```text
Memory usage ↑
Connection count ↑
File descriptors ↑
CPU usage ↑
```

Eventually:

```text
Server 💥
```

Therefore:

> **Connection lifecycle management is a critical part of real-time backend design.**

---

# 20. Reconnection

Mobile networks are unreliable.

A user might:

```text
Wi-Fi
 ↓
Mobile network
 ↓
No network
 ↓
Wi-Fi
```

The WebSocket connection can break.

A good client should generally attempt:

```text
Disconnect
 ↓
Wait
 ↓
Reconnect
 ↓
Authenticate
 ↓
Resume
```

---

# 21. Exponential Backoff

Don't reconnect aggressively:

```text
Immediately
Immediately
Immediately
Immediately
...
```

Instead:

```text
1 sec
 ↓
2 sec
 ↓
4 sec
 ↓
8 sec
 ↓
16 sec
```

This is **exponential backoff**.

Usually a maximum delay is applied.

---

# 22. Why Reconnection Can Be Dangerous

Imagine a server crashes.

There are:

```text
500,000 clients
```

connected.

If all clients immediately reconnect:

```text
500,000 clients
        ↓
      Server
        ↓
       💥
```

This can create a **thundering herd**.

Backoff and jitter help distribute reconnection attempts.

---

# 23. Jitter

Instead of:

```text
All clients reconnect at 8 seconds
```

add randomness:

```text
Client A → 7.2 sec
Client B → 8.5 sec
Client C → 9.1 sec
Client D → 7.8 sec
```

This spreads the load.

---

# 24. WebSockets and Load Balancers

Now imagine:

```text
                 Load Balancer
                /      |      \
               ↓       ↓       ↓
             Server A Server B Server C
```

Users can connect to different servers.

Suppose:

```text
User A → Server A
User B → Server C
```

User A sends:

```text
"Hello User B"
```

Server A needs a way to tell Server C.

This creates a distributed-systems problem.

---

# 25. Pub/Sub ⭐⭐⭐

A common solution is **publish/subscribe**.

```text
                 Redis Pub/Sub
                /            \
               ↓              ↓
          Server A          Server C
             ↑                 ↑
          User A             User B
```

Flow:

```text
User A
 ↓
Server A
 ↓
Publish event
 ↓
Redis
 ↓
Server C
 ↓
User B
```

Now the application servers can coordinate.

---

# 26. Why Redis Is Useful Here

Redis can act as a fast coordination layer.

For example:

```text
User A sends message
       ↓
Server A
       ↓
Redis Pub/Sub
       ↓
Server B
       ↓
User B
```

The database can still persist the message:

```text
PostgreSQL
 ↓
Permanent history
```

So:

```text
Redis
→ real-time coordination

PostgreSQL
→ durable persistence
```

---

# 27. Scaling WebSockets

A single server has limits.

Instead:

```text
             Load Balancer
             /     |     \
            ↓      ↓      ↓
         WS-1    WS-2    WS-3
            \      |      /
             \     |     /
               Redis
```

Each server handles its own connected clients.

Redis or another messaging infrastructure allows events to move between servers.

---

# 28. Sticky Sessions

A load balancer can sometimes use **sticky sessions** so a particular client continues reaching the same backend server.

```text
User A
 ↓
Load Balancer
 ↓
Server 2
```

Future requests/connections from that client are routed consistently to Server 2.

This can simplify some stateful connection handling.

But:

> **Sticky sessions don't solve cross-server communication.**

You may still need shared infrastructure.

---

# 29. Stateless vs Stateful

Normal HTTP APIs can often be designed to be stateless:

```text
Request
 ↓
Any server
 ↓
Response
```

WebSockets introduce long-lived connection state:

```text
Connection
 ↓
Specific server
 ↓
User
```

The connection itself has state.

This makes horizontal scaling more complicated.

---

# 30. Presence

Chat applications often need to answer:

```text
Is User 123 online?
```

This is called **presence**.

Conceptually:

```text
User
 ↓
Connection
 ↓
Presence State
```

You might track:

```text
user_id
last_seen
connection_count
status
```

A fast store such as Redis can be useful for ephemeral presence state.

---

# 31. Online Doesn't Always Mean One Connection

A user may have:

```text
Laptop
Phone
Tablet
```

all connected.

So:

```text
User 123
 ├── Socket A
 ├── Socket B
 └── Socket C
```

If one disconnects:

```text
Socket A ❌
Socket B ✓
Socket C ✓
```

the user is still online.

Therefore presence should often track **connections**, not simply a boolean:

```text
online = true
```

---

# 32. Rooms

Real-time systems commonly group connections into rooms/channels.

Example:

```text
Room: engineering
 ├── User A
 ├── User B
 └── User C

Room: gaming
 ├── User D
 └── User E
```

When an event happens:

```text
Room "engineering"
 ↓
Broadcast
 ↓
A + B + C
```

---

# 33. Broadcasting

Broadcast means sending an event to many clients.

```text
Server
  │
  ├──→ User A
  ├──→ User B
  ├──→ User C
  └──→ User D
```

Examples:

```text
New announcement
Live score update
System notification
Room message
```

---

# 34. Multicast / Targeted Events

Not every event should go to everyone.

You might have:

```text
Broadcast
→ Everyone

Room broadcast
→ Everyone in room

User event
→ One user

Device event
→ One device
```

Choosing the right scope prevents unnecessary traffic.

---

# 35. Event Design

A real-time event should contain enough information for the client to understand it.

For example:

```json
{
  "type": "message.created",
  "id": "msg_123",
  "roomId": "room_42",
  "senderId": "user_10",
  "timestamp": "...",
  "data": {
    "text": "Hello"
  }
}
```

The important part is having a clear event contract.

---

# 36. Event Types

You might define:

```text
message.created
message.updated
message.deleted

user.joined
user.left
user.typing

notification.created

order.updated
payment.completed
```

This makes the protocol easier to reason about.

---

# 37. Event IDs

Events should often have unique identifiers:

```text
eventId = evt_12345
```

Why?

Because networks fail.

A client may receive:

```text
event_123
```

twice.

If the client can identify the event:

```text
event_123
```

it can avoid processing the same event twice where appropriate.

This leads to **idempotency**.

---

# 38. Ordering

Suppose:

```text
Message A
Message B
Message C
```

is sent in that order.

The client might receive:

```text
A
C
B
```

in a distributed system.

If ordering matters, you need an ordering strategy.

For example:

```text
sequence_number
```

```text
A → 101
B → 102
C → 103
```

The client can detect:

```text
101
103
```

and realize:

```text
102 is missing
```

---

# 39. Delivery Guarantees

A real-time system should consider:

```text
At-most-once
At-least-once
Exactly-once
```

---

## At-Most-Once

The event is delivered:

```text
0 or 1 time
```

Potentially lost.

```text
Send
 ↓
Failure
 ↓
No retry
```

---

## At-Least-Once

The event is retried until delivery is likely.

But duplicates can occur:

```text
A
A
```

Therefore consumers should often be idempotent.

---

## Exactly-Once

Sounds ideal:

```text
Exactly one processing
```

but achieving true exactly-once semantics across distributed systems is difficult and often expensive.

In practice, systems frequently use:

```text
At-least-once delivery
+
Idempotent processing
```

---

# 40. Message Acknowledgements

A client may acknowledge receipt:

```text
Server
 ↓
Event
 ↓
Client
 ↓
ACK
```

If the server doesn't receive the ACK:

```text
Retry
```

This can support stronger delivery guarantees.

---

# 41. Replaying Missed Events

Suppose:

```text
Client disconnects
```

while these events happen:

```text
Event 101
Event 102
Event 103
```

When the client reconnects:

```text
Client → "I last received 100."
```

The server can potentially provide:

```text
101
102
103
```

This requires events to be retained somewhere rather than existing only in memory.

---

# 42. Event Log Architecture

A more durable real-time system can use an event stream:

```text
Producer
   ↓
Event Stream
   ↓
Consumers
```

Example:

```text
Application
   ↓
Kafka / Stream
   ↓
WebSocket Workers
   ↓
Clients
```

Now events can potentially be replayed.

This is different from a simple ephemeral Pub/Sub mechanism.

---

# 43. Pub/Sub vs Message Streams

### Pub/Sub

```text
Publisher
   ↓
Subscribers
```

If a subscriber is disconnected, the event may simply be missed depending on the system.

Good for:

```text
Ephemeral notifications
Presence
Real-time coordination
```

### Durable stream

```text
Producer
   ↓
Persistent event log
   ↓
Consumer
```

Consumers can potentially resume from a previous position.

Good for:

```text
Event processing
Analytics
Durable event delivery
Replay
```

# 44. WebSocket vs SSE vs Polling

|                       | Polling        | SSE         | WebSocket            |
| --------------------- | -------------- | ----------- | -------------------- |
| Persistent connection | ❌              | ✅           | ✅                    |
| Server → Client       | ✅              | ✅           | ✅                    |
| Client → Server       | Normal HTTP    | Normal HTTP | ✅                    |
| Two-way realtime      | ❌              | ❌           | ✅                    |
| Simplicity            | High           | Medium      | Medium/High          |
| Best for              | Simple updates | Server push | Interactive realtime |

# 45. When Should You Use WebSockets?

Use WebSockets when you need:

```text
Client ↔ Server
```

communication with low latency.

Examples:

```text
Chat
Gaming
Collaborative applications
Interactive dashboards
Live location
Trading interfaces
```

---

# 46. When Should You Use SSE?

Use SSE when the primary direction is:

```text
Server → Client
```

Examples:

```text
Notifications
Live feeds
Progress updates
Monitoring dashboards
```

It can be simpler than WebSockets when client-to-server realtime communication isn't needed.

# 47. When Is Polling Enough?

Don't automatically use WebSockets.

If the requirement is:

```text
Update every 30 seconds
```

polling might be perfectly adequate.

Architecture should match requirements.

```text
Simple requirement
→ Simple solution
```

# 52. Backpressure in Real-Time Systems ⭐

Suppose:

```text
Producer
→ 10,000 events/sec
```

but a client can process only:

```text
1,000 events/sec
```

What happens?

```text
Events
 ↓
Queue grows
 ↓
Memory grows
 ↓
Latency grows
 ↓
System becomes unhealthy
```

This is **backpressure**.

Real-time systems need strategies such as:

```text
Rate limiting
Buffering
Dropping non-critical updates
Batching
Sampling
Throttling
```

---

# 53. Not Every Event Needs Delivery

Consider a live location:

```text
Driver moves:
A → B → C → D → E
```

If the client hasn't processed:

```text
B
C
D
```

it may only care about:

```text
E
```

For certain state updates, you can safely discard stale intermediate updates.

This is very different from:

```text
Payment completed
```

where every event matters.

---

# 54. State vs Events

This is an important design distinction.

### State

```text
Driver location = E
```

If you miss:

```text
B
C
D
```

you can simply receive the latest state.

### Event

```text
Payment completed
```

You cannot simply discard it.

So:

> **Whether an update is state or an event affects the delivery strategy.**

# 58. Real-Time System Failure

Consider:

```text
WebSocket Server
      ↓
Redis
      ↓
PostgreSQL
```

What happens if Redis fails?

Possible consequences:

```text
Cross-server events stop
```

But:

```text
Existing local connections
```

might still be alive.

This is an example of **partial failure**.

A production real-time system must consider what happens when individual components fail.

---

# 59. Graceful Shutdown

This connects directly to your previous chapter.

Suppose a WebSocket server needs to shut down.

Don't simply:

```text
kill process
```

because thousands of clients could suddenly disconnect.

A graceful approach:

```text
Stop accepting new connections
        ↓
Notify/close existing connections
        ↓
Allow important work to finish
        ↓
Close Redis/database connections
        ↓
Shutdown
```

Clients then reconnect to another server.

# 🧠 Interview Mental Models

### What is a real-time backend?

> A backend that can deliver updates to clients with low latency as events or state changes occur, rather than requiring clients to repeatedly poll for changes.

### Polling vs WebSockets?

```text
Polling
→ client repeatedly asks

WebSocket
→ persistent two-way connection
```

### SSE vs WebSocket?

```text
SSE
→ primarily server → client

WebSocket
→ client ↔ server
```

### Why is WebSocket scaling difficult?

> WebSocket connections are long-lived and stateful, so connections are distributed across servers. When an event needs to reach a client connected to another server, the servers need shared coordination such as Pub/Sub or a messaging system.

### Why use Redis?

> Redis can provide fast ephemeral state and cross-server coordination, such as presence and Pub/Sub.

### Why use Kafka/event streams?

> A durable event stream can retain events and allow consumers to process or replay them, unlike purely ephemeral Pub/Sub.

# ⚠️ Interview Traps

### ❌ "Real-time means zero latency."

No.

Real-time generally means the system delivers updates with sufficiently low latency for the application's requirements.

---

### ❌ "Use WebSockets for everything."

No.

Choose based on requirements:

```text
Simple periodic update
→ Polling

Server → Client
→ SSE

Two-way low-latency communication
→ WebSocket
```

---

### ❌ "WebSockets automatically scale horizontally."

No.

Long-lived connections introduce state and require careful load balancing and cross-server coordination.

---

### ❌ "Redis stores all chat messages."

Not necessarily.

A common design is:

```text
Redis
→ ephemeral coordination / presence / Pub/Sub

PostgreSQL
→ durable chat history
```

The exact architecture depends on requirements.

---

### ❌ "If a client disconnects, nothing important happens."

Disconnected clients can miss events.

A production system may need:

```text
Event IDs
Sequence numbers
Acknowledgements
Replay
Persistent event streams
```

depending on delivery requirements.

---

### ❌ "Every event must be persisted."

Not necessarily.

For example:

```text
User typing...
```

may be ephemeral.

But:

```text
Payment completed
```

should generally be durable.

# 🔥 Core Takeaways

* Real-time systems allow clients to receive updates with low latency as events occur.
* **Polling** makes the client repeatedly ask for updates.
* **Long polling** keeps an HTTP request open until an event is available.
* **SSE** provides persistent server-to-client event streaming.
* **WebSockets** provide persistent two-way communication.
* WebSockets are especially useful for chat, gaming, collaboration and interactive real-time applications.
* Real-time communication doesn't replace persistent storage.
* A common architecture is:

  ```text
  WebSocket → real-time communication
  PostgreSQL → durable state
  Redis → fast ephemeral state / coordination
  ```
* WebSocket connections are long-lived and introduce state that must be managed carefully.
* Heartbeats help detect dead connections.
* Clients should reconnect using exponential backoff and jitter.
* Horizontal scaling requires cross-server coordination when clients communicating with one another are connected to different servers.
* Redis Pub/Sub can help distribute events between WebSocket servers.
* Durable event streams are useful when events need to be retained, replayed, or consumed reliably.
* Presence systems track whether users/devices are connected.
* A user can have multiple simultaneous connections.
* Rooms allow events to be broadcast to groups of clients.
* Events should have well-defined schemas and often benefit from unique event IDs.
* Distributed systems can produce duplicate or out-of-order events.
* At-least-once delivery commonly requires **idempotent consumers**.
* Event ordering needs an explicit strategy when ordering matters.
* Backpressure is critical when producers can generate events faster than consumers can process them.
* Not every real-time update needs to be persisted.
* **State updates and business events have different delivery requirements.**
* Graceful shutdown is particularly important for servers holding thousands of long-lived connections.
* The most important architectural question is:

> **"Who needs to know about what changed, how quickly do they need to know, and what happens if they are temporarily disconnected?"**

That question usually determines whether you need polling, SSE, WebSockets, Pub/Sub, a durable event stream, or some combination of them.
