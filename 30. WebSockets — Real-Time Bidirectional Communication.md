# 30. WebSockets — Real-Time Bidirectional Communication 🔄

> **WebSockets provide a persistent connection between a client and server that allows both sides to send messages at any time.**

Normal HTTP:

```text
Client
   │
   │ Request
   ↓
Server
   │
   │ Response
   ↓
Client
```

WebSocket:

```text
Client
   ⇄
   ⇄ Persistent Connection
   ⇄
Server
```

Once connected, either side can send data whenever necessary.

---

# 1. Why Do We Need WebSockets? ⭐⭐⭐

Imagine building a chat application.

With normal HTTP, the client might repeatedly ask:

```text
"Do I have a new message?"

"Do I have a new message?"

"Do I have a new message?"
```

This is polling.

```text
Client
   ↓
GET /messages
   ↓
Server
   ↓
No new messages

Client
   ↓
GET /messages
   ↓
Server
   ↓
No new messages
```

This is inefficient.

With WebSockets:

```text
Client
   ⇄
Persistent connection
   ⇄
Server
```

When a new message arrives:

```text
Server
   ↓
"New message!"
   ↓
Client
```

No new HTTP request is required.

---

# 2. WebSocket Mental Model ⭐⭐⭐

Think of WebSocket as:

> **Open one connection and keep it alive so both sides can communicate whenever they want.**

```text
          WebSocket Connection

Client  ===========================  Server
         ↑                        ↓
         │                        │
      Message                  Message
         │                        │
         └────────────────────────┘
```

Unlike traditional HTTP request/response communication, the connection remains open.

---

# 3. HTTP vs WebSocket ⭐⭐⭐

### HTTP

```text
Client
  ↓ Request
Server
  ↓ Response
Client
```

Then the interaction is finished.

Another request requires another HTTP exchange.

### WebSocket

```text
Client
  ↓
Connection
  ↓
Server

Client  ⇄  Server
Client  ⇄  Server
Client  ⇄  Server
```

The connection stays open.

---

# 4. WebSocket Is Full-Duplex ⭐⭐⭐

A WebSocket connection is **full-duplex**.

This means:

```text
Client → Server
Server → Client
```

can happen independently.

Example:

```text
Client
  │
  │ "Hello"
  ↓
Server
  │
  │ "Welcome"
  ↓
Client
  │
  │ "Send message"
  ↓
Server
  │
  │ "New notification"
  ↓
Client
```

Neither side has to wait for the other to make a request.

---

# 5. WebSocket vs HTTP

| Feature | HTTP | WebSocket |
|---|---|---|
| Connection | Usually request/response | Persistent |
| Communication | Request → Response | Bidirectional |
| Server can initiate data? | Not normally | Yes |
| Real-time | Requires techniques like polling/SSE | Native |
| Connection overhead | Per request | Connection established once |
| Best for | APIs, CRUD | Real-time communication |

---

# 6. WebSocket vs Polling ⭐⭐⭐

Polling:

```text
Client
  ↓
GET /updates
  ↓
Server

Wait

Client
  ↓
GET /updates
  ↓
Server

Wait

Client
  ↓
GET /updates
```

Problems:

```text
Unnecessary requests
Higher latency
More server load
Wasted bandwidth
```

WebSocket:

```text
Client
  ⇄
Persistent connection
  ⇄
Server
```

The server sends data immediately when something happens.

---

# 7. Long Polling

There is another technique called **long polling**.

Instead of immediately returning:

```text
GET /messages
→ No new messages
```

the server keeps the request open:

```text
Client
   ↓
GET /messages
   ↓
Server waits...
   ↓
New message arrives
   ↓
Response
   ↓
Client
```

Then the client makes another request.

This is better than traditional polling but still isn't the same as WebSockets.

---

# 8. WebSocket vs Long Polling

```text
Long Polling:

Client → Request → Server
Client ← Response ← Server

Repeat


WebSocket:

Client ⇄ Persistent Connection ⇄ Server
```

WebSockets are generally more suitable when you need continuous two-way communication.

---

# 9. How a WebSocket Connection Starts ⭐⭐⭐

WebSockets begin with an HTTP request called a **handshake**.

Conceptually:

```text
Client
   │
   │ HTTP Upgrade Request
   ↓
Server
   │
   │ 101 Switching Protocols
   ↓
Client
```

After the handshake:

```text
HTTP
  ↓
WebSocket
```

The connection becomes a WebSocket connection.

---

# 10. The WebSocket Handshake ⭐⭐⭐

The client initially sends an HTTP request containing:

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
```

The important part is:

```http
Upgrade: websocket
```

This tells the server:

> "I want to upgrade this HTTP connection to a WebSocket connection."

---

# 11. Server Response

If the server accepts:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...
```

The important status is:

```text
101 Switching Protocols
```

Now the WebSocket connection is established.

```text
HTTP Handshake
      ↓
101 Switching Protocols
      ↓
WebSocket Connection
```

---

# 12. `ws://` and `wss://` ⭐⭐⭐

WebSocket URLs look like:

```text
ws://example.com/socket
```

or:

```text
wss://example.com/socket
```

The difference:

```text
ws://
```

is the unencrypted WebSocket protocol.

```text
wss://
```

is WebSocket over TLS.

Think:

```text
http://  →  ws://
https:// →  wss://
```

In production, prefer:

```text
wss://
```

# 20. Broadcasting ⭐⭐⭐

Suppose you have a chat room:

```text
User A
User B
User C
```

User A sends:

```text
"Hello everyone"
```

The server needs to send it to:

```text
User B
User C
```

This is broadcasting.

```text
                 Server
                /      \
               ↓        ↓
           User B     User C
```

Example:

```javascript
wss.clients.forEach((client) => {
    if (client.readyState === WebSocket.OPEN) {
        client.send(message);
    }
});
```

# 23. The Scaling Problem ⭐⭐⭐

Imagine two WebSocket servers:

```text
          Load Balancer
           /         \
          ↓           ↓
      Server A     Server B
       /   \         /   \
      ↓     ↓       ↓     ↓
   User1 User2   User3 User4
```

User 1 connects to Server A.

User 3 connects to Server B.

Now User 1 sends a message to User 3.

Server A knows about User 1.

But:

```text
Server A
   ↓
Doesn't know about User 3
```

This creates a distributed systems problem.

---

# 24. Redis Pub/Sub ⭐⭐⭐

A common solution is Redis Pub/Sub.

```text
User 1
   ↓
Server A
   ↓
Redis Pub/Sub
   ↓
Server B
   ↓
User 3
```

Architecture:

```text
             Redis
          Pub / Sub
          /       \
         ↓         ↓
    Server A    Server B
       ↓           ↓
    Users       Users
```

When Server A receives a message:

```text
Server A
   ↓
Publish
   ↓
Redis
   ↓
Server B
   ↓
User 3
```

---

# 25. Why Redis Helps

Redis acts as a communication layer between WebSocket servers.

```text
Server A
   ↓
Publish event
   ↓
Redis
   ↓
Subscribers
   ↓
Server B / C / D
```

This allows multiple application instances to coordinate.

# 32. Heartbeats / Ping-Pong ⭐⭐⭐

What if the client disappears without properly closing the connection?

The server may think:

```text
"Connection is still alive."
```

Heartbeat mechanisms help detect dead connections.

Conceptually:

```text
Server
   ↓
PING
   ↓
Client
   ↓
PONG
   ↓
Server
```

If the client stops responding:

```text
No PONG
   ↓
Connection considered dead
   ↓
Close connection
```

This prevents stale connections.

---

# 33. Why Heartbeats Matter

Imagine:

```text
100,000 connections
```

Some users disconnect because of:

```text
Network loss
Laptop sleep
Phone switching networks
Wi-Fi failure
Browser crash
```

Without connection cleanup:

```text
Dead connections
      ↓
Resources remain allocated
      ↓
Memory / file descriptors wasted
```

Heartbeats help maintain healthy connections.

---

# 34. Reconnection ⭐⭐⭐

Real networks fail.

A client may lose connection:

```text
Client
   ↓
WebSocket
   X
Network failure
```

A good client should reconnect.

```text
Connected
   ↓
Disconnected
   ↓
Wait
   ↓
Reconnect
   ↓
Connected
```

---

# 35. Exponential Backoff ⭐⭐⭐

Don't reconnect thousands of times immediately.

Bad:

```text
Disconnect
 ↓
Reconnect
 ↓
Fail
 ↓
Reconnect
 ↓
Fail
 ↓
Reconnect
```

Better:

```text
Attempt 1 → immediately
Attempt 2 → wait
Attempt 3 → wait longer
Attempt 4 → wait longer
```

Example:

```text
1 second
2 seconds
4 seconds
8 seconds
16 seconds
```

Usually with some random jitter.

This prevents a large number of clients from reconnecting simultaneously.

---

# 36. Ordering

WebSocket messages sent over a single connection are generally delivered in order.

Example:

```text
Message 1
Message 2
Message 3
```

The receiver expects:

```text
1
2
3
```

However, once you introduce multiple servers, queues, retries, or independent processing systems, application-level ordering can become more complicated.

---

# 37. Delivery Guarantees ⭐⭐

WebSockets themselves don't automatically give you a complete business-level delivery guarantee.

You may need to design for:

```text
At-most-once
At-least-once
Application-level acknowledgements
Message IDs
Persistence
Replay
```

For important messages, don't assume:

```text
"Sent over WebSocket"
=
"Definitely processed by the recipient"
```

```text

   ↓

   ↓
```

# 39. WebSocket Backpressure ⭐⭐

What happens if the server sends messages faster than the client can process them?

```text
Server
 ↓↓↓↓↓↓↓↓↓↓↓
Client
 ↓
Can't keep up
```

The system can accumulate buffered messages.

This can cause memory problems.

Production systems need to consider:

```text
Buffer limits
Rate limits
Dropping low-value messages
Disconnecting slow clients
Flow control
```

# 44. When NOT to Use WebSockets ⭐⭐⭐

Don't automatically choose WebSockets just because they're "real-time."

For simple CRUD:

```text
GET /users
POST /users
GET /products
```

normal HTTP is usually better.

For server-to-client streaming where the client doesn't need to send messages back continuously, **Server-Sent Events (SSE)** may be simpler.

Use the simplest technology that solves the problem.

# 55. Common WebSocket Mistakes 🚨

### Mistake 1 — Using WebSockets for everything

Not every API needs persistent connections.

---

### Mistake 2 — No authentication

Anyone could connect.

---

### Mistake 3 — No heartbeat

Dead connections may remain open.

---

### Mistake 4 — No reconnection strategy

Temporary network failures become permanent disconnections.

---

### Mistake 5 — No message validation

Untrusted clients can send malformed or malicious messages.

---

### Mistake 6 — Assuming one server forever

A design that works on one machine may fail when scaled horizontally.

---

### Mistake 7 — Keeping all important state in server memory

A restarted server loses it.

---

### Mistake 8 — Ignoring backpressure

A slow client can consume excessive resources.

# 56. Interview Questions ⭐⭐⭐

### Q1. What is WebSocket?

WebSocket is a protocol that provides a persistent, full-duplex communication channel between a client and server.

---

### Q2. How is WebSocket different from HTTP?

HTTP typically follows:

```text
Request → Response
```

WebSocket provides:

```text
Persistent bidirectional communication
```

It begins with an HTTP upgrade handshake.

```text

 ↓

 ↓
101 Switching Protocols

WebSocket
```

Both client and server can send messages independently at any time.

Secure WebSocket communication over TLS.

---

For applications requiring frequent, low-latency, bidirectional communication.

Examples:

```text

Live dashboards
Real-time notifications
```

```text
Client
  ↓

  ↓
Server
  ↓
Response


WebSocket

Client
  ⇄
```

# 60. Key Takeaways

> **WebSockets provide persistent, bidirectional communication.**

```text
Client ⇄ Server
```

> **They are useful when low-latency real-time communication is required.**

```text
Chat
Games
Live dashboards
Notifications
Collaboration
```

> **A WebSocket starts with an HTTP upgrade handshake.**

```text
HTTP
 ↓
101 Switching Protocols
 ↓
WebSocket
```

> **Production WebSockets require more than just opening a connection.**

```text
Authentication
Authorization
Heartbeats
Reconnection
Rate limiting
Validation
Backpressure
Observability
```

> **Scaling requires distributed-system thinking.**

```text
Load Balancer
      ↓
Multiple WS Servers
      ↓
Redis / Message Broker
```

> **Use WebSockets when the problem actually requires persistent two-way communication.**

```text
Simple CRUD
   ↓
HTTP / REST

Server → Client streaming
   ↓
SSE

Bidirectional real-time
   ↓
WebSocket
```

**WebSockets turn the client-server relationship from a request/response interaction into a persistent communication channel where both sides can communicate in real time.**
