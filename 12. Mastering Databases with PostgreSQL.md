# 12. Mastering Databases with PostgreSQL 🗄️

> **A backend doesn't just process data. It has to remember it.**
>
> The database is the persistence layer that allows information to survive application restarts, be shared across users, remain consistent under concurrent access, and be queried efficiently.

The goal of this chapter is **not to memorize SQL syntax**.

The important goal is to understand:

```text
Why do we need databases?
        ↓
How should data be modeled?
        ↓
How does the database protect data?
        ↓
How should backend code interact with it?
        ↓
How do we make queries fast?
```

---

# 1. Why Do We Need Databases?

Imagine a to-do application.

You create:

```text
Buy groceries
Study backend
Finish project
```

Then you close the application.

When you open it tomorrow, you expect those tasks to still exist.

That property is called:

> **Persistence**

Persistence means data survives beyond the lifetime of the program that created it.

```text
Application
     ↓
Create data
     ↓
Database
     ↓
Application stops
     ↓
Application starts again
     ↓
Data still exists
```

Without persistence:

```text
Application starts
     ↓
Empty data
```

Every time the application restarted, everything would disappear.

Databases solve this fundamental problem.

---

# 2. What Is a Database?

The word **database** is broader than it initially sounds.

At a very high level, any persistent structured storage system that lets you manage data can be considered a database.

Examples:

```text
Phone contacts
Browser local storage
Session storage
Cookies
Text files
```

Even a simple text file can be considered a very primitive form of database.

The important abstraction is:

```text
Persistent Storage
       +
Data Operations
       ↓
Create
Read
Update
Delete
```

In backend engineering, however, when we say "database", we generally mean a proper database system designed to efficiently handle large amounts of persistent data and concurrent operations.

---

# 3. RAM vs Disk

This is an important mental model.

Think of:

```text
RAM = Whiteboard
Disk = Filing Cabinet
```

### RAM

```text
Very fast
Limited capacity
Expensive
Volatile
```

If the machine loses power:

```text
RAM → Data disappears
```

### Disk

```text
Slower
Much larger
Cheaper
Persistent
```

Data survives application restarts.

Therefore traditional databases commonly use **disk/secondary storage** for persistence.

Caching systems such as Redis or in-memory caches often use RAM because they prioritize speed.

---

# 4. Why Not Store Everything in RAM?

RAM is extremely fast.

So why not simply keep the entire database in RAM?

Because:

```text
RAM
├── Expensive
├── Limited
└── Volatile
```

While disk provides:

```text
Disk
├── Cheap
├── Large
└── Persistent
```

A database therefore makes a trade-off:

> **Use persistent storage for durability and enough capacity, while using memory and caching where speed is important.**

This distinction becomes especially important later when we study caching.

A DBMS provides that functionality.

# 7. Why Not Use Text Files?

You could theoretically store your users in:

```text
users.txt
```

But problems appear very quickly.

The video highlights three major issues:

```text
Text File
│
├── Parsing
├── No enforced structure
└── Concurrency
```

---

# 8. Problem 1 — Parsing

Suppose:

```text
users.txt
```

contains:

```text
1,Yusuf,yusuf@example.com,22
2,John,john@example.com,30
3,Jane,jane@example.com,25
```

To find user 2, your application must:

```text
Open file
 ↓
Read data
 ↓
Parse lines
 ↓
Split fields
 ↓
Search
 ↓
Return result
```

The application itself has to implement all of this.

A DBMS provides optimized mechanisms for querying data.

---

# 9. Problem 2 — No Structure

A text file doesn't naturally enforce:

```text
age → number
email → valid structure
id → unique
user_id → existing user
```

Someone could accidentally store:

```text
Yusuf,banana,hello
```

and the file would happily accept it.

A relational database can enforce structure at the database level.

---

# 10. Problem 3 — Concurrency

This is much more serious.

Imagine the database contains:

```text
amount = 40
```

Two users modify it simultaneously.

### User A

```text
Read 40
Add 20
Write 60
```

### User B

```text
Read 40
Subtract 20
Write 20
```

Depending on how those operations interleave, the final value could become:

```text
60
```

or:

```text
20
```

One update may effectively overwrite another.

A DBMS provides mechanisms for managing concurrent access and maintaining consistency.

# 12. Relational Databases

Relational databases organize information into:

```text
Tables
 ↓
Rows
 ↓
Columns
```

Example:

```text
users

id | name  | email
---|-------|----------------
1  | Yusuf | yusuf@example
2  | John  | john@example
```

The structure is defined ahead of time.

```text
Column
 ↓
Data Type
 ↓
Constraints
```

Tables can be related using concepts such as:

```text
Primary Keys
Foreign Keys
```

Examples:

```text
PostgreSQL
MySQL
SQL Server
```

---

# 13. Relational Database = Structured Schema

Suppose:

```text
users
```

has:

```text
id       → UUID
email    → TEXT
name     → TEXT
age      → INTEGER
```

A new row is expected to follow that schema.

This strict structure provides an important advantage:

> **Data integrity**

You know what kind of data exists in the database.

---

# 14. Non-Relational Databases

A non-relational database generally provides a more flexible data model.

For example, MongoDB uses:

```text
Database
   ↓
Collection
   ↓
Documents
```

One document might contain:

```json
{
  "name": "Yusuf",
  "age": 22
}
```

Another could have:

```json
{
  "name": "John",
  "skills": ["Go", "Rust"],
  "experience": 5
}
```

The structures can be more flexible.

---

# 15. Flexibility vs Integrity

The fundamental trade-off presented in the video is:

```text
Relational
   ↓
Strong structure
   ↓
Strong integrity

Non-relational
   ↓
Flexible structure
   ↓
More responsibility in application code
```

With a flexible schema:

```text
Application
   ↓
Must enforce more rules
```

With a relational database:

```text
Application
   ↓
Database constraints
   ↓
Integrity enforced
```

The video uses examples such as CRM systems as a good fit for relational databases because the data has strong relationships and consistency requirements, while flexible content systems can benefit from a more flexible data model.

# 26. Decimal vs Floating Point

This is a very important interview concept.

Suppose you store:

```text
price = 19.99
```

Floating-point representation can introduce precision issues.

For values where **exactness matters**, such as:

```text
Money
Prices
Financial calculations
```

prefer:

```text
DECIMAL / NUMERIC
```

rather than floating-point types.

---

# 27. Why Not Float for Money?

Floating-point numbers use a representation that cannot represent every decimal value exactly.

That can result in tiny precision differences.

For financial calculations, tiny differences matter.

Therefore:

```text
Money
 ↓
DECIMAL / NUMERIC
```

Where small approximation is acceptable and performance characteristics are more important:

```text
Scientific calculations
 ↓
Floating point
```

The video uses this distinction specifically when discussing price versus less precision-sensitive fractional values.

# 28. CHAR vs VARCHAR vs TEXT

PostgreSQL has:

```text
CHAR
VARCHAR
TEXT
```

### CHAR

Fixed-length string.

If you define:

```sql
CHAR(10)
```

and store:

```text
AB
```

the value is padded to the fixed length.

Use this only when a fixed length genuinely makes sense.

---

# 29. VARCHAR

```sql
VARCHAR(255)
```

means:

> A variable-length string with a maximum length of 255.

The actual stored value doesn't need to be 255 characters.

---

# 30. TEXT

```sql
TEXT
```

allows variable-length textual data without an application-chosen maximum length in the column definition.

The video strongly favors `TEXT` for general-purpose strings in PostgreSQL rather than blindly using `VARCHAR(255)`. It notes that `TEXT` and `VARCHAR` have no meaningful performance difference for ordinary PostgreSQL use and that arbitrary `255` limits often come from conventions associated with other databases.

---

# 31. Where Should String Length Be Enforced?

Suppose your product requirement says:

```text
username ≤ 50 characters
```

You don't necessarily need:

```sql
VARCHAR(50)
```

just to enforce that rule.

The video's approach is:

```text
Database
   ↓
TEXT

Application validation
   ↓
username.length ≤ 50
```

This keeps the database schema simpler and avoids unnecessary schema migrations when the product requirement changes.

# 35. ENUM

PostgreSQL allows custom enum types.

For example:

```sql
CREATE TYPE project_status AS ENUM (
    'active',
    'completed',
    'archived'
);
```

Now:

```text
status → project_status
```

can only contain those values.

---

# 36. Why Use ENUM?

Two major benefits highlighted by the video:

### 1. Data Integrity

The database rejects invalid values.

```text
active
completed
archived
```

are valid.

```text
banana
```

is rejected.

### 2. Documentation

Someone reading the schema immediately knows the allowed values.

Without an enum:

```text
status TEXT
```

they would have to search the application code to discover the possible values.

Enums therefore make the database schema more self-documenting.

# 37. Constraints

A database schema isn't just:

```text
Table
+
Columns
```

It also contains **constraints**.

Constraints are rules enforced by the database.

Important ones:

```text
PRIMARY KEY
FOREIGN KEY
NOT NULL
UNIQUE
CHECK
```

---

# 38. Primary Key

A primary key uniquely identifies a row.

Example:

```text
users

id
---
1
2
3
```

A primary key implicitly provides:

```text
UNIQUE
NOT NULL
```

Therefore:

```text
id = NULL
```

is invalid.

And:

```text
id = 1
id = 1
```

cannot appear twice.

---

# 39. NOT NULL

By default, PostgreSQL columns can contain `NULL` unless constrained otherwise.

If a field is required:

```sql
email TEXT NOT NULL
```

then:

```text
email = NULL
```

is rejected.

The video emphasizes being deliberate about `NOT NULL` because unnecessary nullability can make application state harder to reason about.

---

# 40. UNIQUE

A unique constraint prevents duplicate values.

Example:

```sql
email TEXT UNIQUE
```

Then:

```text
user1@example.com
```

can exist once.

Attempting to insert another row with the same value fails.

Useful for:

```text
Email
Username
External IDs
Other naturally unique values
```

---

# 41. CHECK

A `CHECK` constraint lets the database enforce a custom condition.

For example:

```sql
CHECK (priority BETWEEN 1 AND 5)
```

Now:

```text
priority = 3
```

is valid.

But:

```text
priority = 55
```

is rejected.

This is database-level data integrity.

---

# 42. Foreign Key

A foreign key establishes a relationship between tables.

Suppose:

```text
users
```

contains:

```text
id = 123
```

and:

```text
projects
```

contains:

```text
owner_id = 123
```

Then:

```text
projects.owner_id
       ↓
users.id
```

is a foreign-key relationship.

The referenced user must exist.

---

# 43. Referential Integrity

This is a critical database concept.

Suppose:

```text
users
  1

projects
  project A
  owner_id = 1
```

Now someone tries:

```text
DELETE user 1
```

What happens?

The database needs a rule.

This is where referential integrity actions come in.

---

# 44. ON DELETE RESTRICT

With:

```sql
ON DELETE RESTRICT
```

the database refuses to delete the referenced user if dependent rows exist.

```text
Delete User
    ↓
Has Projects?
    ↓
YES
    ↓
❌ Reject
```

This prevents accidentally creating orphaned data.

---

# 45. ON DELETE CASCADE

With:

```sql
ON DELETE CASCADE
```

deleting the parent automatically deletes related records.

```text
Delete Project
      ↓
Delete associated Tasks
```

This is useful when child records have no meaningful existence without the parent.

But:

> **CASCADE is powerful and should be used carefully.**

A single delete can cause many records to disappear.

---

# 46. ON DELETE SET NULL

Another option:

```sql
ON DELETE SET NULL
```

If the parent is deleted:

```text
owner_id
   ↓
NULL
```

The child survives, but its reference disappears.

This requires the child column to allow `NULL`.

---

# 47. ON DELETE SET DEFAULT

Another possibility is:

```sql
ON DELETE SET DEFAULT
```

The foreign-key value is replaced by the column's default value.

This only makes sense if an appropriate default exists.

---

```text

   ↓

```

# 58. Down Migration

A down migration reverses the change.

If up did:


```sql

```

Conceptually:

```text
New DB State
    ↓

    ↓

```

# 63. Parameterized Queries

This is one of the **most important backend database security concepts**.

Never construct SQL by directly concatenating user input.

### ❌ Dangerous

```javascript
const query =
  `SELECT * FROM users WHERE email = '${email}'`;
```

If an attacker provides malicious SQL syntax, your query structure can be manipulated.

---

# 64. SQL Injection

Imagine:

```text
email =
' OR 1=1 --
```

With unsafe string concatenation, the resulting SQL can become something entirely different from what you intended.

This is:

> **SQL Injection**

---

# 65. Parameterized Query

Instead:

```javascript
const query =
  `SELECT * FROM users WHERE email = $1`;

db.query(query, [email]);
```

Now:

```text
SQL structure
      +
User data
```

are treated separately.

The database knows:

```text
$1
```

is a value, not SQL code.

---

# 66. Parameterization Mental Model

```text
❌ String Concatenation

User Input
    ↓
SQL String
    ↓
Database


✅ Parameterized Query

SQL Structure ─────┐
                   ├──→ Database
User Value ────────┘
```

This is a fundamental backend security rule.

> **Never concatenate untrusted values into SQL.**

The video explicitly treats parameterized queries as the secure mechanism for passing user values to the database.

# 77. What Is an Index?

With an index:

```text
   ↓

   ↓
```

A database index provides a similar optimization for finding rows.

# 78. Without an Index

```text

1,000,000 rows
```

Conceptually:

```text

Row 2 → match?
Row 3 → match?

```

That becomes expensive as the dataset grows.


Conceptually:

```text

    ↓

```

The database doesn't need to inspect every row.

This can dramatically improve lookup performance.

# 84. Index Trade-off

Indexes aren't free.

They improve:

```text
READ performance
```

but add overhead to:

```text
INSERT
UPDATE
DELETE
```

because the index itself must be maintained.

Think:

```text
              Index
             /     \
            ↓       ↓
        Faster     More
         Reads    Write Cost
```

Therefore:

> **Don't index everything.**

Index based on actual query patterns and performance requirements.

Indexes should be driven by workload, not superstition.

# 🧠 Interview Mental Models

## What is a database?

> A persistent system that stores data and provides mechanisms to create, read, update, and delete it.

---

## Why do we need a DBMS?

> A DBMS provides efficient data access, organization, integrity, concurrency handling, and security instead of forcing application code to manage raw files.

---

## Relational vs NoSQL?

```text
Relational
→ Structured schema
→ Tables
→ Relationships
→ Strong integrity

NoSQL
→ Flexible schema
→ Documents/other models
→ Useful for certain flexible-data workloads
```

---

## Why PostgreSQL?

> PostgreSQL is open source, feature-rich, reliable, extensible, and provides strong relational capabilities along with powerful JSON/JSONB support.

---

## Primary key?

> A column or set of columns that uniquely identifies a row. A primary key is non-null and unique.

---

## Foreign key?

> A constraint that ensures a value refers to a valid record in another table.

---

## Referential integrity?

> Maintaining consistency between related tables through constraints such as foreign keys and delete actions.

---

## Migration?

> A version-controlled change to the database schema that can be applied consistently across environments.

---

## Index?

> A data structure maintained by the database to make certain queries faster by avoiding expensive scans.

---

## Why not index everything?

> Indexes improve reads but introduce storage and write-maintenance overhead.

---

## Parameterized query?

> A query where SQL structure and user-provided values are kept separate, preventing user input from being interpreted as SQL code.

# ⚠️ Interview Traps

### ❌ "PostgreSQL is SQL."

### ✅

```text
SQL
→ Query language

PostgreSQL
→ Database management system
```

---

### ❌ "NoSQL has no schema."

### Better answer:

> NoSQL databases often provide more flexible or less rigidly enforced schemas than relational databases, but that doesn't mean the application has no data model or structure.

---

### ❌ "Foreign keys are automatically indexed."

### Important:

> A foreign-key constraint does not automatically create an index on the referencing column in PostgreSQL. Primary keys are automatically backed by unique indexes.

---

### ❌ "Indexing always makes the database faster."

### No.

Indexes generally improve certain reads but introduce:

```text
Storage cost
Write overhead
Maintenance cost
```

---

### ❌ "Use VARCHAR(255) for every string."

### Not a good PostgreSQL default.

The video recommends `TEXT` for general strings and enforcing product-specific length rules at the application layer when appropriate.

---

### ❌ "Use FLOAT for prices."

### Usually wrong.

For exact financial values:

```text
DECIMAL / NUMERIC
```

is the safer choice.

---

### ❌ "Validation prevents SQL injection."

### Incomplete.

Use:

```text
Validation
+
Parameterized Queries
```

Validation checks whether the input is acceptable.

Parameterization ensures the input is treated as **data rather than SQL code**.

---

### ❌ "CASCADE is always better."

### No.

`ON DELETE CASCADE` can delete large amounts of dependent data.

Use it only when the child records genuinely should disappear with the parent.

# 🔥 Core Takeaways

* **Persistence is the fundamental reason databases exist.**
* Traditional backend databases commonly use disk-based persistent storage.
* RAM is faster but limited and volatile; disk is slower but persistent and much larger.
* A DBMS provides efficient CRUD operations along with organization, integrity, concurrency, and security mechanisms.
* Text files fail to provide the structure, efficient querying, integrity, and concurrency management expected from a DBMS.
* Relational databases provide structured schemas and strong relationships/integrity.
* NoSQL databases provide more flexible data models for appropriate workloads.
* PostgreSQL is a powerful relational database with strong JSON/JSONB support.
* **SQL is the language; PostgreSQL is the database system.**
* Choose data types based on the actual meaning and requirements of the data.
* Use `DECIMAL/NUMERIC` when exact numerical representation matters, such as money.
* PostgreSQL's `TEXT` is a sensible default for many general-purpose string fields.
* `TIMESTAMPTZ` is important when dealing with time across different locations.
* UUIDs are useful identifiers, particularly in distributed systems.
* Enums can enforce valid values and make schemas self-documenting.
* Primary keys uniquely identify rows.
* Foreign keys enforce relationships and referential integrity.
* `NOT NULL`, `UNIQUE`, and `CHECK` allow the database itself to enforce important invariants.
* One-to-one relationships can use the parent's primary key as the child's primary/foreign key.
* One-to-many relationships generally put the foreign key on the "many" side.
* Many-to-many relationships use a linking table.
* Composite primary keys can uniquely identify relationships such as `(project_id, user_id)`.
* **Migrations are version control for your database schema.**
* Seeds provide useful development/test data.
* Parameterized queries are essential for preventing SQL injection.
* Indexes can make frequently used reads dramatically faster.
* Indexes aren't free: they add storage and write-maintenance overhead.
* Consider indexes around frequent `WHERE`, `JOIN`, and `ORDER BY` patterns.
* Database triggers can automate database-level behavior such as maintaining `updated_at`.
* A backend engineer frequently translates API requirements into safe, efficient database queries.

> ### The interview-level mental model
>
> **Don't think of PostgreSQL as "the place where I run SQL queries."**
>
> Think of it as the **integrity and persistence layer of your backend**.
>
> Your API receives a request → validation establishes what is acceptable → the service decides what should happen → the repository constructs safe database operations → PostgreSQL enforces schema/integrity and retrieves the data efficiently → the result travels back through the application.
>
> **Good backend engineering means understanding that entire chain.**
